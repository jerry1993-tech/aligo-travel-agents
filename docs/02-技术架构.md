## 一、技术选型

| 技术 | 选它的理由 | 不选它的话会怎样 |
| --- | --- | --- |
| **AgentScope（vendored）** | 框架已提供 Agent / 中间件 / 工具 / 会话 / 消息总线 / HITL / 多租户 | 自己重造这些轮子，且与上游行为不一致 |
| **FastAPI / Starlette（ASGI）** | 框架的 `create_app` 就是 FastAPI 应用，直接复用其返回值作根应用 | — |
| **纯 ASGI 中间件**（不用 `BaseHTTPMiddleware`） | 后者会**缓冲整个响应体**，SSE 在它上面一个字节都读不出来 | 流式退化成「攒够了再一次性返回」 |
| **DashScope 原生档**（而非 OpenAI 兼容协议打百炼） | 原生档多出 `thinking_enable` / `thinking_budget`，是「显示推理」的基础 | 兼容协议档拿不到这些字段，等于把思考链这条路提前堵死 |
| **PostgreSQL** | 框架的 `AsyncSQLAlchemyStorage` 原生支持；业务表可与框架表分 schema 共存 | 框架自带存储需要关系库 |
| **Redis（`RedisMessageBus`）** | 跨副本的 SSE 事件总线、取消广播、幂等锁 | `InMemoryMessageBus` 在多副本下 SSE 事件收不到（框架注释明示） |
| **Milvus** | 向量检索；单集合政策知识库 + 画像语义召回 | 语义召回无从实现 |
| **自研熔断器**（`src/llm/breaker.py`） | 框架**完全没有**这个能力；重试对付偶发失败，熔断对付持续失败 | 持续失败时每个请求都去撞一次上游 |
| **Prometheus / OTel→Langfuse** | 指标与 trace 是**两件事**：指标看趋势，trace 看单次调用 | — |

## 二、分层

`src/` 是**本项目自己的代码**，与 `third_party/` 里 vendored 的 AgentScope / ReMe 严格分开。
`agentscope` / `reme` 靠**安装元数据**解析（本机 editable，容器里 `pip install` 进 `/opt/venv`），
本项目**不设** `PYTHONPATH=third_party/...`——一旦同时存在两条解析路径，「实际加载的是哪一份代码」就变得不确定。

分层自下而上（依赖方向**只能朝下**，越靠下的层越不依赖框架）：

| 层 | 包 | 职责 | 依赖框架吗 |
| --- | --- | --- | --- |
| 领域层 | `src/domain/` | 实体（`TransportOption`/`HotelOption`/`TravelOrder`/`ApprovalRequest`）、枚举（`Intent`/`LaneName`/`TripStage`/`OrderStatus`/`TaskState`…）、规则引擎（`check_transition`/`check_cabin`/…） | **否** |
| 配置层 | `src/config/` | `schema.py`（形状）+ `loader.py`（来源与合并）——配置的唯一真值入口 | 否 |
| 基础设施 | `src/storage/` `src/observability/` `src/llm/` `src/web_embedding/` | 业务库 engine、指标/trace/日志、模型装配与熔断、Embedding 三档 | 部分 |
| 能力层 | `src/knowledge/` `src/memory/` `src/tools/` `src/chains/` | 知识库检索、长期画像、业务工具、思考链投影 | 部分 |
| 编排层 | `src/orchestration/` | 快慢车道分流、路由交接、上下文注入、动态 Prompt | 部分 |
| 智能体层 | `src/agents/` | 各子智能体的系统提示 + 版本化注册表 | 否（prompts 是纯数据） |
| 服务层 | `src/server/` | FastAPI 装配、路由、中间件、静态资源 | 是 |

**关键约束：纯逻辑与框架耦合必须分开。** 例如 `src/orchestration/__init__.py` **只**导出纯逻辑
（`classifier`、`prompt`），框架耦合的 `lane` / `context` 由使用方按完整路径显式导入。
理由：`classify` 与 `build_system_prompt` 是**最该能脱离框架被验证**的部分，
若把它们与 `agentscope` 一起 export，那么 `from src.orchestration.classifier import classify`
会因为包的 `__init__` 先执行而**顺带**把框架拉进来。
`src/orchestration/__init__.py` 的模块文档说明了这一点，且
`tests/test_orchestration_classifier.py` / `tests/test_orchestration_prompt.py` 在**子进程**里
断言 `agentscope` 不在 `sys.modules` 中（必须子进程——`conftest.py` 早就导入了框架，进程内断言必然假通过）。

## 三、一次对话的数据流：HTTP → SSE

以「用户发一句话，看到逐字流式输出」为例。这条链路上有几个**顺序敏感的**选择，错了不会报错，
只会表现为某种「看起来正常但不对」的行为。

```text
浏览器
  │  POST /chat/  (X-User-ID 或 Bearer JWT)
  ▼
[中间件，由外到内] TraceContext → HttpMetrics → Auth → 降级凭据播种 → RateLimit
  │  Auth 解析凭据，**先删光客户端自带的 x-user-id 再注入**可信值
  ▼
框架 AppService.chat_service  →  一轮 Agent 回复
  │
  ├─ 编排层介入：LaneRouter 判快慢车道 → 短路「第一次模型调用」
  ├─ ContextInjection.on_system_prompt → 把画像/槽位拼进 system prompt
  ├─ 模型按需调用工具（src/tools/），工具返回 ToolChunk（JSON 卡片）
  └─ 每个环节产出 AgentEvent，依次 log_append + publish
  │
  ▼
RedisMessageBus  (agentscope:session:events:{sid})
  │
  ├─ 框架原生：GET /sessions/{id}/stream  → 原始事件流（前端得自己维护状态机）
  └─ 本项目：GET /api/v1/sessions/{id}/chains → **加工好的**思考链全量快照
```

### 3.1 为什么中间件的顺序不能反

`Starlette.add_middleware` 内部是 `user_middleware.insert(0, ...)`，构建时按 `reversed(...)` 迭代，
**列表里越靠后 = 越外层**。目标链（由外到内）是：

```text
TraceContext → HttpMetrics → Auth → 降级凭据播种 → RateLimit → 应用
```

三条最容易搞错：

- **`HttpMetrics` 在 `Auth` 之外** —— 放里面的话，被 401/429 拒绝的请求不进指标，
  而鉴权失败率与限流率恰恰是最需要看板的两条曲线。更糟的是它看起来完全正常：有流量、有延迟，
  只是永远看不到被拒的那部分。
- **降级凭据播种（`MockCredentialSeedMiddleware`）在 `Auth` 之内、`RateLimit` 之外** ——
  它要读 `Auth` 写进 `scope["state"]` 的身份才知道该给谁播种；同时它自己会写库，
  该排在一个注定 429 的请求**之后**（那种请求不该产生写）。放到 `Auth` 之外是本层最阴的失效：
  读不到身份 ⇒ 永远不播种，而它是**静默**的（无日志、无异常），
  症状与「零密钥下发送按钮是灰的」一模一样，分不出是没播种还是播种了没用。
- **`RateLimit` 在 `Auth` 之内** —— 它要读 `Auth` 写进 `scope["state"]` 的身份当限流键。
  顺序反了不会报错，只会让所有请求退化成按客户端 IP 限流，多人共用出口 IP 时互相误伤。

外层是 `TraceContext`，才能保证**所有**日志与指标都带上 trace id（这处曾经写反过，
trace id 在某些路径上丢失）。顺序由 `tests/test_api_v1.py::test_middleware_stack_order` 逐字断言。

### 3.2 鉴权：中间件**注入** `X-User-ID`，而不是替换框架的 `get_current_user_id`

框架的 `get_current_user_id` 自称临时方案，但它在**13 个路由文件、85 个 `Depends` 点**被使用。
替换它意味着把这 85 处全改掉，且框架每次升级都可能加新的调用点——**漏掉的那一处就是一个没有鉴权的口子**，
且不会报错。所以做法是「一处修改、全链路生效」：中间件解析凭据后**先删光客户端自带的 `x-user-id`
再注入**可信值。⚠️「先删光」不是洁癖：Starlette 的 `Headers` 取**第一个**匹配项，
只追加不删除的话，客户端伪造的 `X-User-ID` 会排在前面并**胜出**——JWT 通道的全部安全价值就在这一行删除上。

⚠️ 本节讲的是「身份**怎么**被注入」；唯一一条「凭据格式完全合法、也必须拒绝」的例外见 3.6：
`aligo-system` 是系统凭据的属主，客户端（以及任何 token 的 `sub`）永远不得声明它。

### 3.3 为什么另起 `/chains` 端点，不复用框架的 `/stream`

框架那条推的是**原始事件**，前端要自己维护「哪些工具正在跑、谁成功了」的状态机——
而那套状态机才是最容易写错的部分：参数是分片到达的、结果也是分片的、人工确认之后还会补发一个
`reply_id` 相同的续接 `REPLY_START`。把它放前端，等于每个前端实现各写一遍，且错了不报错，
只表现为「进度条不消失」。本项目把这份状态机（已在 `src/chains/collector.py` 里被穷举测试过）
放到服务端跑，推**已加工好的任务清单**。代价是多一条连接、多一份每连接的投影状态，
而这个代价是刻意接受的：投影算错了不影响业务数据，前端因此可以对这条连接完全无状态。

帧格式与去重、回放顺序的细节见 `docs/01-功能接口.md` 第 2.3 节。

### 3.4 前端产物托管在 `/` 上：两条**不能想当然**的规则

前端（`web/frontend`，基于 `examples/web_ui` 二次开发）由 vite 构建到 `src/server/static/`，
再由 `create_root_app` 的**最后一步** `app.mount("/", SpaStaticFiles(...))` 托管。
选择「挂到 `/` 上」而不是另起一个前端容器，是为了不改 `Dockerfile`：
产物随 `COPY src` 进镜像，开发期被只读挂载覆盖即可。

代价是**前端的路径与后端的路由共处一个命名空间**，于是有两条规则必须显式写下来 ——
它们都不是「顺手就对了」，漏掉任何一条的症状都只在浏览器里看得见：

| 规则 | 漏掉的症状 | 位置 |
| --- | --- | --- |
| 产物**根目录下的每个文件**都要免鉴权 | 页面上一个碎图标（浏览器取 `<img src="/agentscope.svg">` 时**不带任何自定义头**，拿不到 `X-User-ID`） | `spa.static_root_public_paths` 按磁盘内容算，装配期传给鉴权中间件 |
| 浏览器导航（`Accept: text/html` 的 GET）要免鉴权**且**返回首页 | 在 `/chat` 页面按 F5 白屏。`StaticFiles(html=True)` 的 `html` **不做** SPA 回退，它只在「请求的是一个已存在的目录」时补 `index.html` | `spa.SpaStaticFiles` + `spa.is_spa_navigation` |

⚠️ 免鉴权**不等于**不碰请求头：放行前会**剥掉**客户端自带的 `x-user-id`。
否则 `curl -H 'X-User-ID: 别人' -H 'Accept: text/html' /mcp` 就绕过了整套鉴权——
`Accept` 是普通请求头，谁都能填，而框架的 `get_current_user_id` 只认 `x-user-id` 的值、不看来源。

**已知限制**：前端的 `/mcp`、`/skill` 两个路由与框架的 `GET /mcp`、`GET /skill` **同路径**，
而 API 路由在静态挂载之前注册、优先匹配，所以在浏览器里直接刷新这两个地址会看到接口的 JSON。
点击导航（history pushState，不经服务端）不受影响。上游 `examples/web_ui` 的设计是
「前端独立部署、用 `server_url` 指向后端」，同源托管下的这一处冲突是它的固有代价。

### 3.5 三条链路的语义

| 链路 | 输入 | 输出 | 谁消费 |
| --- | --- | --- | --- |
| 对话 | `/chat/` | 模型回复（含工具调用） | 用户 |
| 思考链 | 事件总线 | 任务清单**全量快照** | 前端进度条 |
| 事件 | 每个环节 | `AgentEvent`（28 种 `EventType`） | 上述两条 + trace |

### 3.6 保留身份：一条「凭据合法但必须拒绝」的规则

3.2 讲的是「身份**怎么**被注入」；这一节讲它唯一的例外——有一个 user_id，
无论来自哪条通道，客户端都不得声明它。规则的三块拼图必须同时在位，缺任何一块整条规则就失效：

| 拼图 | 位置 | 作用 |
| --- | --- | --- |
| 身份定义 | `src/llm/identity.py:42`（`SYSTEM_USER_ID = "aligo-system"`） | 保留身份与系统凭据属主共用**同一个**真相源 |
| 请求拦截 | `src/server/middleware/auth.py:392-398`（直连）/ `:461-468`（JWT）/ `:360-363`（匿名） | 三条通道放行前各过一遍 `is_reserved_user_id`，命中即 403 |
| 共享侧对偶 | `src/llm/system_credential.py:264-324` | 策略里 `viewer_id == SYSTEM_USER_ID`——属主自己不会在共享列表里再出现一次 |

**aligo-system 是谁**：运营者在 `.env` 里配了真 key 时，系统把 key 写成**一条**
属主为 `aligo-system`、id 固定为 `aligo-system-model` 的凭据
（`src/llm/system_credential.py:100`），再经资源访问策略以 READ 共享给全体已鉴权用户
（见第五节）。也就是说，这个身份名下挂着**全公司的模型密钥**。

**为什么它能读出明文**：框架的可见性规则是「属主读自己的凭据是明文，非属主才打码」。
打码只发生在 `record.user_id != viewer_id` 时（`app/_service/_access.py:562-567`），
而属主走的两条只读路径——列表 `app/_service/_access.py:269-271`、单条
`app/_service/_access.py:346-351`——给的都是**未打码**的 `data` 与 `editable: true`。
于是修复前实测：

```text
X-User-ID: alice         → GET /credential/  data 打码成 {type, name}
X-User-ID: aligo-system  → GET /credential/  data 里有 api_key 明文、editable: true
X-User-ID: aligo-system  → DELETE /credential/aligo-system-model → 204
```

最后一行是更狠的那一半：不只把密钥读走，还能**删掉那条凭据**——全体用户的模型当场失效。
`tests/test_default_model.py:931` 把这三条原始输出抄进 docstring 并逐条断言 403。

**为什么这不是「提权」**：`X-User-ID` 直连通道本来就**不校验真伪**（见 3.2），
任何人写 `X-User-ID: alice` 就是 alice。所以病灶不是「伪造了一个更高的权限」，
而是**把一个内部身份当成了可声明的身份**——系统身份从来不是给客户端用的登录名，
它只是存储层的一个隔离维度（`src/llm/identity.py:36-42`）。JWT 通道同理：
签名合法 ≠ 这个身份可以被用来登录，保留身份根本没有对应的登录主体。

**为什么三条通道一条都不能少**：直连通道身份即请求头（漏拦 = 直接能用）；
JWT 的 `sub` 由签发方填写（漏拦 = 一张合法 token 就能当系统用）；
`require_user_header=false` 的匿名通道**不重写请求头**（漏拦 = 关掉这个开关
就成了绕过规则的捷径，而这两个配置项在运维眼里毫不相干）。
`tests/test_auth_middleware.py:841` 起的一组用例把三条通道各钉一遍。

**为什么是 403 而不是 401**：401 的语义是「你没提供可用凭据」，客户端据此会去走
登录流程——但**没有任何一次登录能让人变成系统身份**，于是它只会陷入「登了再试、再 401」。
403 说的是「凭据本身没问题，但这件事不能做」，也告诉调用方别再重试
（`src/server/middleware/auth.py:543-576`，状态码在 `src/server/middleware/auth.py:573`）。
响应体**不回显**被拒绝的 id，但理由**不是**「名字要保密」——它压根不是秘密：
常量就写在 `src/llm/identity.py:42`，本文档与 README 都在讲它，配了密钥的部署里
`GET /credential/` 返回的那条共享凭据记录上也带着这个属主。回显一个调用方
自己填进来的字符串对排查没有半点帮助（它本来就知道自己发了什么），
而真正拦下这次请求的从来只是 `is_reserved_user_id` 那行判断。

**为什么常量住在一个零 import 的叶子模块**：鉴权中间件在**每一次请求**的路径上，
而 `src/llm/system_credential.py` 在 import 期会拉进 `agentscope.app.access`（策略基类）。
让中间件为了一个字符串常量多背一个框架子包，等于把「agentscope 的 import 期副作用」
放大成「服务起不来」——而零密钥启动恰恰是 README 承诺的开箱即用路径。所以定义放在
`src/llm/identity.py`（零 import，理由见 `src/llm/identity.py:17-31`），
`src/llm/system_credential.py` 只做 re-export（`src/llm/system_credential.py:89-94`）。
⚠️ 不要为了「顺手」往 `identity.py` 加需要 import 的东西——它一旦有了依赖，这条理由就失效。

**判据是精确比较**（调用方先 `strip()`，`src/llm/identity.py:66-88`），不做大小写折叠：
框架是拿请求头值与 `record.user_id` 做 `==` 的（`app/storage/_sql/_storage.py:807`），
所以 `ALIGO-SYSTEM` 在框架眼里本就是**另一个用户**，凭据照样打码。写得更「严格」
只会误伤形似的真实用户，换不来任何安全收益——`tests/test_auth_middleware.py:930`
断言四个形似值全部放行。

### 3.7 回复守卫：把「内部过程」与「编造数值」挡在用户之外

`ReplyGuardMiddleware`（`src/orchestration/reply_guard.py`）是编排层里唯一**改写输出内容**的
中间件，也是全项目最大的一块判据代码（约 2400 行，其中大半是注释与反例）。它挂在
`main_plan` 一个 agent 上（``_AgentScopedMiddleware`` 收窄，理由见 `src/server/agents_factory.py:701-717`），
**只搬运与裁决事件，不在模型调用链上**。

**它解决的两个真实问题**（都是实测出来的，不是设想）：

| 现象 | 用户看到什么 | 守卫的动作 |
| --- | --- | --- |
| 模型把「我要先查一下差标…」这类过程叙述当答复发出来 | 一句没有结论的空话 | 剥离草稿段落；剥完全空则吞掉 `ReplyEndEvent` 要求重说 |
| 模型报了一个工具**从没给过**的差标数字（如工具说 600、正文写 500） | 一个会误导报销决策的数 | 拦下、塞入点名该数值的纠正指令、重说 |

**它是怎么做事的**：缓冲每轮文本事件 → 在 `ModelCallEndEvent` 结算 → 通过判据就放行
（原文未变时**复用原事件**，保住 block id）→ 不通过就吞掉 `ReplyEndEvent` 触发重试 →
重试用尽仍无可用内容时走兜底（优先回收最后一版可用草稿，否则固定话术）。

**判据的取舍方向是有意不对称的**：

- **占位符/独白**（空话）——「宁可放过空话，也不改坏真答案」，所以判据表是**已知形状表**
  （`_is_draft` 的强/弱开场词两档），换种说法就漏，这一点写在模块文档的「能力边界」里；
- **编造数值**（误导决策）——「宁可让用户看不到复述，也不让编造的数值上屏」，
  所以例外轮（HITL 确认复述）也走同一条流水线，不整轮放行。

**2026-10-04 对抗审计修掉的六处**（每一处都有现场复现与一条钉住它的用例）：

| 代号 | 缺陷 | 现在的行为 |
| --- | --- | --- |
| F1 | 剥草稿时误伤正文里的方法说明段 | 尾段剥离只信**强证据**（尾段剥离不可回退，所以门槛更高） |
| F2 | 第一轮就调差标工具时，`tool_text` 必然还空 → 闸门整个短路 | 工具文本为空时**再问一句**「本轮调的就是差标工具吗」 |
| F3 | 折全角用整段 `NFKC`，把 ``①600`` 折成 ``1600``（模型没写过的数） | 只折「全角形式」区（1:1 映射，偏移不漂） |
| F4 | 兜底把闸门**刚拦下**的草稿用工具回显「洗白」后复活 | 记录拦下的文本，兜底不再复活（拦过的就是拦过的） |
| P1 | 动态 Prompt 注入的**用户自己的**预算被当成编造（正确答复被拦到只剩道歉） | 新增第四个合法来源：我们自己注入进 prompt 的用户数据数字 |
| P2 | 预算/价格用 ``:g`` 渲染，``1200000`` 变 ``1.2e+06``（模型照抄则是科学计数法，不照抄则被判编造） | 统一走 `render_amount`（十进制逐字还原） |

**数字规则只有一份**（`src/orchestration/amounts.py`，无依赖的叶子模块）：动态 Prompt
（渲染给模型看）、差旅工具（渲染进工具返回）、回复守卫（切词与归一）三处消费同一个实现。
这是 P2 的结构性修复——两处各写一份规则时，分歧的症状是**同一段正确答复时对时错**，
`tests/test_orchestration_amounts.py::test_all_consumers_share_one_implementation`
按对象身份钉住它（谁抄一份实现就立刻红）。

**接地闸门的四个合法来源**（`_ungrounded_limit_claims`，只在本轮调过 ``check_travel_policy``
时才启动）：本轮工具返回里的数、用户**本轮**说过的数、工具数乘小整数算出的合计、
**我们自己注入进 prompt 的用户数据数字**（登记在 `agent.state.middle_context`，
按 `reply_id` 校验新鲜度——``middle_context`` 随会话持久化，旧登记绝不能当豁免）。
四处**全部按完整数字比对**，绝不退回子串包含：历史上正是子串匹配让
「用户说 5000 → 答复写 500」与「工具返回 2000 → 答复写 200」两种编造同时漏网。

⚠️ 被拦下的次数、被剥掉的草稿数、兜底走了哪条路，全部进
`aligo_reply_guard_actions_total`（`src/observability/metrics.py`）——**判断「该不该收紧判据」
靠的是这条曲线，不是读代码**。

**2026-10-04 的第二轮优化：提示词与剥离器一起改，用指标验证**

同一张曲线上有两类动作长期分不开，也就答不了「提示词改得有没有效」。
这一轮把根因（提示词）与兜底（剥离器）同时修，并把指标按**可行动性**拆开：

| 改动 | 位置 | 理由（全部由对抗验证逐条复现后采纳） |
| --- | --- | --- |
| 提示词改说**机制**：调了工具的那一轮，文字整轮不发；「要查就只调工具，一个字都别配」 | `src/agents/prompts.py`（`MAIN_PLAN_PROMPT`） | 原文写的是「你输出的每一段文字都会原样出现在用户屏幕上」——与 `_settle_round` 的真实行为**相反**。模型按旧文写前言，用户看不到、还白等一轮 |
| 「结论先行」限定为**最后那段完整答复** | 同上 | 数据没查回来就先下结论，会踩中接地闸门（一轮重说） |
| 假设写成**内容**而不是过程（「按周三出发，方案如下」✓ /「我先假设一下」✗） | 同上 | 旧示例「先给你看个方案」示范了「先…」句式 |
| 追问上限静态侧与动态侧对齐为**两个** | 同上 + `src/orchestration/prompt.py` | 静态说「一次只问一个」、动态说「最多两项」，`MAX_MISSING_PROMPTS=2` 才是事实 |
| 收集阶段指令改**规则句**（「本轮只做一件事：把还没定下来的要素问出来」） | `src/orchestration/prompt.py`（`_STAGE_DIRECTIVES`） | 旧文是状态描述（「你正在补全出差要素」），模型会当旁白复述出来 |
| 段尾草稿句**救回**（`_strip_trailing_draft_sentences`） | `reply_guard.py` | 「您的订单已确认，出票时间是 10 月 12 日。我应该把行程发给您。」旧实现整段删——**静默丢答案** |
| 救回后 `continue`：紧跟着的纯草稿段仍删 | `reply_guard.py`（`_strip_drafts`） | 写成 `break` 会漏出中间那句带工具名的草稿（对抗验证击穿过） |
| 「系统已经…」「当前处于…」从强档**降到弱档** | `reply_guard.py`（`_MONOLOGUE_OPENERS_WEAK`） | 它们是结论文常见开头。降到弱档后：段首剥离与 `_answer_problem` 照旧、**结尾删除收手**（尾删不可逆）。⚠️ 不能直接删表——「系统已经为您核对完成，请稍候。」会被当答复发出去 |
| 第三人称判据收窄（去掉 `\|已经\|是`） | `reply_guard.py`（`_THIRD_PERSON_PLANNERS`） | 「该用户的申请已经提交」是状态陈述，不是「盘算下一步」；`他既然要去北京…` 仍被抓 |
| 「原文未变」改判 `cleaned == text`（不再用 `removed == 0`） | `reply_guard.py`（`_settle_round`） | 面向未来清洗通道的加固：动过文本却没自增计数时会静默发旧文本 |

**指标按可行动性拆开**（旧口径 = 新口径之和，由
`_classify_suspicious_paragraph` 与 `_is_draft` 的**等价性用例**钉住）：

| 动作 | 怎么读 |
| --- | --- |
| `dropped_tool_round_narration` / `..._other` | 前者 = 模型还在工具轮里写过程叙述（提示词要治的，**该下降**）；后者 = 判据认不出来的形状，**要盯**：工具轮的文字是静默丢弃的，里面可能夹着答案。后者在 `DEBUG` 下会留一份**截断到 200 字符**的样本（`ALIGO__APP__LOG_LEVEL=DEBUG` 可见）—— 这一段文本在本路径外零留痕，没有样本就答不了「被吃掉的到底是不是真答案」 |
| `draft_paragraph_left_internal` / `..._monologue` | 发给用户的正文里的残留：前者是工具名/智能体名泄露（该做名字清洗），后者是行文夹带（该压提示词） |

## 四、存储拓扑

三种存储各司其职。**不要问「为什么不用一种」——它们回答的是三个不同的问题。**

```text
                    ┌─────────────────────────────────────────────┐
                    │              PostgreSQL                     │
                    │  默认 database: aligo                        │
                    │   ├ 默认 schema: 框架的 13 张表               │
                    │   │   (sessions / messages / sops / …)      │
                    │   └ schema "business": 本项目业务表           │
                    │       (画像 / 订单 / 行程 / 申请单 / 审批流)    │
                    └─────────────────────────────────────────────┘
                    ┌─────────────────────────────────────────────┐
                    │                Redis                        │
                    │  RedisMessageBus:                           │
                    │   · SSE 事件总线（回放日志 + pub/sub）        │
                    │   · 取消广播                                 │
                    │   · 幂等锁                                   │
                    └─────────────────────────────────────────────┘
                    ┌─────────────────────────────────────────────┐
                    │                Milvus                       │
                    │  {milvus.collection}          政策知识库      │
                    │  {milvus.collection}_memory   画像语义召回     │
                    └─────────────────────────────────────────────┘
```

### 4.1 PostgreSQL：框架表与业务表**分 schema**

框架的 `AsyncSQLAlchemyStorage` 管它自己的 13 张表（`sessions` / `messages` / `sops` / `sop_runs` /
`knowledge_documents` 等），它们挂在一个私有全局 metadata（`_Base`）上，**没有任何参数能换掉它**。

本项目的业务域要建的是另一批表（用户画像、订单、行程、申请单、审批流）。
它们的名字（`orders` / `trips` / `users` …）与框架那 13 张一样通用，而且都要「按 metadata 建表」。
**一旦两边共用 metadata，框架升级时新增的表会与我们的表混在一起，回滚应用版本却回滚不了 schema。**

因此：**业务表单独一套 engine + 单独一个 `business` schema + 单独一套 metadata**。
`schema` 是 `src/storage/engine.py` 的 `BUSINESS_SCHEMA`；`business_schema_for` 只在 PostgreSQL 系返回它
（sqlite 上没有 schema 概念，返回 `None`——这保证了 `make test` 能在 sqlite 内存库上跑）。

> ⚠️ **框架表与 Langfuse 共用同一个 PostgreSQL 实例、但不同 database**（省内存）。
> 这是 compose 侧的安排，见 `docs/06-部署与运维.md`。

### 4.2 Redis：消息总线是**必须**的

`RedisMessageBus` 承担 SSE 事件总线（`log_append` 写回放日志 + `publish` 广播）、取消广播、幂等锁。
`InMemoryMessageBus` 在多副本下会让 SSE 事件收不到——框架自己的注释就是这么写的。
测试里用内存总线，只是因为测试是单进程且不测跨副本。

⚠️ 回放与实时订阅**可能重叠**（一条事件先 `log_append` 再 `publish`，若它恰好落在
「订阅已挂、回放未读」之间，两处都能拿到），所以消费方按 `_entry_id` 去重——
那个 id 由总线分配，回放与实时是**同一个值**。

### 4.3 Milvus：单集合政策库 + **派生**的画像集合

- **政策知识库**：`milvus.collection`（默认 `aligo_travel_policy_dev`）。由
  `src/knowledge/manager.py` 的 `SingleCollectionKbManager` 管理——**单集合**策略，
  隔离键 `KB_ID_KEY` / `USER_ID_KEY` 写进 chunk 的 `metadata`，由 Milvus 按 JSON 字段路径过滤（`metadata["aligo_kb_id"] == …`）区分租户 / 知识库。
- **画像语义召回**：`{milvus.collection}_memory`，由 `src/memory/semantic.py` 的
  `memory_collection(settings)` **派生**出来。刻意不另起一个配置项：集合名的对应关系是**结构性**的，
  配成两个独立的键，迟早会配成不一致的一对。

⚠️ **Milvus 首次启动不会创建业务集合**——两个集合都由 `scripts/milvus_init.py` 显式建
（同一条命令，建完逐个回读核验形态）。另有两处**惰性自愈**兜底：框架
`KnowledgeBase.search()` 会为政策库补建（`rag/_knowledge.py` 的 `ensure_collection`），
`SemanticMemory.remember` 会在第一次写入前为画像集合补建——但两条自愈都**不做形态核验**，
所以 `milvus_init` 仍是发布前的必做项。`docs/06-部署与运维.md` 的迁移与初始化一节详述。

### 4.4 长期记忆的读写路径

长期记忆 = **结构化画像**（`src/memory/profile.py`，存 Postgres，`SqlProfileRepository`）
与 **语义召回**（`src/memory/semantic.py`，存 Milvus）两部分，二者在 `src/memory/service.py`
的 `TravelerMemory` 里合并。

**读写路径的容错是不对称的**，这是一条刻意的设计：

- **读路径永不抛异常**——记不住用户的偏好顶多是回答不够个性化，不该让整轮对话失败；
- **写路径抛异常**——写不进去是**真故障**，必须让人知道，否则画像会静默地永远不更新。

⚠️ **这条不对称描述的是「对话链路」那一个出口**。同一个 `TravelerMemory` 有**第二个出口**：
显式接口 `/api/v1/memory/**`（`src/server/routers/_memory.py`），而那里的错误语义是**反的**——
调用方正在等一个答案，把故障降级成「空列表 / 没有画像」等于把一次故障伪装成一个**错误的事实**。
于是：能力缺失 503（并说清缺的是开关还是向量模型）、召回失败 `200 + error` 非空、
写失败 503 且明说「没有生效」（原因经 `safe_error` 脱敏）。
两个出口的完整契约见 `docs/01-功能接口.md` 2.5。

⚠️ 这个接口面是 2026-10-03 **补上**的：在此之前 `remember` / `update_profile` / `put_profile`
在 `src/` 里一个调用者都没有——写入面在产品里**不可达**，而 `docs/03` 早就写着
「『记住偏好』这类写入会以异常形式出现在用户面前」，那是一句当时无从兑现的话。

⚠️ **写入的「可见性」不跟着写路径的返回值走**。Milvus 建集合时的一致性级别默认是
`Bounded`，而框架的建集合接口没有这个旋钮——于是「刚 `POST` 进去的一条」对紧接着的
召回**可能不可见**。2026-10-03 在容器里实测：插入后 `0.39s / 0.40s / 1.37s` 才可见，
删除后 `0.56s / 0.57s / 0.58s` 才不可见——`DELETE` 返回 200「已忘记」之后紧接着的召回
**仍可能命中那条被删掉的笔记**。修法是把它请求成 `Strong`
（`src/knowledge/store.py:133`，建集合之后调用一次；记忆那个集合由 `remember` 惰性创建，
所以写路径上也有一次「本进程只做一次」的请求），复测 3 轮全部即时。
⚠️ 这件事**不能**用返回值或紧随其后的回读来证明：`alter_collection_properties` 对不认识的
属性名不报错，而回读会先返回旧值——所以真实级别只在 `/readyz` 与 `milvus_init` 的回读里看。

## 五、凭据引导：让「配好密钥」真的等于「能用上模型」

### 5.1 缺口：探针全绿，但「发送」永远是灰的

框架的对话链路**不靠**「全局默认模型」工作，它要两样东西同时在位：

```text
(a) 一条调用者可解析的 credential 记录（credentials 表）；
(b) 会话的 chat_model_config 指向它（type + credential_id + model + parameters）。
```

缺 (b)：`app/_service/_chat.py:1097-1105` 直接 404（`No model configuration found for agent ...`）；
缺 (a)：另一条 404（`Credential '...' not found.`），抛自
`ResourceAccessService.resolve_credential`（`app/_service/_access.py:401`，方法体在 `:376-401`：
先按调用者自己查，再遍历共享引用），调用点是 `app/_service/_model.py:42`。
⚠️ **不是** `CredentialFactory.from_dict` 报的：它（`credential/_factory.py:78-87`）只是
`validate_python(data)` 的纯反序列化，不查任何记录 —— 记录缺失时它**根本不会被调用**
（`app/_service/_model.py:47` 那行拿到的已经是取回的 `data`）。
⚠️ 这里把路径写全而不是简写成 `_model.py`：仓库与 third_party 里叫 `_model.py`
的文件不止一个（`app/_router/_model.py`、`app/_router/_schema/_model.py`、
`exception/_model.py`…），简写会让校验（与读者）指到一条**别的**文件上 ——
`scripts/check_doc_refs.py` 正是按「路径段后缀」解析的，少一段就是另一个候选集。
两条都不会让健康检查变红——`/healthz`
只看进程活没活，`/readyz` 只看 Postgres / Redis 与 **boot**（启动完成标记
`app.state.boot_completed`）这三项（`src/server/probes.py:100-102` 的 `REQUIRED_CHECKS`）。
⚠️「凭据有没有播种成功」**不在任何一项里**，这正是下面那个最坏形态的成因。于是最坏的部署形态是：
**探针全绿、SPA 正常渲染、「发送」按钮永远灰着。**

前端那一半同样是空转：可用模型是 `GET /credential/` × `GET /model/?provider=` 拼出来的
（`web/frontend/src/hooks/useAvailableModels.ts:22-42`），零凭据 ⇒ 分组为空 ⇒
`getFirstAvailableModel()` 返回 `null` ⇒ `selectedModel === null` ⇒ 发送按钮 `disabled`
（`web/frontend/src/pages/chat/ChatViewport.tsx:852`）。⚠️ 两个接口都要有内容才算通：
凭据在、但 `GET /model/` 的卡片列表为空时，分组里的 `models` 仍是空数组，按钮照样灰——
这正是 `MockChatModel.list_models`（`src/llm/mock.py:452-469`）必须覆写基类、
返回一张卡片的原因。

### 5.2 两条互斥且互补的路径

判据只有一个来源（`src/llm/factory.py:103` 的 `has_api_key`、`src/llm/factory.py:127`
的 `should_use_mock`），两条路径不可能同时生效：

| | 零密钥降级 | 系统凭据共享 |
| --- | --- | --- |
| 判据 | `should_use_mock(settings) == True` | `not should_use_mock(...) and has_api_key(...)`（`src/llm/system_credential.py:107-125`） |
| 谁播种、播几份 | `MockCredentialSeedMiddleware` 按需、**每个已鉴权用户一条**（`src/server/middleware/mock_credential.py:124-141`） | lifespan 里写**一条**属主为 `aligo-system` 的凭据（`src/server/app.py:408`） |
| 凭据里有什么 | 无秘密（MockLLM），复制一万份也不损失什么 | 运营者的真 key，全公司只有这一份 |
| 用户读到的 | 自己的 Mock 凭据（明文也无所谓） | 打码的 `{type, name}`——能用，读不到 |

**零密钥 Mock 播种**：身份来自请求（`X-User-ID` 或 JWT 的 `sub`），没有用户表，
启动那一刻服务并不知道将来会有谁用——所以播种只能挂在「第一次见到某个用户」这个时机上，
这就是它是中间件（而不是启动钩子）的原因。凭据 id 由 user_id **确定性派生**
（`src/llm/mock.py:110`），重复调用只会命中框架的就地更新分支，不会越长越多。

**有密钥的系统凭据共享**：把运营者的 key 写成**一条**属主为 `aligo-system`
（`src/llm/identity.py:42`）、id 固定为 `aligo-system-model`
（`src/llm/system_credential.py:100`）的记录，再实现框架的 `ResourceAccessPolicyBase`
（`src/llm/system_credential.py:264-324`）把它以 **READ** 权限共享给全体已鉴权用户。
框架随后把「能用但读不到」变成现实：列表里 `data` 打码成 `{type, name}`
（`app/_service/_access.py:562-567`），运行期 `resolve_credential` 返回原始记录供构造模型
（`app/_service/_access.py:376-401`）。

⚠️ **为什么不把真 key 复制进每个用户的记录**：owner 读自己的凭据是**明文**。
一次共享会变成全员泄密——任何能通过鉴权的用户都能在「凭据」页把自己那份 key 抄走。
共享这条路安全的前提只有一个：**属主不是用户自己**——这正是 3.6 必须让
`aligo-system` 不可声明的原因。

⚠️ **为什么权限是 READ 而不是 EDIT**：EDIT 意味着任何用户都能把全公司的密钥删掉
或改成自己的——那不是「共享」，是「开放的写权限」。READ 之下，共享者对这条记录的
`resolve_for_edit` 直接 403（`app/_service/_access.py:520-527`）。策略也**只共享凭据**：
智能体与知识库不共享（`src/llm/system_credential.py:53-58`）——「顺手多共享一点」
是多租户系统里最容易失控的一类改动。

### 5.3 `GET /api/v1/default-model`：四种 mode，顺序是刻意的

`src/llm/degradation.py:199-314` 是全部判据，HTTP 层只是它的外壳
（`src/server/routers/_default_model.py:63-140`）。返回体 `{mode, chat_model_config, hint}`，
四种模式**都不含任何密钥**：

| 顺序 | mode | 判据 | `chat_model_config` |
| --- | --- | --- | --- |
| 1 | `mock` | 降级开关开着：替用户播种，并给一份可直接用的 Mock 配置 | 有 |
| 2 | `configured` | 用户**自己**有凭据：不替他选模型，只让他去选择器挑 | 无 |
| 3 | `shared` | 用户自己没有、但系统凭据**对他可用**（走 `policy.list_accessible` 判定，不是「查一下记录在不在」） | 有 |
| 4 | `missing` | 都没有：给一句可执行的 hint | 无 |

顺序里有两条不能反：

- **`mock` 最先判**：开关开着本身就是运营者的明示选择；先判它，才能保住「零密钥也能对话」
  这个承诺不被用户列表里的其他记录干扰。
- **`configured` 必须排在 `shared` 之前**：反过来的话，一个自带公司密钥的用户会被
  **悄悄切到**系统凭据上，账单与配额都算错地方（`tests/test_default_model.py:715` 钉住这一条）。

四种模式的解释文案是常量 `HINT_MOCK` / `HINT_CONFIGURED` / `HINT_SHARED` / `HINT_MISSING`
（`src/llm/degradation.py:121-138`）——smoke 脚本与文档引用同一句话，手抄一份必然漂移。
⚠️ **四个业务分支一律返回 200**（`src/server/routers/_default_model.py:84-88`）：用非 200 表达
「没有模型」会让客户端把正常的业务状态当成传输层故障，重试与告警对着一个
「本来就该有人去配凭据」的状态狂响。唯一的 **503** 不是业务分支，而是
`app.state` 取不到 `settings`/`storage`（应用未按预期装配，`src/server/routers/_default_model.py:104-116`）——
那才是真的「这个端点现在不可用」。`shared` 分支的 import 是**函数内局部**的
（`src/llm/degradation.py:285-290`）：零密钥路径不该为了共享分支多背一个
`agentscope.app.access` 的导入面（同 3.6 的理由）。

### 5.4 播种的并发语义与 `hide_parameters`

**幂等写入**：两条路径共用 `src/llm/preset_credential.py:71-102`。框架对预设 id 的写入
是「先查后写」：id 不属于调用者就直接 INSERT，撞全局主键即抛 `IntegrityError`
（框架有意如此，防止跨租户覆盖，`app/storage/_sql/_storage.py:739-779`）。但
「两个执行者同时给同一个用户首次播种」是**并发、不是故障**，所以只把
`type(exc).__name__ == "IntegrityError"` 当冲突并重试一次；其余异常原样抛出；
重试后仍冲突也照样冒泡——不把真故障掩盖成「反正重试过了」。

**`hide_parameters` 必须打开**（`src/storage/engine.py:100-126` 的 `storage_engine_kwargs`）。
SQLAlchemy 默认把**绑定参数**渲染进异常文本，而 `credentials.data` 里就是运营者的真 key；
播种那条 INSERT 一旦失败，`logger.exception` 会把 key 原样落进容器日志。对照：

```text
不开（SQLAlchemy 默认）：
  [SQL: INSERT INTO credentials (id, user_id, data) VALUES ($1, $2, $3)]
  [parameters: ('aligo-system-model', 'aligo-system', '{"api_key": "sk-not-a-real-key", ...}')]

开了（本项目，src/storage/engine.py:125）：
  [SQL: INSERT INTO credentials (id, user_id, data) VALUES ($1, $2, $3)]
  [SQL parameters hidden due to hide_parameters=True]
```

⚠️ 它是 Engine 级、**跨方言**的参数，所以写在方言分支**之前**：sqlite 分支
（`src/storage/engine.py:128`）与 postgres 分支（`src/storage/engine.py:139`）都会带上它
（用例在 `tests/test_storage_engine.py:304`，对 sqlite 与 postgres 两类连接串都断言
`is True`，断言落在 `:312`）。它顺带管住 `echo=true`：
echo 打印的是**渲染后**的语句、同样带参数——只开 echo 不设它，「开 echo 调试一下」
就等于把 key 打到 stdout。

### 5.5 一条共享凭据，两处要喂到

共享凭据不只喂对话链路（`chat_model_config`），还要喂**知识库的 embedding 凭据**。
框架在这里留了一道缝：

- `GET /knowledge_bases/embedding_models` 明确把共享凭据列进可选列表
  （`app/_router/_knowledge_base.py:90-105`，docstring 原文 own + shared），
  用户据此建的 KB，记录里钉的是一个**别人的** credential_id；
- 而框架的 `get_knowledge` 只按**属主**查 embedding 凭据
  （`app/rag/knowledge_base_manager/_collection_per_kb.py:187-195`，注释写明它假设
  「凭据与 KB 同属一个属主」——这个前提在本项目不再成立）。

于是检索时解析不出凭据 ⇒ `KnowledgeBaseNotFoundError` ⇒ 对话链路把它吞成一行
「Skipping knowledge base」（`app/_service/_chat.py:1048-1059`）⇒ **知识库静默失效**：
上传、索引、列表全正常，只有回答里永远没有出处。

修复在 `src/knowledge/manager.py:308-392`：先按属主查，查不到再问
`access_policy_provider()` 给出的策略，用
`list_accessible(owner_id, ResourceKind.CREDENTIAL, storage)` 找到匹配的 ref 后，
再用 **`ref.owner_id`** 去取记录。这里没有放宽权限：查的始终是「该 KB 属主可访问的凭据」，
策略不给就照样解析不出来——**能不能用只有一个权威**，不另立一套。装配那一半在
`src/server/app.py:749-764`：策略是框架在 `create_app` 内部才写进 `app.state` 的，
所以传的不是策略对象而是一个延迟取值的函数；`app_box["app"] = app` 必须在
`create_app` **之后**（`src/server/app.py:862-868`）——写在之前会永远取到 `None`，
症状正是上面那条静默失效（`src/server/constants.py:81-100` 专门说明了这个
「框架属性名」为什么值得抄成常量）。

## 六、可观测：指标与 trace 是两件事

| | 指标（Prometheus） | trace（OTel → Langfuse） |
| --- | --- | --- |
| 回答 | 「整体趋势如何」 | 「这一次调用里发生了什么」 |
| 端点 | `/metrics`（条件式） | 无端点，导出到 Langfuse |
| 装配 | `observability.metrics_enabled=true` | `trace_exporter=="otlp"` **且** `otlp_endpoint` 非空 |

指标注册在**自己的** `CollectorRegistry` 上（`src/observability/metrics.py` 的 `REGISTRY`），
命名规范 `aligo_<subsystem>_<measure>_<unit>`。

⚠️ **trace 的装配条件是显式必需的**：未配 `TracerProvider` 时框架的 `TracingMiddleware`
会**静默短路**，表现为「trace 功能看起来开了，但 Langfuse 里什么都没有」，极易被误判成网络问题。
