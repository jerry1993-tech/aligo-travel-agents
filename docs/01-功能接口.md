## 一、接口的三个命名空间

一个 `uvicorn src.server.app:app` 起来的进程同时提供**三组路径**，它们由不同的人维护，
契约也不同。把这一点先讲清楚，后面才不会在「这个端点归谁管」上浪费时间。

| 命名空间 | 谁提供 | 前缀 | 鉴权 | 例子 |
| --- | --- | --- | --- | --- |
| **框架路由** | pip 安装的 AgentScope（`create_app` 的返回值） | 无（就在根上） | 中间件补在前面 | `/chat/`、`/sessions/**`、`/agent` |
| **业务命名空间** | 本项目（`src/server/routers/`） | `/api/v1` | 中间件 | `/api/v1/me`、`/api/v1/sessions/{id}/chains` |
| **根探针** | 本项目（`src/server/probes.py`） | 无 | 公开（白名单） | `/healthz`、`/readyz`、`/metrics` |

### 为什么业务接口是 `/api/v1/**`，而不是给框架路由套前缀

框架路由在**根路径**上是既定契约：官方前端用 `new URL(path, baseUrl)` 且调用处传的是
绝对路径，`scripts/smoke.py` 也按根路径调 `/chat/`。给框架的 `include_router` 加一个
`prefix="/api/v1"` 会让 `/chat/` **直接消失**——不是报错，是静默地少一条路由。

所以 `/api/v1/**` 是**另一个平行的命名空间**，不是框架路由的外壳。两者互不遮蔽，
`tests/test_api_v1.py::test_business_routes_do_not_shadow_framework_routes` 钉住了这一点。

## 二、业务接口明细（`/api/v1/**`）

路由树只在 `src/server/routers/__init__.py` 里挂一次前缀，子路由自己不带前缀。

### 2.1 `GET /api/v1/health` —— 业务命名空间的存活探针

| 项 | 值 |
| --- | --- |
| 鉴权 | 公开（在白名单里，中间件不做鉴权） |
| 请求体 | 无 |
| 响应 | `200`，固定形状 |
| 实现 | `src/server/routers/_health.py` |

```json
{ "status": "ok", "scope": "api/v1", "message": "业务接口可用。依赖状态请查看 /readyz。" }
```

**它和 `/healthz` 是两件事**（读者不同）：

- `/healthz` 给**编排系统**看（compose healthcheck / k8s livenessProbe），极浅、零 I/O；
- `/api/v1/health` 给**调用方**看，它在业务命名空间里，于是它顺带证明了三件事：
  「鉴权中间件放行了公开路径」「限流没有误伤探针」「`/api/v1` 路由树装配正确」。

如果只有 `/healthz`，当 `/api/v1` 整棵树因为某次 `include_router` 写错而没挂上时，
所有探针仍然是绿的。这里**刻意不做依赖检查**——要查依赖请打 `/readyz`。

### 2.2 `GET /api/v1/me` —— 把「你是谁」显式回答出来

| 项 | 值 |
| --- | --- |
| 鉴权 | 需要（中间件解析出身份后才谈得上「你是谁」） |
| 请求体 | 无 |
| 响应 | `200` |
| 错误 | `401` 凭据缺失/无效（**由中间件**返回）；`422` 身份依赖没取到可用标识 |
| 实现 | `src/server/routers/_identity.py` |

```json
{ "user_id": "alice", "auth_mode": "header", "trace_id": "…", "consistent": true }
```

字段含义：

| 字段 | 说明 |
| --- | --- |
| `user_id` | 本次请求**最终被认定**的身份。它经框架的 `get_current_user_id` 解析，而不是我们自己读 scope |
| `auth_mode` | 身份是怎么来的：`jwt` / `header` / `public` / `anonymous`，中间件没留标记时为 `unknown`（正常装配下不出现） |
| `trace_id` | 本次请求的 trace id，可拿去日志里串起整条链路 |
| `consistent` | 比对「框架依赖解析出的 user_id」与「中间件写进 scope 的 user_id」。正常装配恒为 `true`；为 `false` 说明有中间层改了请求头（新加的中间件 / 网关注入），这类问题若不显式暴露，会表现为「有些接口按 A 过滤、另一些按 B」 |

**它存在的唯一理由**是把鉴权链路变成可观测的：`user_id` 对得上说明鉴权通，对不上说明问题在中间件——
否则你只能靠间接证据，且分不清是「鉴权没生效」还是「隔离没生效」。

⚠️ 这个端点走的是**框架的**身份依赖 `get_current_user_id`（而不是自己读 scope）。
因为它才是**有意义的证明**：证明我们中间件产出的东西与框架那 85 个既有 `Depends` 点期望的输入完全兼容。

### 2.3 `GET /api/v1/sessions/{session_id}/chains` —— 思考链 SSE

| 项 | 值 |
| --- | --- |
| 鉴权 | 需要（属主校验） |
| 协议 | `text/event-stream`（SSE，长连接） |
| 实现 | `src/server/routers/_chains.py` |
| 404 | 会话不存在**或不属于当前身份** |
| 响应头 | `Cache-Control: no-cache`、`X-Accel-Buffering: no` |

**查询参数**：

| 参数 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- |
| `agent_id` | **是** | — | 会话所属的智能体 id，属主校验需要它（`get_session` 的三元组键） |
| `expose_reasoning` | 否 | `false` | 是否把模型推理文本一并推送 |

**帧格式**：每帧是一个 JSON 对象，含 `tasks` 与 `reasoning` 两个字段（**全量快照**）：

```text
data: {"tasks": [{"name": "...", "state": "doing", ...}], "reasoning": ""}

```

- `tasks` 是这场会话「现在在干什么」的任务清单，`state` 取值见 `TaskState`
  （`src/domain/enums.py` 的 `TaskState`）；清单有上限（`src/chains/collector.py:62` 的 `DEFAULT_MAX_TASKS`）。
- `reasoning` **默认恒为空串**——关掉推理时 `EventChainAdapter` 根本不累积它，
  但字段**始终存在**，前端不必为「开没开推理」写两套解析。
- 空闲时每约 30 秒发一帧心跳 `:\n\n`（SSE 规范里以 `:` 开头的行会被客户端忽略）。
  心跳的作用有两个：穿过会掐空闲连接的反向代理；让前端能区分「还活着但没事发生」与「连接已经死了」。

**为什么发全量快照而不是增量**：增量要求前端自己维护合并逻辑，丢一个包或重连一次就永久错位，
而错位的表现是「界面上少了一个任务」，没人会往「增量丢了」上想。全量快照是**自描述**的：
前端每次整体替换即可，重连天然自愈。代价只是一帧多几十字节，而清单有上限，不会无界膨胀。
「变了才发」用「上一次已发送的序列化串」逐字节比对来实现。

**为什么 404 而不是 403**：403 会告诉调用方「这个会话存在，只是不属于你」——
那就把「谁拥有什么」泄露出去了。404 让「不存在」与「不是你的」**不可区分**。
框架的 `/messages`、`/stream`、`/status` 全是这个做法。

**回放与订阅的顺序**：本端点是**先订阅、后回放**。框架自带的 `/stream` 是「先回放、后订阅」，
那样在「回放已读完、订阅还没挂上」之间发布的事件会**同时错过两处**，表现为「偶尔少几个事件」，
且只在负载高时出现。反过来的代价是回放日志与订阅队列会有**重叠**，
所以按 `_entry_id` 去重（该 id 由总线分配，回放与实时是同一个值）。

⚠️ **每个连接各建一份 collector + adapter，绝不共享**：两者都是「一轮回复作用域」、
非线程安全的，跨连接复用会把 A 会话的分片拼进 B 会话的结果里（`tool_call_id` 由模型生成，
两条会话里未必不同）。所以它们在 `_sse_generator` 内就地构造，随连接生、随连接灭。

### 2.4 `GET /api/v1/default-model` —— 「我现在能用什么模型？」

| 项 | 值 |
| --- | --- |
| 鉴权 | 需要（回答的是**当前身份**此刻的处境） |
| 请求体 | 无 |
| 响应 | `200`（四种 `mode` 一律 `200`）；应用装配不完整时 `503` |
| 错误 | `401` 凭据缺失/无效（**由鉴权中间件**返回）；装配缺失时 `503` |
| 实现 | `src/server/routers/_default_model.py:78`；判定逻辑 `src/llm/degradation.py::resolve_default_model`（`src/llm/degradation.py:199`） |

```json
{
  "mode": "mock",
  "chat_model_config": { "type": "…", "credential_id": "…", "model": "…", "parameters": {} },
  "hint": "当前处于零密钥降级模式：已为本用户准备了一条 MockLLM 凭据（不产生任何费用、输出确定）。配置真实密钥后本模式自动关闭。",
  "trace_id": "…"
}
```

**它回答的是对话链路里那个「能不能发出去」的问题**：框架的对话链路**不是**靠一个全局默认模型工作的，它要一条**调用者可解析**的 credential 记录与会话上指向它的 `chat_model_config` 同时在位；缺任何一个，探针全绿、SPA 正常渲染，而「发送」按钮永远灰着。本端点把「此刻到底能用什么」显式说出来——`mode` 是四选一的**枚举**（不是布尔值），`hint` 是一句可以直接交给用户的人话；`trace_id` 的用途与 2.2 相同，排障时用来把响应与日志串起来。

⚠️ **它是 smoke 的对话检查问的第一个问题，也是浏览器选择器的兜底答案**：`scripts/smoke.py:591-593` 的端到端对话检查第一步就是问它要一份配置（拿到后写进会话，再真的发一句话）。浏览器端「可用模型」是 `GET /credential/` × `GET /model/?provider=` 两个**列表**接口拼出来的（`web/frontend/src/pages/chat/ChatViewport.tsx:536` 的 `getFirstAvailableModel()`；选不到时 `selectedModel === null` ⇒ 发送按钮 `disabled`，同文件 `:852`）。列表为空时，「拼」这个动作**无法区分**两种处置方式完全相反的处境：

- (a) 本来就没有模型可用——需要人去配一条凭据；
- (b) 有降级模型可用，只是「列表为空」这件事本身是缺陷。

两者在 UI 上长得一模一样（一个灰掉的发送按钮）。本端点就是把 (a)/(b) 显式说出来；浏览器端选择器在可用模型为空时也应回落到它（`src/server/routers/_default_model.py` 的模块文档字符串）。⚠️ 它**不是** `GET /model/` 的替代：那两个列表接口回答「你**看得见**哪些凭据/模型」（选择器的数据源），本端点回答「你**此刻默认该用**哪一份」——都叫「模型」，一个是目录，一个是决策。

**四种 `mode`**（判定顺序是刻意的，理由见 `src/llm/degradation.py:212-222` 的 docstring）：

| mode | 何时返回 | `chat_model_config` | 对应文案 |
| --- | --- | --- | --- |
| `mock` | 零密钥降级开关开着（`should_use_mock`） | 一份指向**该用户自己**的 Mock 凭据的配置 | `HINT_MOCK` |
| `configured` | 开关关着，且该用户**自己有**凭据 | `null` | `HINT_CONFIGURED` |
| `shared` | 用户自己没有、但运营者的系统凭据（id `aligo-system-model`）**对他可用** | 一份指向那条系统凭据的配置 | `HINT_SHARED` |
| `missing` | 以上都不是 | `null` | `HINT_MISSING` |

**为什么是这个顺序**：

1. **先判 `mock`**：降级开关开着本身就是运营者的明示选择，此时「服务至少能对话」这个承诺不取决于用户名下有没有别的记录。该分支顺带确保那条 Mock 凭据存在（`ensure_mock_credential` 幂等；零密钥部署下中间件其实已为每个已鉴权用户播过，这里只是兜底）。
2. ⚠️ **`configured` 必须排在 `shared` 之前**：用户自己配了凭据时，系统凭据是**备选**而不是**默认**。反过来的话，一个自带公司密钥的用户会被悄悄切到系统凭据上——账单与配额都算错了地方，而且**没有任何界面会提示这件事发生过**。
3. **`shared` 用策略判定**：`policy.list_accessible(user_id, ResourceKind.CREDENTIAL, storage)`（`src/llm/system_credential.py:211`），而不是「查一下那条记录在不在」——「在不在」与「能不能用」是两回事；直接查库会绕过策略，在「启动时那条凭据没播种成功」时仍告诉用户可以用，而真正的表现是发起对话后 404。
4. **最后是 `missing`**：给一句可执行的 hint（去「凭据」页加一条），而不是一个非 200 的状态码。

⚠️ **四种模式都是 `200`**：调用方真正需要的信息是 `mode` 与 `hint`，不是一个 HTTP 状态码。用 `404/503` 表达「没有模型」会让客户端把**正常的业务状态**当成传输层故障——重试、告警、熔断会对着一件「本来就该有人去配凭据」的事狂响。唯一的 `503` 是**装配不完整**（`app.state` 上取不到 `settings`/`storage`，例如有人直接构造了裸 FastAPI），hint 里明说是启动方式的问题（`src/server/routers/_default_model.py:104-116`）。

**四种文案**（原文在 `src/llm/degradation.py:121-138` 的 `HINT_*` 常量；放常量是因为 smoke 脚本与文档要引用同一句话，手抄必然漂移）：

| 常量 | 原文 | 它指向的动作 |
| --- | --- | --- |
| `HINT_MOCK` | 当前处于零密钥降级模式：已为本用户准备了一条 MockLLM 凭据（不产生任何费用、输出确定）。配置真实密钥后本模式自动关闭。 | 什么都不用做；想关掉降级就去配真实密钥 |
| `HINT_CONFIGURED` | 检测到本用户已配置模型凭据，请在模型选择器中选择要使用的模型（零密钥降级不会覆盖你自己的选择）。 | 去选择器里挑一个 |
| `HINT_SHARED` | 本用户没有自己的模型凭据，但管理员已配置系统默认模型且对全员开放（只读共享：你可以使用它，但不能查看或修改其中的密钥）。下面的配置可直接使用，也可以在选择器里换成其它模型。 | 可以直接用返回的配置，也可以去选择器换 |
| `HINT_MISSING` | 未检测到可用的模型凭据，且零密钥降级已关闭（ALIGO__LLM__USE_MOCK_WHEN_NO_KEY=false，或已配置真实密钥）。请先在「凭据」页添加一条模型凭据。 | 去「凭据」页加一条凭据 |

⚠️ **`chat_model_config` 只在 `mock` 与 `shared` 两种模式下非空**：这两种的共同点是「默认选谁由运营者决定」（降级开关、系统凭据都是运营者配的）；`configured` 是「选谁由用户决定」，服务端**不替他选**，因此给 `null` 并请他去选择器。`missing` 则没有东西可给。

⚠️ **四种模式的响应都绝不含任何密钥**，这是有测试守着的：`tests/test_default_model.py:293` 断言响应文本里不出现 `api_key` / `sk-` / `password` / `secret` / `"Bearer "`；`tests/test_default_model.py:273` 断言那份配置的字段集合恰为 `{type, credential_id, model, parameters}`——用例注释写明「多出来的字段很可能是密钥——它会进入日志与浏览器缓存」。本端点与 `resolve_default_model` 只读凭据记录的 **id**，任何一行都不读凭据的 `data`；⚠️ 一旦将来有人「顺手」把 `data` 也带上（比如方便前端一键填充），明文密钥就会进入 HTTP 响应、访问日志、浏览器缓存与中间代理。要填凭据请走框架自己的 `POST /credential/`。

### 2.5 `/api/v1/memory/**` —— 长期记忆的显式读写面

| 端点 | 作用 | 请求体 |
| --- | --- | --- |
| `GET /api/v1/memory/profile` | 读当前身份的结构化画像 | 无 |
| `PUT /api/v1/memory/profile` | **部分**更新画像（`null` = 不改；清空见下方四条） | `ProfilePatchIn` |
| `POST /api/v1/memory/notes` | 记住一句话（幂等） | `{"text", "kind"}` |
| `GET /api/v1/memory/notes?query=…&top_k=…` | 按语义相似度召回 | 无（`query` 必填） |
| `DELETE /api/v1/memory/notes` | 忘掉一条（请求体给原文）或清空全部（`?all=true`） | `{"text"}` 或 `?all=true` |

| 项 | 值 |
| --- | --- |
| 鉴权 | 全部**需要**；身份只来自 `Depends(get_current_user_id)`，任何端点都不接受指定 `user_id` 的参数 |
| 响应 | 一律带 `trace_id` |
| 实现 | 五个端点在 `src/server/routers/_memory.py`：读画像 `src/server/routers/_memory.py:376`、改画像 `src/server/routers/_memory.py:436`、记住 `src/server/routers/_memory.py:529`、召回 `src/server/routers/_memory.py:583`、忘记 `src/server/routers/_memory.py:667`；门面 `src/memory/service.py::TravelerMemory`（`forget` `src/memory/service.py:247`、`forget_all` `src/memory/service.py:274`） |

**清空一个字段：给空值，不是给 `null`**（`null` 永远只表示「不改这个字段」）。这条约定在**每一个位置**都成立——包括字典的**值**：

| 想做的事 | 怎么写 |
| --- | --- |
| 清空航司 / 酒店品牌 / 饮食偏好列表 | `"preferred_airlines": []` |
| 清空座位偏好、成本中心、审批人等字符串 | `"seat_preference": ""` |
| 清空舱位偏好 | `"preferred_cabin": ""` |
| 删掉**某一个**常旅客号 | `"frequent_flyer_numbers": {"CA": ""}` |

⚠️ 后两行是 2026-10-03 对抗性审核补上的：当时文档与接口文案都写着「清空给空值」，但 `preferred_cabin` 给了 `""` 会**报 400**（`_validate_cabin` 把空串当非法值），而 `frequent_flyer_numbers` 只合并不删除、`{}` 与「不传」都是「不动」。于是那句文案在其中两个字段上**是假的**，而这两个字段也成了**永远清不掉的死角**——用户换掉航司之后，旧卡号会一直留在画像里、被注入 Prompt、被下单工具拿走。修法不是把文案写得更啰嗦，而是**把约定补成真的**：现在空值在哪儿都是「清空」，四行都有用例守着（`tests/test_api_memory.py::test_clearing_a_field_takes_an_empty_value_not_null` 与 `::test_empty_values_also_clear_cabin_and_a_flyer_number`）。

**为什么这个接口面是「补上的」，而不是「新加的」**：在它出现之前，`remember` / `update_profile` / `put_profile` 在 `src/` 里**一个调用者都没有**（7 个业务工具与全部业务路由里都没有记忆写入），而与此同时三处代码都已经把它当成存在的东西在描述——`src/server/constants.py` 的 `MEMORY_ATTR` 写着「读取方：`/api/v1/memory/**` 的画像接口」、`TravelerMemory.get_profile` 的 docstring 写着「它是给 `/api/v1/memory/profile` 这类**显式**接口用的」、`docs/03` 写着建表失败时「『记住偏好』这类写入会失败，且会以异常形式**出现在用户面前**」。前两条是「文档指向一个不存在的接口」，第三条描述了一个正确但**无从兑现**的故障语义（写入口根本不存在）。本接口把这三处一起变成真的。

```jsonc
// GET /api/v1/memory/profile —— 没有任何记录时 profile 为 null（200，不是 404）
{ "profile": { "user_id": "alice", "seat_preference": "靠窗", "frequent_flyer_numbers": {"CA": "111"}, "…": "…" },
  "trace_id": "tr-…" }

// POST /api/v1/memory/notes
{ "note": { "note_id": "3f1c…", "text": "我一般坐靠窗，不吃辣", "kind": "preference", "score": 1.0 },
  "trace_id": "tr-…" }

// GET /api/v1/memory/notes?query=坐靠窗 —— error 非空表示「这次没查到」
{ "notes": [ { "note_id": "3f1c…", "text": "我一般坐靠窗，不吃辣", "kind": "preference", "score": 0.63 } ],
  "error": null, "trace_id": "tr-…" }

// DELETE /api/v1/memory/notes?all=true
{ "removed": 2, "trace_id": "tr-…" }
```

⚠️ **身份只能来自鉴权**：三个带请求体的端点全部 `extra="forbid"`，body 里出现 `user_id` 一律 **422**。这不是洁癖——若模型是默认的 `extra="ignore"`，调用方发 `{"user_id": "别人"}` 会被**静默忽略**，他以为自己改的是别人的画像，接口却改了他自己的，两边都以为自己是对的，而账单与审批流会按其中一个的假设走。那是水平越权与「看起来成功的失败」的叠加。

⚠️ **读也报 503，不降级成空**：`TravelerMemory.recall` 在**对话链路**上永不抛、失败降级（锦上添花，见 `docs/03`），但这里是**显式**接口——调用方正在等一个答案，把故障变成「空列表 / 没有画像」等于把一次故障伪装成一个**错误的事实**（与 `get_profile` 的 docstring 同一条理由）。所以能力缺失时显式 503，且 `detail` 里说清**缺的是哪一半**：

| 缺失 | `detail` 指向 | 处置 |
| --- | --- | --- |
| 应用未装配（`app.state` 上没有门面） | 启动方式 | 确认服务由 `src.server.app:app` 启动 |
| `ALIGO__MEMORY__ENABLED=false` | 那个开关 | 打开开关并重启 |
| 向量模型不可用（语义那半降级） | 启动日志里的告警 | 修向量模型；`/api/v1/memory/profile` 不受影响 |

这三种混成一句「记忆不可用」的话，运维会先去改一个本来就对的开关。

⚠️ **写失败必须说出来，但读失败只是「这次没查到」**——本项目「读永不抛 / 写照常抛」那条不对称在 HTTP 层的落点：

| 场景 | 状态码 | 为什么 |
| --- | --- | --- |
| 记住/忘记/改画像**失败**（向量库、Postgres 故障） | `503` + `detail` 含「失败…**没有**生效」 | 静默丢弃是一次欺骗（他下周才发现助手没记住）；原因经 `safe_error` 脱敏，响应里不会出现 `scheme://user:pass@` 形式的凭据 |
| 召回**失败**（Milvus 抖了一下） | `200` + `error` 非空、`notes` 为空 | 召回是增强；但 `error` 必须在，否则调用方无法区分「没有相关记忆」与「这次没查到」 |
| 能力缺失（开关关掉 / 模型起不来） | `503` | 这时连「降级结果」都不成立，返回空列表就是一句谎话 |

⚠️ **`400`（改请求）与 `503`（服务故障）的分界由我们划，不能由异常的基类划**：改画像的校验路径与存储路径在同一次调用里，而 pydantic 的 `ValidationError` 本身就是 `ValueError` 的子类——仓储把**库里读出来的**记录反序列化时同样会抛它。按 `except ValueError → 400` 分类的写法会把「数据库故障」报成「你的请求有问题」（调用方改了请求也不会好，而且**不会重试**），并且把异常原文直接拼进响应体（对抗性审核实测能让 `postgresql+asyncpg://user:pw@…` 明文出现在响应里）。现在只有我们自己的 `src/memory/profile.py::ProfileValidationError` 映射成 `400`，其余一律 `503` + `safe_error`；分类发生在 `ProfilePatch.apply` 这道「调用方的值进入系统」的门上——同一份 `model_validate` 在仓储 `get` 里被调用时代表的是**数据损坏**，语义相反，所以不能靠异常类型本身去猜。

⚠️ **写入与删除对「检索」的可见性：默认有约 1 秒的窗口，本项目已把它消掉**。Milvus 建集合时的默认一致性级别是 `Bounded`，它意味着**刚写进去的一条不一定立刻能被召回**——2026-10-03 在容器里实测：插入后 `0.39s / 0.40s / 1.37s` 才可见，删除后 `0.56s / 0.57s / 0.58s` 才不可见。也就是说 `DELETE` 已经返回 `200`「已忘记」之后，紧接着的 `GET …?query=` **仍可能命中那条已被删掉的笔记**；用户刚说完「忘掉这个」，助手下一句又提起它。本项目在**建集合之后与首次写入之前**把该集合的一致性请求为 `Strong`（`src/knowledge/store.py:133`），复测 3 轮全部即时可见 / 不可见，召回耗时 101–186ms（一致性带来的增量在噪声里）。

⚠️ 说「请求」而不是「保证」，是因为这条路径上**没有任何东西能证明它生效**：`alter_collection_properties` 对不认识的属性名**不报错**（实测传一个不存在的键，返回成功且键真的出现在集合属性里），而改完之后回读还会**先返回旧值**一段时间。真实级别只在两处回读里可见——`/readyz` 的 `milvus.consistency_level` 与 `scripts/milvus_init.py` 的输出（它**不参与**发布闸门判定：那不是形态问题，且延迟生效会误报）。

⚠️ **「忘记」只能按原文**：`DELETE` 要的是与当初 `POST` 进来时**逐字一致**的文本（`note_id` 由 `(user_id, text)` 确定性算出）。正确用法是先 `GET …?query=` 召回、拿到原文再删。这是刻意的——「按相似度删」会误删用户没说过的内容，而删除不可撤销。`?all=true` 清空的是**当前身份**的全部笔记（底层按 `user_id` 过滤后逐条删，绝不碰整个集合：那个集合里住着所有用户的记忆），并返回删掉的条数——只回一个 200 的话，调用方无法区分「清空了 3 条」与「本来就没有任何记录」。两个参数（`all=true` 与请求体）**同时给出**时返回 `400` 而不是猜一个：删除不可撤销，而这两个参数表达的是完全不同的意图。

⚠️ **`POST` 幂等，所以成功是 `200` 不是 `201`**：同一句话记住两次不会产生两条（第二次覆盖第一次）。幂等不是省空间——Top-K 检索里两条一模一样的笔记会挤掉别的笔记的位置，用户越是反复提到某件事，它就越把其他记忆挤出召回窗口，恰好与直觉相反（`src/memory/semantic.py::note_id`）。

   要看历史请走 `GET /sessions/{id}/messages`。
2. **但清理是异步的，中间有一个真实窗口。** 落库与清理都在一个后台任务里跑

框架的**凭据与模型目录**同样在根路径上：`GET/POST /credential/`、`PATCH/DELETE /credential/{id}`（凭据 CRUD）与 `GET /model/?provider=`（模型卡片列表）——前端选择器就是这两份列表拼出来的（见 2.4）。⚠️ 配了真实密钥的部署里，那条属主为 `aligo-system` 的共享凭据（id `aligo-system-model`）会出现在 `GET /credential/` 的列表里，但**看得见、读不到**：非属主的 `data` 被框架打码成 `{type, name}` 且 `editable` 为假，共享权限只有 `READ`（打码在 `_build_view`，`agentscope/app/_service/_access.py:548-569`；权限来源见 `src/llm/system_credential.py:264` 的 `SystemCredentialAccessPolicy`）——对话运行期**用**它，调用方却**读不出密钥、改不了、也删不掉**。配套的另一半是：`aligo-system` 是**保留身份**，客户端（含 JWT 的 `sub`）声明它一律拒绝（完整约定在「五、状态码与错误约定」；共享凭据为什么必须是只读、以及四条 `mode` 的判定顺序见 2.4）。零密钥部署不播种这条记录，本段只对「配了密钥」的部署生效。

## 四、工具集（模型可调用）

工具是「智能体能做什么」的边界。全部由 `src/tools/` 提供，通过
`src/tools/__init__.py` 的 `build_business_tools` **单点登记**（要加工具只改这一处）。

### 4.1 只读 vs 需要确认（HITL）

`FunctionTool` 的 `is_read_only` 决定权限引擎怎么对待它：

- **只读**（`is_read_only=True`）：走引擎的**快速通道**，在**所有** `PermissionMode` 下自动放行，不弹确认。
- **非只读**（默认 `ASK`）：走人工确认（HITL）——用户点一下才执行。

判据不是「它写不写数据库」，而是**「每次调用都弹一次确认，产品还成立吗」**。
例如意图识别工具每次都弹「正在识别你的意图」，产品就没法用了，所以它是只读的。

### 4.2 工具清单

| 工具名 | 入参 | 返回卡片 | 只读 |
| --- | --- | --- | --- |
| `search_transport` | `origin`, `destination`, `depart_date`, `mode="ANY"` | `transport_options` | ✅ |
| `search_hotels` | `city`, `area=""`, `check_in=""`, `check_out=""` | `hotel_options` | ✅ |
| `check_travel_policy` | `kind`, `price=0.0`, `cabin=""` | `policy_verdict` | ✅ |
| `query_orders` | `kind=""`, `limit=5` | `order_list` | ✅ |
| `submit_approval` | `title`, `destination=""`, `depart_date=""`, `days=0`, `amount=0.0` | `approval_result` | ❌ 需确认 |
| `aligo_route_intent` | `intent`, `matched_rule=""`, `target_agents=None`, `reason=""` | `route_decision` | ✅ |
| `recognize_intent` | `text` | 无卡片（`items` 为结构化拆解） | ✅ |

逐条说明（**入参细节与语义边界以源码里的 docstring 为准**，这里只说要点）：

- **`search_transport`**（`src/tools/travel.py`）——查班次。`mode` 取 `FLIGHT` / `TRAIN` / `ANY`，
  解析失败**退回 `ANY`（「未指定」）而不是报错**：这是一个「模型给了个看不懂的值」的常见场景，
  当成致命错误会让一次正常查询变成报错。必填项（origin / destination / depart_date）任一为空时，
  返回的是**追问**（`needs_input`）而不是错误，并给出缺失项清单。
- **`search_hotels`**（`src/tools/travel.py`）——查酒店。只有 `city` 必填，其余可空（空 = 不限）。
- **`check_travel_policy`**（`src/tools/travel.py`）——合规检查。`kind` 取 `hotel` / `flight`；
  `cabin` 只在 `kind=flight` 时有意义。判定逻辑在 `src/domain/rules.py` 的
  `check_cabin` / `check_hotel_price` / `check_flight_price`。
- **`query_orders`**（`src/tools/orders.py`）——查订单与待审批事项。`limit` 会被**夹到 `[1, 20]`**
  （`safe_limit`）——模型完全可能传 `limit=1000`，那会把整个订单历史塞进上下文。**不信任模型给的值**。
- **`submit_approval`**（`src/tools/orders.py`）——**唯一的非只读工具**，走 HITL。
  提交时把订单从 `DRAFT` 推到 `PENDING_APPROVAL`，迁移合法性由 `src/domain/rules.py` 的
  `check_transition` 把关（不允许的迁移返回错误而不是抛异常）。**申请单号**用 `shortuuid` 生成
  （`AP-xxxxxx`，`src/tools/orders.py:275-290`）——注意它与 `TravelOrder.order_id`（订单号）是
  **两个刻意分开的标识**（`src/domain/entities.py:166` 与 `:215`），别混用。
- **`aligo_route_intent`**（`src/tools/route.py`）——**通常由系统自动调用**，不由模型决定。
  当它出现时，说明路由规则已经根据输入（多为一键按钮）定好了意图，模型只需照「下一步」执行。
  意图值非法时返回 `error_chunk`（中文说明）而不是抛异常——抛出的异常会被框架吞成一段英文错误文本，
  模型只能看到 `ValueError: 'FOO' is not a valid Intent`，而中文说明能让模型知道「路由坏了，请自己判断」，
  这对用户是**可恢复**的。
- **`recognize_intent`**（`src/tools/expert.py`）——把一句话拆成结构化意图。**不要每轮都调**，
  只在「意图不确定」或「一句话说了好几件事」时用。`text` 要**原样**传（不要改写、不要省略），
  因为识别器看的正是用户真实的措辞与错别字。返回体里含前端契约字段
  （`reasoning` / `rewritten_query` / `needs_clarification` / `clarification_question`），
  **字段名改动要前后端一起动**。

### 4.3 统一返回契约（卡片约定）

所有工具返回一个 `ToolChunk`，其内容是一段 JSON 文本（`ensure_ascii=False`，中文不转义）。
契约的定义与理由写在 `src/tools/_result.py:32-43`：

```json
{
  "ok": true,
  "summary": "找到 5 个从杭州到北京的选项",
  "card": "transport_options",
  "items": [ { "...": "卡片数据" } ],
  "needs": ["出发城市"]
}
```

| 字段 | 出现时机 | 给谁看 |
| --- | --- | --- |
| `ok` | 始终 | 机器判定成败 |
| `summary` | 始终 | 给**模型**和**用户**看的自然语言 |
| `card` | 有卡片时 | 给**前端**看的机器可读标记；无卡片时为空串 |
| `items` | 有卡片时 | 卡片数据；无卡片时为 `null` |
| `needs` | 仅 `needs_input` | 缺失项清单，让模型知道该追问什么 |

**`summary` 与 `card` 的分工是这份契约的核心，两者都要有**：只留 `card`，模型拿到一串没有语义的 JSON
会开始瞎猜字段含义；只留 `summary`，前端只能渲染纯文本。卡片类型由 `src/tools/_result.py` 里的常量定义：

| 常量 | 值 | 用途 |
| --- | --- | --- |
| `CARD_TRANSPORT` | `transport_options` | 交通班次 |
| `CARD_HOTEL` | `hotel_options` | 酒店 |
| `CARD_POLICY` | `policy_verdict` | 合规判定 |
| `CARD_ORDERS` | `order_list` | 订单列表 |
| `CARD_APPROVAL` | `approval_result` | 审批结果 |
| `CARD_ROUTE` | `route_decision` | 路由决策 |

三个构造函数决定 `ok` / `state` 的组合：

| 函数 | `ToolResultState` | 语义 |
| --- | --- | --- |
| `ok_chunk` | `SUCCESS` | 正常完成 |
| `needs_input_chunk` | `SUCCESS` | **不是错误**——用户还没说清楚，去问用户（带 `needs`） |
| `error_chunk` | `ERROR` | 工具自身失败（带 `detail`） |

> ⚠️ `needs_input` 是 `SUCCESS` 而不是 `ERROR`，这是刻意的：它表达的是「正常流程里缺一个槽位」，
> 不是「出错了」。把它当错误会在界面上弹一个不该有的失败提示。

**`policy_verdict` 卡片有两种语义，靠 `lookup` 判别**（`src/tools/travel.py:513-588`）：
「查标准」（`lookup: true`）与「核对价格」（`lookup: false`）共用同一张卡片，
但核对的负载里有 `compliant`、查标准没有。前端**必须**按 `lookup` 分流，
不能写成 `compliant === true ? 绿 : 红`——那样「住宿标准是多少」这种最普通的问法
会打出一个红色「不符合」徽标，用户看到的是一句**无中生有的指控**。
核对分支显式写 `lookup: false`（而不是省略该字段），是为了让两种语义在负载里能被穷举出来，
而不是靠「有没有 `compliant`」去猜。

## 五、状态码与错误约定

| 场景 | 状态码 | 备注 |
| --- | --- | --- |
| 正常 | `200` | SSE 为 `200` + `text/event-stream` |
| 凭据缺失/无效 | `401` | **由鉴权中间件**返回，不是路由抛的 |
| 声明保留身份（`aligo-system`） | `403` | **刻意不用 401**：401 会让客户端去走登录流程，而没有任何登录能变成系统身份（见下） |
| 超过限流 | `429` | 由限流中间件返回 |
| 资源不属于当前身份 | `404` | **刻意不用 403**（见 2.3 的理由） |
| 身份依赖没取到标识 | `422` | 框架 `Depends` 校验失败 |
| 请求体形状不对（含未知字段） | `422` | 记忆接口用它挡住 body 里的 `user_id`（见 2.5） |
| 字段值不合法（如舱位不在枚举里） | `400` | 是**调用方**该改请求，不是服务故障（报 503 会让它重试一个永远不会成功的请求）。⚠️ 判据是**我们自己的** `ProfileValidationError` 而不是 `ValueError`——后者会把仓储/驱动碰巧抛出的同类异常也算进来，见 2.5 |
| 记忆接口拿到**空白**文本（`"   "`） | `400` | 空白在语义上就是「什么都没给」，而 `min_length=1` 拦不住它；放行的话它会返回一个与「确实没有记忆」同形的空结果（见 2.5） |
| 记忆能力缺失 / 记忆写入失败 | `503` | 三种缺失的区分与「写失败不会静默」见 2.5 |
| 指标未启用时打 `/metrics` | `404` | 条件式路由 |
| 依赖不健康时打 `/readyz` | `503` | 响应体自解释，逐项列出哪个 not ok |

**保留身份为什么是 `403` 而不是 `401`**（`src/server/middleware/auth.py:543` 的 `_reject_reserved_identity`）：
配了真实密钥的部署里，`aligo-system` 名下有一条带运营者密钥的系统凭据，而框架的规则是「属主读自己的凭据是明文、且可编辑可删除」——若客户端能声明这个身份，一次 `GET /credential/` 就能读出密钥明文、一次 `DELETE` 就能让全员的模型当场失效。所以中间件在**三条通道**（`X-User-ID` 直连、JWT 的 `sub`、`require_user_header=false` 的匿名分支）都拒绝它；一处漏掉就等于没有拦，而最后那条尤其容易被忘：它不重写请求头，只拦前两条的话，「把开关关掉」就成了绕过规则的捷径。
⚠️ 401 的语义是「你没提供可用的凭据」，客户端据此会去走登录流程——但没有任何一次登录能让人变成系统身份，于是它会陷入「登了再试、再 401」；403 说的才是「凭据本身没问题，但这件事实在不能做」，同时告诉调用方**别再重试**。
⚠️ 响应是 `{"detail": "该身份为系统保留身份，客户端不得声明。"}`，**不回显**被拒绝的那个 id——攻击者得先知道这个名字，才谈得上尝试它。判据是**精确比较**（调用方先 `strip()`）：框架拿请求头的值与记录属主做 `==`，`ALIGO-SYSTEM` 在它眼里本就是另一个用户，因此这里也不做大小写折叠（`src/llm/identity.py:66`）。这类拒绝会计入 `aligo_auth_failures_total` 的 `reserved_identity` 标签——规则若被整条删掉，它掉到 0，而其它一切看起来完全正常。

**错误信息里永不出现凭据**：探针与 `describe_*` 输出只给 `api_key_configured` 这类布尔值，
错误信息会剥掉 `scheme://user:pass@` 形式的口令。
