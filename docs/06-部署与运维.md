## 一、快速开始

```bash
# 1) 准备环境变量（首次）
cp .env.example .env
#    必须改掉其中的口令类占位值（POSTGRES_PASSWORD / REDIS_PASSWORD / MINIO_ROOT_PASSWORD / ...）
#    ⚠️ 不要把 ALIGO__IMAGE_REGISTRY 写进 .env —— 理由见第三节

# 2) 起核心档（postgres / redis / etcd / minio / milvus / app）
make up

# 3) 建集合、灌演示数据、预置智能体（幂等，见 6.2 / 6.3 / 6.4）
make milvus_init
make seed_data
make provision-agent

# 4) 验证
curl -s localhost:8000/healthz   # {"status":"ok"}
curl -s localhost:8000/readyz    # 各依赖的真实连通性
curl -s localhost:8000/metrics   # Prometheus 文本
make smoke                       # 端到端冒烟，退出码 0 = 通过
make concurrency                 # 3 个用户同时发不同请求，并发正确性，退出码 0 = 通过
```

> ⚠️ 第 3 步少跑任何一条，症状都是**页面打得开、但用不了**：
> 漏 `milvus_init` → 政策检索与记忆召回报 `collection not found`（第九节）；
> 漏 `provision-agent` → **输入框是灰的、点不动**（8.3）。
> 这两种都不会让探针变红 —— `/readyz` 照常全绿。

`make smoke` 的最后一项会**真的发一句话**（端到端对话），所以它会临时建一个智能体
与一条会话 —— 跑完**自己删掉并回读确认**，删除结果写在该项检查的详情里（绿行上的
「🧹 已清理本轮产物」就是它），失败与异常路径同样会删。要留现场排查时用
`python scripts/smoke.py --keep-artifacts`（只打印 id，什么都不删）。

`make concurrency` 与 `make smoke` **问的不是同一件事**，两者都要跑：

| 目标 | 形态 | 回答的问题 |
| --- | --- | --- |
| `make smoke` | 串行，各打一发 | 这套部署能不能用 |
| `make loadtest` | 并发，但只发 GET、只打一个端点 | 并发下延迟与失败率的**分布** |
| `make concurrency` | 3 个用户同时发**不同**请求 | 同时用的时候数据会不会**串号** |

⚠️ 前两者的绿灯推不出后者，而且不是理论上的可能：`loadtest.py` 的模块注释里
写死了「本脚本不发送请求体」，它只会发 GET —— 「三个用户各建各的会话、各发各的话」
这条路径它一毫秒都没覆盖过。而线上一次真正的并发，几乎必然发生在这里。

`make concurrency` 同样**跑完自己删掉**（与 smoke 同一条纪律），用户是
`concurrency-user-1..3` 这几个一次性工作区，不碰 `alice`。要留现场用
`make concurrency CONCURRENCY_ARGS="--keep"`。加压用
`CONCURRENCY_ARGS="--users 6 --rounds 2"`。

> ⚠️ 它的 12 条判据里有一条叫「**确实同时**」，判定的是每人 `POST /chat/`
> 与收到 `REPLY_END` 的时间窗**重叠**（`max(t_chat) < min(t_end)`）。
> 这条不通过时，其余「通过」都没有意义 —— 一个把请求顺序发出的脚本同样会
> 打印「3/3 通过」，而那验的是排队。所以看报告时先看这一条的详情里
> 「全员同时在飞 N 秒」那个数字。
>
> ⚠️ 但要**知道这条判据有多弱**：栅栏保证所有人几乎同时发出 `POST /chat/`，
> 于是 `max(t_chat) < min(t_end)` 在**一个严格串行的服务端上也会通过**
> （同时到达，排队处理，但都还没结束）。它能排除的是「脚本自己按顺序发」，
> 排不掉「服务端串行处理」。真正强的那份证据在服务端一侧，见下。

**怎么自己核一遍「服务端真的在并发」**（不要只信脚本的绿灯）。app 在 `--workers 1`
下单进程跑 asyncio，所以下面这条命令量的是**一个进程内**的同时打开数：
把 `http_trace` 每个 span 的耗时从结束时刻倒推回开始时刻，再扫一遍时间轴。

```bash
docker compose logs app --since 10m | grep http_trace   # 先看原样日志
# 每个 GET /sessions/*/stream 行都有「→ 200（Nms）」，N 就是该次流的服务端耗时
```

实测（6 用户 × 2 轮，`--workers 1`，单进程已确认）：

| 观测量 | 数值 | 串行服务端上会是 |
| --- | --- | --- |
| 同一时刻打开的 SSE 流 | **≥6 条**，累计约 39 秒、最长连续约 25 秒 | 恒为 1 |
| 12 条流的服务端耗时合计 | **253.1s** | — |
| 对应墙钟跨度 | **45.0s** | ≈253s |
| 倍率 | **5.6×** | ≈1.0× |

倍率 5.6 就是「单进程把 253 秒的活儿压进 45 秒」，串行不可能做到。≥6 条同时打开
同样是直接反证——串行服务端上第二个请求要等第一个流关闭才可能开始。

> ⚠️ **「≥6」而不是「峰值 6」是刻意的。** 这套算法要把「结束时刻 − 耗时」还原成
> 开始时刻，而日志时间戳当时只有**秒级**精度，每条区间因此带 ±1 秒的不确定度。
> 严格按毫秒扫，瞬时峰值会算到 **7**，但那 7 只出现在 3 段共 0.71 秒的亚秒毛刺里
> —— 落在不确定区内，**既不能当真实峰值断言、也不能当作不存在**。
> 能抗住 ±1 秒位移的结论只有「≥6 条同时在开」。
> 想要钉死瞬时峰值，得先把日志时间戳升到毫秒（`src/observability/logging.py`
> 的 `_LOG_FORMAT`，已加 `%(msecs)03d`；改动之前那里注释写着「精确到毫秒」
> 而格式串只有秒，正是这个不确定度的唯一来源）。

### 这个脚本**测不到**什么（别把它当成容量证明）

一次通过只说明「3~6 个用户、各 1~2 轮、约定负载下没有异常」。以下都是**已知未覆盖**：

- **连接池上限**：`POOL_SIZE=10 + MAX_OVERFLOW=20` ⇒ 单 engine 峰值 30 连接。
  N≤6 时离上限很远，**连接耗尽这条路径一次都没走到过**。
- **限流**：`ALIGO__RATE_LIMIT__*` 的 429 在 N≤6 时打不出来，客户端侧
  「没有 429」是**因为没触发**，不是因为限流工作正常。
- **同会话并发**：脚本给每人**各建一条**会话，`POST /chat/` 的 409
  （同会话已在跑）**是刻意避开的**——它测的是跨会话并发，不是同会话互斥。
  那条路径由 `tests/` 里的单测覆盖。
- **业务库 / 向量库**：订单与差标走的是**内存仓储**（`agents_factory.py` 里的
  `InMemoryOrderRepository()`），所以并发下的**数据库争用、事务隔离、Milvus 召回**
  都没有被压到。业务表本身也没写入。
- **跨用户隔离只验了 GET**：判据 7 只探了读接口的 404，没验证「A 能不能 DELETE 掉
  B 的会话」这类**写**越权。
- **判据 10 的会话回读有一个前提**：它依赖「这些会话在本轮里被成功读写过」，
  所以「存在」是已证的。若将来会话的 DELETE 变成异步软删、列表里仍会出现，
  这条判据会报失败——那是**该报的**，不是误报。
- **进程级崩溃**：全部失败模式都是「返回了错误码」。OOM、段错误、worker 被
  `kill -9`（此时 `finally` 里的清理也跑不到）都不在观测范围内。

`make up` 内部是 `docker compose up --wait`，**只等 healthy**。app 的 healthcheck 探的是
`/readyz`（真实连 PG / Redis / Milvus），所以「`make up` 返回」这件事本身就是
「依赖真的都通了、应用也完成启动」的证据。

> ⚠️ `--wait` 必须有超时上限（`Makefile` 的 `WAIT_TIMEOUT`，默认 480s），否则 Redis 密码不对时
> SchedulerManager 卡在「等订阅就绪」，容器既不 healthy 也不 exited，`--wait` 会**一直挂住**，
> 终端看起来像卡死。给上限后超时会以非零退出码失败并打印未就绪的服务。

镜像级健康检查（`Dockerfile` 的 `HEALTHCHECK`）探的是 `/healthz`（零 I/O），
与 compose 的 `/readyz` **刻意不同**——理由见第五节。

## 二、四个 compose 档位与端口

compose 里共 **13 个服务**，全部**显式挂档**，没有「默认档」服务；命令按档过滤。

| 档位 | 服务数 | 服务 | 何时用 |
| --- | --- | --- | --- |
| `core` | 6 | app / postgres / redis / etcd / minio / milvus | 默认。跑业务与对话 |
| `tracing` | 4 | langfuse / langfuse-worker / langfuse-redis / clickhouse | 要看全链路 trace |
| `observability` | 2 | prometheus / grafana | 要看指标面板 |
| `optional` | 1 | maxkb | 只作可选对照（自建 Milvus RAG 才是主路径） |

默认全栈（core + tracing + observability）= **12 个**。

| 服务 | 宿主端口 | 说明 |
| --- | --- | --- |
| app | `8000` | 可用 `ALIGO__APP__PORT` 覆盖 |
| postgres | 5432 | 业务库 + Langfuse 元数据库（**同实例、不同 database**，省内存） |
| redis | 6379 | 会话状态、幂等锁、SSE 事件总线 pub/sub |
| minio | 9000 / 9001 | 对象存储（Milvus 依赖）/ 控制台 |
| milvus | 19530 / 9091 | 向量库 / metrics |
| prometheus | 9090 | 观测档 |
| grafana | 3000 | 观测档 |
| langfuse | 3001 | trace 档 |
| maxkb | 8080 | optional 档 |

常用命令：

```bash
make up           # core 档
make up-obs       # core + observability（prometheus + grafana）
make down         # ⚠️ 切档前先 down；up-tracing 会重建 app 容器
make up-tracing   # core + observability + tracing（含 langfuse v3 四容器，内存占用最高）
make up-optional  # **只有** optional 档（maxkb）；不含 core，app/pg/redis 都不会被启动
```

> ⚠️ `make up-tracing` 带的是**三档**（`core` + `observability` + `tracing`），不只是
> `core + tracing`：它复用 `up-obs` 的指标栈，并且会注入 OTLP 变量**重建 app 容器**。
> 已启动的 app 会被停掉重建，这是预期行为。
>
> ⚠️ `make up-optional` 与其它目标不同，它带的是**单独的** `optional` 档 ——
> 跑它**不会**启动 core。若需要一个连得上后端、能对话的 MaxKB 环境，
> 请先 `make up`，再 `make up-optional`。

> ⚠️ **`down` / `clean` / `pull` 必须带齐档位**，否则 compose 会**静默什么都不做**却照样退出 0。
> `Makefile` 用 `ALL_PROFILES` 统一处理，并有测试
> （`tests/test_makefile_contract.py::test_all_profiles_matches_compose`）钉住
> 「档位名集合必须与 compose 的 `profiles:` 完全一致」。

> ⚠️ 本机 Docker VM 内存约 3.82 GiB。core 与观测栈同跑时优先用 `make up-obs`（只加指标），
> 确认有余量再加 Langfuse。用 `docker stats` 看真实占用。

## 三、配置体系

### 3.1 优先级（从低到高）

```text
config/base.yaml                    全环境默认值
  ↓ 深度合并
config/{env}.yaml                   env 由 ALIGO__APP__ENV 决定，默认 dev
  ↓ 逐键覆盖
ALIGO__<段>__<键> 环境变量           例：ALIGO__LLM__MODEL=qwen3.8-flash
```

- 段名与键名都是**大写**，用 `__`（双下划线）分隔。
- `${VAR}` / `${VAR:-default}` 可在 YAML 值里做展开。`${VAR:-default}` 表示「缺失是允许的，用默认值」，
  这样「没设置」是预期状态、不产生告警；`${VAR}`（无 `:-`）在缺失时会被 loader 记进 missing 列表并告警。
- `config/` 下的文件：`base.yaml` + `dev.yaml` / `test.yaml` / `prod.yaml`，都有全中文注释。

### 3.2 `extra="forbid"`：未知键 = 启动即崩

配置模型是 pydantic `_StrictModel`（`extra="forbid"`）。**一个 schema 不认识的键会让容器启动即抛
`extra_forbidden`**，而不是被静默忽略。

这条是刻意的：配置写错时立刻崩，比带着一份「以为生效了」的默认值跑起来强。它对每个消费者都成立：

- **`.env` 里的键**：`.env.example` 里列的键必须与 `src/config/schema.py` 的字段一一对应。
  用例 `tests/test_config_loader.py::test_env_example_keys_are_all_accepted_by_the_loader`
  会把模板里每个生效的键喂给真正的 `load_settings`，有一个对不上就红。
  被 `#` 注释掉的示例**不算数**——它们不会进入容器环境。
- **命令行环境变量**：同样受约束（见 3.3 的 `IMAGE_REGISTRY` 陷阱）。
- **`config/{env}.yaml`**：分段名写错一样崩。

### 3.3 🔴 `ALIGO__IMAGE_REGISTRY` 绝不能写进 `.env`

本机实测：写进去会让 app 容器**崩溃重启**。原因是 `.env` 被**两个消费者**读取：

1. **compose 自身** —— 用于镜像名的 `${...}` 插值；
2. **app 容器** —— 因为 app 服务经公共片段继承了 `env_file: .env`。

而 app 的配置加载器对 `ALIGO__` 前缀做严格校验，它没有 `image_registry` 这个设置项，
于是启动即抛 `extra_forbidden` 并进入 `Restarting (1)` 循环。

**正确用法是把前缀放在命令行上**（只影响 make 进程与其子进程 compose，不进容器）：

```bash
ALIGO__IMAGE_REGISTRY=docker.m.daocloud.io/ make up
```

需要它是因为部分镜像（如 `milvusdb/milvus`）只发布在 Docker Hub，而某些环境
`registry-1.docker.io` 会时通时断。给它一个镜像站前缀即可整体改走该站。
注意 `~/.docker/daemon.json` 的 `registry-mirrors` 在本机**实测无效**。

### 3.4 `.env` 与 `.env.example`

`.gitignore` 忽略 `.env` / `.env.*`，但用 `!.env.example` **显式放行**模板。
所以 `.env.example` 是**注定要提交进仓库**的那一个——**里面不得有任何真实密钥**。
需要密钥时放进 `.env`。

⚠️ **trace 的 OTLP 端点默认不写进 `.env`**，而是由 compose 的 `app.environment` 按档位注入：

- 默认（core / up-obs）：`ALIGO__OBSERVABILITY__TRACE_EXPORTER=none`——不装配导出器，零噪声；
- `make up-tracing`：Makefile 在 compose 命令前注入 otlp 两个变量（**命令行环境变量优先级高于 `.env`**），
  app 容器被重建并带上配置。

也可以把它们写进 `.env` 手工常开（compose 的注释里明说了这一点，见 `docker-compose.yaml:400`）——
但那会让 **core 档**也去连一个解析不了的域名并重试，故不推荐。这就是「默认不写」而非「不能写」。

为什么不默认设成 otlp：trace 的接收端 `langfuse` 只在 tracing 档存在。
默认就设 otlp 的话，`make up`（core 档）会让应用一直去连一个解析不了的域名，导出器按批重试并刷 ERROR 日志，
于是「本来一切正常」的 core 档看起来像坏了。

### 3.5 凭据引导：两种形态，且**不存在**「共享开关」

框架的对话链路不靠「全局默认模型」工作，它要求 (a) 一条**调用者可解析**的 credential 记录与
(b) 会话的 `chat_model_config` 指向它，两者同时在位。缺任何一个，表现都是同一副面孔：
探针全绿、SPA 正常渲染、「发送」按钮永远灰着（前端可用模型由 `GET /credential/` ×
`GET /model/?provider=` 拼出，零凭据 ⇒ 分组为空 ⇒ `selectedModel === null` ⇒ `disabled`，
`web/frontend/src/pages/chat/ChatViewport.tsx:852`）。本项目用两条**互斥且互补**的路径把 (a) 补上：

| 形态 | 触发判据 | 播种什么 | 有没有秘密 |
| --- | --- | --- | --- |
| 零密钥降级 | `should_use_mock(settings)`：`use_mock_when_no_key=true` **且** `api_key` 为空（`src/llm/factory.py:127-140`；默认 true，见 `config/base.yaml:293`） | **每个已鉴权用户**一条 Mock 凭据，id 由 user_id 确定性派生（`src/llm/mock.py:110`），在「第一次见到该用户」时按需播种（`src/server/middleware/mock_credential.py:124-141`） | 无（MockLLM 不联网、不花钱，复制一万份也不损失什么） |
| 系统凭据共享 | `sharing_enabled`：`not should_use_mock(...) and has_api_key(...)`（`src/llm/system_credential.py:107-125`） | **一条**属主 `aligo-system`、id 固定 `aligo-system-model` 的真凭据（`src/llm/system_credential.py:100`），启动期由 lifespan 幂等写入（`src/server/app.py:408`） | 运营者的真 key，全公司只有一份；以 READ 权限共享，用户**能用但读不到**明文 |

⚠️ **共享没有开关**。运维常去找一个「共享开关」——它不存在，也不该存在：`sharing_enabled`
完全由既有配置**派生**，只要「不是降级」且「密钥非空」就自动共享。

⚠️ **关掉共享只有一条路：清空密钥**（`DASHSCOPE_API_KEY`，或显式覆盖 `ALIGO__LLM__API_KEY=`）。
这里有个**反直觉的坑**：把 `ALIGO__LLM__USE_MOCK_WHEN_NO_KEY` 设为 true **关不掉共享** ——
判据是 `sharing_enabled = not should_use_mock(settings) and has_api_key(settings)`
（`src/llm/system_credential.py:125`），而 `should_use_mock = use_mock_when_no_key and not has_api_key`
（`src/llm/factory.py:140`）。**只要 api_key 非空**，那个开关取任何值都得到
`should_use_mock=False`，共享照旧生效（它是「没密钥时才降级」的开关，不是「降级开关」）。
清空密钥后，默认 true 的它会让服务自动切到零密钥 Mock 形态——这才是关掉共享时会发生的事
（启动日志里也是这么写的，`src/server/app.py:426-439`）。
⚠️ 环境变量在**容器创建时**注入，改完 `.env` 必须让 app 容器重建才生效（`make up`；只
`docker compose restart app` 不会重新读取 `.env`）。

⚠️ **为什么共享权限是 READ、而不是把 key 复制进每个用户的记录**：owner 读自己的凭据是
**明文**，复制一份就是「一次共享、全员泄密」（完整论证见 `src/llm/degradation.py:48-63`）。
共享形态下用户在「凭据」页看到的是打码的 `{type, name}`，运行期由框架解析原始记录供模型使用。
⚠️ 属主名 `aligo-system` 同时是**保留身份**：任何客户端都不得声明它（见 8.2）。

**改了密钥怎么办**：改 `.env` 里的 `DASHSCOPE_API_KEY` → `make up`。凭据 id 固定，
每次 lifespan 进入段都会走**就地更新**分支（`src/llm/system_credential.py:226-233`），
即覆盖同一条记录，不会越长越多，也不需要手工删旧记录。

## 四、健康检查与探针

| 端点 | 语义 | 关键性质 | 谁在用 |
| --- | --- | --- | --- |
| `GET /healthz` | 存活 | **零 I/O**——不连任何依赖，恒 200 | 镜像 `HEALTHCHECK`、k8s livenessProbe |
| `GET /readyz` | 就绪 | **真实连** PG / Redis / Milvus，全绿才 200，否则 503 + 逐项明细 | compose healthcheck、k8s readinessProbe |
| `GET /metrics` | 指标 | `metrics_enabled=true` 才存在，否则 404 | Prometheus |

### 4.1 `/readyz` 的判据

- 三项检查**并发**执行，每项 **3 秒**上限（`src/server/probes.py` 的 `CHECK_TIMEOUT_SECONDS`）。
- 必需项是 `REQUIRED_CHECKS = {postgres, redis, boot}`（`src/server/probes.py`）。
  ⚠️ **Milvus 不是必需项**——它会出现在响应体里（`required: false`），但并不参与就绪判定。
  理由：Milvus 没起来不该拖垮整个服务（P4 验收明确要求「Milvus 不可用不得拖垮服务」）。
- `boot` 检查的就是 `app.state.boot_completed` 标志——由本项目自己的 lifespan 在
  框架 lifespan 进入段之后置 `True`、在退出段开始处置 `False`（见 `docs/03-模块关系与调用逻辑.md` 2.3）。
- 响应体**自解释**，逐项给出 `{ok, detail, duration_ms, required}`，
  使 503 本身就能定位问题，不必翻日志。且它**永不泄露凭据**（错误信息经过脱敏）。

### 4.2 两条设计原则

1. **`/healthz` 与 `/readyz` 判断的是两件独立的事。** 外部依赖挂了 ⇒ `/readyz` 503 但 `/healthz` 仍 200，
   编排系统不该因此重启进程（重启治不好一个挂掉的数据库，只会让日志更难读）。
2. **`/metrics` 未启用时返 404 而不是 200 空体。** 404 会让 Prometheus 把该 target 标成 down，
   这是一个**显式**的信号；若返回 200 空体，抓取会显示成功而所有面板都是空的。

### 4.3 为什么镜像探 `/healthz`、compose 探 `/readyz`

- 镜像里的 `HEALTHCHECK` 探 `/healthz`：它写在镜像里，意味着 `docker run` 单跑也生效。
  单跑时 PG / Redis / Milvus 都不在，就绪**必然**失败，`/readyz` 会让容器永远 unhealthy。
- compose 里的 healthcheck 探 `/readyz`：compose 环境下这些依赖都在（`depends_on` 已保证它们 healthy），
  「就绪」在这里可判定且有意义。超时给到 10s（需 ≥ 探针自身的 3s/项预算；三项并发，故 10s 足够）。

> ⚠️ 两处探针的**语义差异是刻意的**，不要为了「统一」而改成一致。
> 另注：Docker **不会**因为容器 unhealthy 而自动重启它（没有 autoheal 机制），
> 所以依赖短暂抖动只会让状态显示为 unhealthy，不会造成重启风暴。

### 4.4 trace 的装配是条件式的

OTLP → Langfuse 的装配条件有**四个**，缺一即不装配（`src/observability/tracing.py:187-217`）：

1. `trace_exporter == "otlp"`；
2. `otlp_endpoint` 非空；
3. `langfuse_public_key` 非空；
4. `langfuse_secret_key` 非空。

⚠️ 后两条容易被忽略，理由却不神秘：Langfuse v3 的 OTLP 端点要求 HTTP Basic 认证，
缺认证头直接 401，而 OTLP 导出器**只重试 408/5xx**——401 会被丢弃且不重试，
装上也收不到任何 trace。所以缺密钥时代码**主动不装配**并打一条 warning，
而不是让你去查「为什么一条都没有」。

⚠️ 这些条件必须**显式满足**——未配 `TracerProvider` 时框架的 `TracingMiddleware`
会**静默短路**，表现为「trace 功能看起来开了，但 Langfuse 里什么都没有」，极易被误判成网络问题。

## 五、镜像与构建

- **多阶段构建**：builder 阶段只装依赖进 `/opt/venv`，运行阶段只带该虚拟环境，
  把编译器与构建缓存留在构建层，减小体积与攻击面。
- **非 root 运行**：`USER aligo`；`EXPOSE 8000`。
- **`PYTHONPATH=/app`**（只放仓库根）：让 `import src.*` 可用；`agentscope` / `reme`
  由 `pip install -r requirements.txt` 装进 `/opt/venv`，靠安装元数据决定解析到哪儿，
  比在配置里硬编码一条源码树路径更稳。
- **pip 双源**：`Dockerfile` / `docker-compose.yaml` 给 pip 配了
  `PIP_EXTRA_INDEX_URL=https://pypi.org/simple/` 作为**备用源**。这是正确性保障，不是可选优化：
  阿里云镜像索引页的 gzip 缓存副本曾陈旧到不含某个真实存在的版本，而 pip 无条件发 `Accept-Encoding: gzip`。
- **构建耗时**：`make build` 带 `--no-cache` 全量重建，pip 层占绝大部分（本机容器内下载实测约 180–240 kB/s）。
  只改了源码或文档时请用 `make up`，别用 `make build`。

**前端产物走 `src/` 这一层，所以「改前端」不必重建镜像**：`web/frontend/vite.config.ts:36`
把 `outDir` 定在 `src/server/static`（相对工程根解析），也就是**镜像里随 `COPY src` 一起进去的那一层**；
而 compose 的 app 服务又把 `./src` 只读挂进容器（`docker-compose.yaml:435`）。
两个后果：

1. **宿主机上跑一次 `pnpm build` 就够了**（`web/frontend/package.json` 的 `build` 脚本
   = `tsc -b && vite build`；Makefile 里**没有** `web-build` 目标，前端构建不走 `make`）
   —— 容器里的 `StaticFiles` 是**按请求读盘**的，新产物立刻生效，
   **不必重启 app、更不必重建镜像**（前提是钩子/路由没变）。
2. ⚠️ 反过来说，**只改 `web/frontend/src/` 而不 build，容器里什么都不会变**。
   症状是「我明明改了文案，刷新还是旧的」—— 那是构建产物的锅，不是浏览器缓存。

⚠️ 改了后端代码同理。**哪些改动要重建、哪些只要重启，按「生效时机」分**（全是实测口径，
别再凭「配置也在镜像里」的直觉去猜）：

| 改了什么 | 要做什么 | 为什么 |
| --- | --- | --- |
| `src/**` | `docker compose restart app` | 只读挂载（`docker-compose.yaml:435`），重启即读新文件。Makefile **没有** `make restart` 目标 |
| `config/*.yaml` | `docker compose restart app` | 同样是挂载（`docker-compose.yaml:436`），且 loader 把配置缓存在**进程内**（`src/config/loader.py:453-465`），重启才会重读 |
| `scripts/**` | 什么都不用做 | 这些脚本由 `make <目标>` 在**宿主机**直接跑（`PYTHON ?= python3`，见 `Makefile:60`），根本不经过容器 |
| `requirements.txt` / `Dockerfile` | `make build` | 只在**构建期**生效 |
| `docker-compose.yaml` 的 `environment:` / `volumes:` / `ports:` | `docker compose up -d app` | 这些值在**容器创建时**定死；`restart` 不重读 compose 文件，只有重建容器才会（`up -d` 检测到配置变化即重建） |

## 六、迁移与初始化

三件事回答三个不同的问题，**顺序不能乱**：

| 步骤 | 命令 | 做什么 | 不做什么 |
| --- | --- | --- | --- |
| 1. 业务 schema | 自动（lifespan 进入段） | 建 `business` schema 与画像表 | 不建框架表（框架自己建） |
| 2. 建集合 | `make milvus_init` | 幂等建 Milvus 集合（**政策库 + 长期记忆两个**），并**回读核验**维度/索引/度量 | **不灌数据** |
| 3. 灌数据 | `make seed_data` | 往集合里灌政策文档，往业务库写演示数据 | **不建集合** |

### 6.1 PostgreSQL 初始化

- 容器首启时 `scripts/postgres/init/` 下的脚本由 Postgres 镜像的 `/docker-entrypoint-initdb.d`
  机制执行（挂载自 compose 的 `postgres.volumes`）。两个脚本：
  - `01-business-schema.sh`——建本项目的 `business` schema；
  - `02-langfuse-role-and-db.sh`——为 trace 后端创建 Langfuse 专用角色与专用 database。
  ⚠️ 它们在 **PGDATA 为空时**才跑一次，之后重启容器**不会再跑**。
- 业务 schema 与画像表**另外**由 `ensure_business_schema` / `ensure_profile_table` 在
  **每次 lifespan 进入段**幂等创建（见 `docs/03-模块关系与调用逻辑.md` 2.3）。
  两份保障是**互补**的：init 脚本覆盖全新数据卷的首启，lifespan 覆盖**已存在的数据卷**
  （以及手工 drop 过 schema 之后的重启）。所以不要只依赖 init 脚本。
- ⚠️ **`auto_migrate` 恒为 `False`** —— 框架明确警告多副本下它不安全。

### 6.2 `make milvus_init`

`scripts/milvus_init.py` 做两件事而**不只一件**：

1. 建集合（幂等——集合已存在时 `create_collection` 是 no-op）；
2. **把建好的集合读回来，逐项与配置比对**（`verify_collection_shape`）。

第 2 步不是锦上添花。维度相同但度量不同（比如建的时候是 L2、配置写着 COSINE）的集合，
**写入成功、检索成功、有分数——没有任何一处会报错**，只是分数的大小关系没有意义。
只有回读能发现它。

⚠️ **建的是两个集合**，不是一个：

| 集合 | 谁在用 | 名字 |
| --- | --- | --- |
| 政策知识库 | 框架 KB 链路（检索/引用） | `{ALIGO__MILVUS__COLLECTION}` |
| 长期记忆画像 | `SemanticMemory`（「记住这个」+ 每轮语义召回） | `{ALIGO__MILVUS__COLLECTION}_memory` |

两者形态约束**逐项相同**（同一个 Milvus、同一个向量模型、同一个维度），所以脚本对它们
用同一套期望值。`ALIGO__MEMORY__ENABLED=false` 时跳过第二个并打印一行说明——
跳过一个东西却不说，与忘了建它，在日志上长得一模一样。
（记忆集合曾**漏建**：2026-10-03 实测，全新部署上「记住这个」直接以
`collection not found` 失败。现在写路径会在第一次写入前幂等自愈，
但**自愈不做形态核验**，所以本目标仍是发布前的必做项。）

退出码：`0` = **全部**集合已就绪且形态正确；`1` = 有集合形态不符或连接失败。

⚠️ **形态不符时不自动重建。** 删集合会丢光已索引的向量，那可能是一小时的重新灌数据——
这种决定不该由一个初始化脚本替运维做。脚本只负责把问题说清楚并给出一条可复制的修法
（修法里写的是**出问题的那个集合名**，两个集合的名字不同）。

### 6.3 `make seed_data`

`scripts/seed_data.py` 往**已建好**的集合里灌数据，并往业务库写演示数据。三条硬约束：

1. **确定性**——所有数据都是字面量，不用 `random`、不用 `hash()`。同一天跑两次，写进去的字节完全一样。
2. **幂等**——重复跑不产生重复数据。Milvus 侧幂等键是 `document_id = "seed-policy-<doc_id>"`，
   并**先 delete 再 insert**；业务库侧按各表主键，只补缺的那些。
3. **绝不打印任何密钥**——只打印**目标**（URI 已脱敏）与**条数**。

⚠️ 灌数据前请先跑 `make milvus_init`（本脚本**不建集合**）。
`make seed_data ARGS="--dry-run"` **不建立任何连接**，只把「将要写入的东西」打印出来——
它既是给人看的手稿，也是 `tests/test_seed_data.py` 的抓手。

⚠️⚠️ **政策库用哪个向量模型，是在灌数据那一刻定死的**，规则只有一条：
`DASHSCOPE_API_KEY` 非空就走真实提供方，否则走确定性 Mock
（`ensure_kb_embedding_credential`）。这不是「每次检索时再选一次」——
框架的知识库链路只认 KB 记录里钉着的凭据类型，而那条记录由本脚本写入。

由此推出两条运维上必须知道的事：

- **看到「本次用的是确定性假向量」的告警，补救动作是「配好密钥后重跑
  `make seed_data`」**：重跑会重新钉住凭据并**先删后插**重算全部 chunk 的向量。
  这是唯一的路（框架的 `PATCH /knowledge_bases` 明确不接受改 embedding 配置）。
  ⚠️ 该告警**不提供**「装 fastembed 重灌」这种补救 —— 本地 ONNX 档是本项目
  自己那条链的档位，框架侧没有对应凭据类型，装了也不会改变本脚本的结果。
- **反过来，也正因为它钉死**：换了向量模型（或维度）之后必须**重灌**，
  否则库里同时存在两种模型算出来的向量 —— 检索能跑、结果却是错的。

### 6.4 `make provision-agent`

`scripts/provision_agent.py` 给**一个身份**预置 AliGo 主智能体 `main_plan`
（并按需建一条空会话）。它是 `/chat` 页面能输入的前提，理由见 **8.3**。

```bash
make provision-agent                        # 默认 PROVISION_USER=alice
make provision-agent PROVISION_USER=bob     # 换一个身份
python scripts/provision_agent.py --no-session   # 只建智能体，不建会话
```

四条硬约束：

1. **幂等，且只创建不修改**——已存在同名智能体时直接复用，**一个字节都不改**
   （提示词也不刷新）。`--user` 指向的是别人的工作区，自动改提示词会在对方
   没要求时改掉他正在用的智能体，且改完没有任何记录。要更新提示词请用前端的
   编辑对话框（那里有明确的用户动作）。
2. **名字取自 `src/agents/prompts.py::MAIN_AGENT_NAME`，不在脚本里重抄**。
   ⚠️ 这不是风格问题：`LaneRouterMiddleware` 等中间件按 `agent.name` 收窄
   （`src/server/agents_factory.py`），名字不对时**能聊天但快慢车道与动态 Prompt
   静默失效**。用户自己在前端建智能体时，名字也必须是 `main_plan`。
3. **建会话时不写 `chat_model_config`**——模型由用户在前端选择器里挑
   （会话没有模型时前端会自动选第一个可用的并回写）。服务端替他选，等于把
   「用哪个模型」钉死在一次脚本调用上。
4. **回读核验**——创建后重新列一次，确认它真的出现在该用户的列表里。
   与 `make milvus_init` 同一条纪律：写完不算数，读回来才算。

> ⚠️ Makefile 变量刻意叫 `PROVISION_USER` 而不是 `USER`。`USER` 是 POSIX
> 环境变量，make 会直接把环境里的值当成变量值 —— 于是 `make provision-agent`
> （不带参数）会用**当前登录的操作系统用户名**建一个谁都没听说过的工作区，
> 还打印「✅ 已创建」，而目标用户什么都没拿到。带 `PROVISION_` 前缀的名字
> 不在环境里，缺参数时用的才是 `alice` 这个默认值。

## 七、扩容与已知限制

**这些是故意的、已记录的边界**（不是「还没发现的 bug」）：

### 7.1 `WORKERS=1`

默认单进程。`Dockerfile` 里 `ENV ALIGO__APP__WORKERS=1`，`config/base.yaml` 的 `app.workers` 也是 1。
**扩容到多 worker 前必须一并解决两件事，不能只调 worker 数**：

1. **调度器会重复触发**——框架的 `SchedulerManager` 用内存 jobstore，每个 worker 进程都会
   独立触发一次 cron，N 个 worker 就是 N 次重复执行。要扩就先把调度器拆成独立进程
   （除一个进程外其余都传 `enable_scheduler=False`）。
2. **连接池要算总账**——见下。

**单 worker 的容量信号，第一个出现在 `/readyz` 上。** 2026-10-03 用 `make concurrency`
在本机（4 核）压测，一边打并发对话、一边以 0.4 秒间隔采 `/readyz`：

| 场景 | `/readyz` 中位 | 最大 | 同时刻单项依赖耗时 |
| --- | --- | --- | --- |
| 空载 | 50 ms | — | postgres ~70 ms |
| 3 个用户同时在飞 | 103 ms | 472 ms | postgres 111 ms / redis 93 ms |
| 7 条 SSE 流同时在飞 | — | **2871 ms** | （那一次没采到分解） |

⚠️ 读这张表的重点在**最后一列**：依赖本身没有变慢 —— 容器内 `psql` 裸连
`SELECT 1` 只要 0.00–0.02 s，探针里的 postgres 检查在并发中仍是 ~110 ms。
可采到分解的那些样本里，涨的部分**全在检查之外**，即等事件循环调度。
所以单 worker 下被共享的瓶颈是**那一个事件循环**，不是数据库连接。

⚠️ 上限在哪：`/readyz` 每项检查 3 s（`CHECK_TIMEOUT_SECONDS`），compose 探针超时 10 s。
2871 ms 已经吃掉单项预算的 96%。一旦某项越过 3 s，`/readyz` 返回 503 ⇒ compose 把容器
标成 unhealthy ⇒ `depends_on: service_healthy` 的下游跟着受影响。
**扩容的信号是这个数字，不是「请求开始报错」** —— 后者要等到事件循环彻底排满才出现。

⚠️ 测这三行时本机负载平均值是 **11.6（4 核）**（VS Code 渲染进程单独占满一核，
Docker Desktop 的虚拟机另占约 27%）。绝对数字会被这个负载放大，但**结论的方向不受影响**：
同一台机器、同一时段，依赖的裸耗时比探针里的耗时小两个数量级。

### 7.2 连接池账目

单 engine 峰值 = `pool_size + max_overflow` = `10 + 20` = **30** 条连接（`src/storage/engine.py`）。
业务库是**自己的一套 engine**（`build_business_engine`），与框架的引擎分开，两者 `pool_size` 互不挤占：

```text
单进程峰值 = 30（框架 engine）+ 30（业务 engine）= 60 条
4 个 worker = 240 条
PostgreSQL 默认 max_connections = 100   → 直接打爆
```

所以要扩 worker，**同时**要调小 `ALIGO__DB__POOL_SIZE` / `ALIGO__DB__MAX_OVERFLOW`，或抬高 PG 的 `max_connections`。

### 7.3 三种「等数据库」的等待，各有各的闸门

「数据库慢」在用户那里是同一个现象（请求不返回），成因却有三层，而且**互相不能替代** ——
只设一条闸门时，另外两层仍然无界。三条都在 `src/storage/engine.py` 里装配：

| 等待 | 闸门 | 配置键 | 默认 | 挡的是什么 |
| --- | --- | --- | --- | --- |
| 等一条**空闲连接** | `pool_timeout` | `ALIGO__DB__POOL_TIMEOUT_SECONDS` | **5.0s** | 池被占满：慢查询堆积、连接泄漏、PG 侧 `max_connections` 打满。**数据库本身很快也会卡在这里** |
| **建一条新连接** | `connect_args["timeout"]` | 无独立键，= `statement_timeout` + 5s 余量 | 15.0s | 建连本身挂住：网络黑洞、TCP 半开、PG 在听但迟迟不完成握手。**`pool_timeout` 盖不到这一段** —— 新建连接发生在「计时等待」之外 |
| 一条**语句执行太久** | `statement_timeout` | `ALIGO__DB__STATEMENT_TIMEOUT_SECONDS` | **10.0s** | 慢查询、锁等待。由 **PostgreSQL 自己**执行 —— 杀掉查询并把连接**干净地**还回池里 |
| 连上之后**没回应** | `command_timeout` | 无独立键，= `statement_timeout` + 5s 余量 | 15.0s | 网络黑洞、TCP 半开、PG 进程被 `SIGSTOP`。此时服务端的定时器也在同一个进程里，帮不上忙 |

⚠️ 第 2 行和第 4 行是**两件事**，别合并：`connect_args["timeout"]` 管**建连阶段**
（asyncpg 默认 **60s**，不设就是留一个一分钟的黑洞），`command_timeout` 管**连上之后
每条语句的往返**。两者都以 `statement_timeout` 为基准 + 5s，
所以「服务端先动手、客户端后放弃」的方向在**两段**上一致。

⚠️ **`pool_timeout` 的默认 30s 太长**（SQLAlchemy 的默认值，本项目改成 5s）：
数据库其实很快、只是池满了的时候，30s 会让**每个**请求都卡半分钟才报错。

⚠️ **客户端的预算必须大于服务端**，且要大出一个余量（`_COMMAND_TIMEOUT_MARGIN_SECONDS = 5.0`）。
方向反过来（客户端先超时）会让 asyncpg 在 PG 还没执行完杀掉动作时就放弃，
连接带着一条**仍在运行**的查询回到池里 —— 下一个拿到它的请求要么被拖慢，
要么直接踩上 `another command is already in progress`。

⚠️ `statement_timeout` 换算成毫秒时用的是 `max(1, round(...))`，不是直接截断：
填 `0.0005` 秒时截断会得到字符串 `"0"`，而 PG 把 `statement_timeout = 0` 读作
**不限制** —— 一个手滑的配置会静默地把这道闸门**彻底拆掉**，比填错更危险。

⚠️ 四条**都只在 PostgreSQL 生效**。`server_settings` / `command_timeout` 是 asyncpg 专有参数，
换成 psycopg / aiopg 会以「未知连接参数」直接抛在 `create_async_engine` 上（连引擎都建不出来）；
sqlite（`make test` 的内存库）既没有连接池也没有语句超时概念，传参会直接建不出引擎。
所以 `storage_engine_kwargs` 按方言分流 —— 非 asyncpg 时**不猜**等价参数，只留一条 `WARNING`。
猜错是启动期崩溃，不猜只是少一层护栏，而少一层护栏会在日志里留下可查的事实。

> `.env.example` 里这两个键**不接受 0**：PostgreSQL 的 `statement_timeout = 0` 意思是**不限制**，
> 而不是「立刻超时」—— 留一个「填 0 关掉」的口子只会让人以为自己设了护栏。

**怎么确认它在真实 PG 上生效**（本机跑过，输出如下）：

```bash
docker exec -e ALIGO__DB__STATEMENT_TIMEOUT_SECONDS=0.5 aligo-app python -c "..."
# dialect = postgresql | pool_timeout = 5.0
# server statement_timeout = 500ms
# cancelled as expected: DBAPIError ... QueryCanceledErr
```

即：把预算压到 0.5s 后，`SELECT pg_sleep(2)` 被 PG 以 `QueryCanceledError` 取消 ——
说明服务端那道闸门是真的在执行，不是只写在连接参数里。

### 7.4 其他硬约束

- **消息总线必须是 `RedisMessageBus`**——`InMemoryMessageBus` 在多副本下会让 SSE 事件收不到
  （框架自己的注释里就这么写着）。测试里用内存总线只是因为测试是单进程且不测跨副本。
- **`download_secret` 在多副本下必须显式设为固定值**——否则每个进程随机生成，
  LB 后面的签名 token 会失效（症状是「点下载随机失败、刷新一下可能又好了」）。
  单实例 + `WORKERS=1` 时留空（随机）反而是正确的。
- **`auto_migrate` 恒为 `False`**——框架明确警告多副本下它不安全。
- **前端与后端同源**（产物托管在 `/` 上，见 `docs/02-技术架构.md` 第 3.4 节）。
  两个后果：① 重新构建前端后**不必重启后端**，但产物目录若是通过卷挂载进去的，
  要确认容器里看到的是新文件；② 前端的 `/mcp`、`/skill` 两个路由与框架的
  `GET /mcp`、`GET /skill` 同路径，直接刷新这两个地址会看到接口 JSON（点击导航正常）。
  若要彻底消除，把前端放到独立域名/端口，并在 SetupPage 里填后端地址。

### 7.5 `hide_parameters`：凡是新建 engine 就必须带上的安全约束

`storage_engine_kwargs()` 里的 `"hide_parameters": True`（`src/storage/engine.py:125`）
**不是日志洁癖，是安全约束**，因为 `credentials.data` 里装的就是运营者的真 key（系统凭据）。
SQLAlchemy 默认把**绑定参数**渲染进异常文本，而播种那条 INSERT 一旦失败，
`logger.exception` 会把 key 原样落进容器日志、日志采集系统，以及任何一次 `make logs` 的
终端回滚缓冲。打开它之后同样的异常仍然抛出（类型、语句、SQLSTATE 都在），只是参数位置变成
`(...)`。它顺带管住 `echo=true`：echo 打印的是**渲染后**的语句、同样带参数——只开 echo
不设它，「调试一下」就等于把 key 打到 stdout（`src/storage/engine.py:120-124`；不开/开的
对照输出见 `docs/02-技术架构.md` 第 5.4 节）。

**硬约束：任何新建 engine 的地方都必须经由 `storage_engine_kwargs()` 取参**——框架 storage 的
`engine_kwargs=...`（`src/server/app.py:190-195`）、业务 engine（`src/storage/engine.py:200`），
以及**将来 `scripts/` 下的离线脚本**（今天 `scripts/seed_data.py:1279-1281` 走 `build_storage`，
自动带上）。自己拉一个裸 `create_async_engine(...)`，就绕过了这道保护。自检：

```bash
grep -rn "create_async_engine(" src scripts --include='*.py'
```

今天应当只命中两处，**两处都带这道开关**：

- `src/storage/engine.py:200`——业务 engine，参数来自 `storage_engine_kwargs()`（`**` 解包）；
- `src/server/probes.py:213`——`/readyz` 的**短命探针** engine（`NullPool`、`echo=False`、
  只跑无绑定参数的 `SELECT 1`）。它**刻意不复用** `storage_engine_kwargs()`——探针要的池参数
  与业务引擎正好相反——所以它显式写上 `hide_parameters=True`（`src/server/probes.py:226`）。
  ⚠️ 这一处曾经**漏掉过**，是审计时找出来的：漏掉的那个 engine 只会在「恰好执行一条带绑定
  参数的语句并抛异常」时才显形，而那可能是一年后某个人在探针里加了个带租户参数的查询 ——
  那时密钥会明文进 `/readyz` 响应体。所以下面那条契约用例就是为它而加的。

行为上由**四条**用例钉住（都在 `tests/test_storage_engine.py`）：

| 用例 | 钉住的是 |
| --- | --- |
| `:304` `test_hide_parameters_is_on_for_every_dialect` | 两种方言分支都打开开关（sqlite 分支会提前 return，容易漏） |
| `:316` `test_an_engine_built_from_these_kwargs_never_prints_bind_values` | 用真实引擎跑注定失败的语句，密钥**不在**异常文本里（**自带反向证据**） |
| `:359` `test_the_framework_storage_honours_our_engine_kwargs` | 框架**真的**把 `engine_kwargs` 交给了引擎 —— 这是链条上最容易断、最没人看的一环 |
| `:475` `test_every_engine_call_site_disables_parameter_rendering` | **静态契约**：扫描 `src/` 与 `scripts/` 下所有 engine 构造点，没带开关的当场红 |

最后一条是这里唯一能防「**将来**新加一个 engine 忘了开关」的 —— 前三条都只覆盖**已经存在**的
调用点。它的扫描范围刻意不含 `tests/`：那里有一个 engine 必须**不带**这个开关
（`tests/test_storage_engine.py:340` 附近的反向证据），把它纳进来只会逼人开豁免。

| 症状 | 先看什么 | 常见原因 |
| --- | --- | --- |
| 容器 `Restarting (1)` 循环 | `make logs` 里的 `extra_forbidden` | 某个 `ALIGO__` 键 schema 不认识（多办是 `ALIGO__IMAGE_REGISTRY` 进了 `.env`，见 3.3） |
| `make up` 挂住不返回 | 加 `WAIT_TIMEOUT`、看未就绪服务清单 | Redis 密码没注入 ⇒ SchedulerManager 卡在等订阅 |

| trace 开着但 Langfuse 空 | 确认四个装配条件都满足：`trace_exporter=otlp`、`otlp_endpoint` 非空、Langfuse 的 public/secret key 都非空（见 4.4） | 条件没显式满足时框架的 `TracingMiddleware` **静默短路**；缺密钥时代码主动不装配并打 warning |
| `/metrics` 404 | 看 `ALIGO__OBSERVABILITY__METRICS_ENABLED` | 指标未启用（条件式路由） |
| 检索「找不到刚建的知识库」 | 确认 `storage` 只造了一个实例 | KB 记录写进 A、对话链从 B 读（见 `docs/03` 第二节第 4 步） |
| Milvus 里没有业务集合（或日志里出现 `collection not found`） | 跑 `make milvus_init`（建**两个**：政策库 + 长期记忆） | 首启不自动建集合，见**第九节**；记忆那条读路径漏跑时会每轮打一条 ERROR |
| 同一句话在容器与本机行为不同 | 两边各跑 `python -c "import reme,agentscope; print(reme.__version__, agentscope.__version__)"` 对比 | 两边装的是**同一份钉版清单**（`requirements.txt`），版本上不该有差异 —— 先怀疑数据/配置差异，再怀疑代码 |
| 配好了密钥，浏览器里却一个模型都没有 / 发送按钮是灰的 | `curl /api/v1/default-model` 看 `mode` 与 `hint` | 见 **8.1**；探针与 SPA 都不会报这个病 |
| 登录进去了，但**输入框是灰的、点不动** | `curl -H 'X-User-ID: <用户>' /agent/` 看 `total` | `total: 0` ⇒ 一个智能体都没有，跑 `make provision-agent`，见 **8.3**；否则是缺模型，见 **8.1** |
| 客户端拿到 403，响应体含「该身份为系统保留身份」 | 指标 `aligo_auth_failures_total{reason="reserved_identity"}` | 有人/某脚本在声明 `aligo-system`，见 **8.2**（安全事件信号） |

排障时的一条通则：**先确认两边跑的是不是同一份代码与同一组版本**。自 2026-10-04（框架改 pip 包安装，
见 `requirements.txt` 第 零 节）起，本机与容器装的是**同一份钉版清单**，版本上已不存在「本地一套、
容器另一套」的错位；一个「本机测试全绿、容器里行为不同」的 bug，先怀疑数据与配置差异。

### 8.1 配好了密钥，浏览器里却一个模型都没有 / 发送按钮是灰的

**症状**：`.env` 里的密钥肉眼可见，容器也活着，但浏览器里模型选择器是空的、「发送」按钮灰着
（前端可用模型由 `GET /credential/` × `GET /model/?provider=` 拼出，零凭据 ⇒ 分组为空 ⇒
`selectedModel === null` ⇒ `disabled`，`web/frontend/src/pages/chat/ChatViewport.tsx:852`）。
这是「服务端有能力调模型」与「用户能用上模型」是两件事的经典形态——探针与 SPA 都不会报它。

**判据**（先拿机器可读的答案，不要靠猜；响应体不含任何密钥，四种模式皆然，可安全贴进工单）：

```bash
curl -s -H 'X-User-ID: <该用户>' http://localhost:8000/api/v1/default-model | python3 -m json.tool
```

读 `mode`（四种模式一律 **200**，`src/server/routers/_default_model.py:84-88`）与 `hint`
（四种文案是常量，`src/llm/degradation.py:121-138`）：

| mode | 含义 | 下一步 |
| --- | --- | --- |
| `mock` | 零密钥降级在工作，`chat_model_config` 可直接建会话 | 服务端没问题；浏览器仍空就刷新页面再看 |
| `configured` | 用户**自己**有凭据，服务端不替他选模型 | 去选择器里挑一个。**这不是故障**（smoke 有专门文案，`scripts/smoke.py:630-639`） |
| `shared` | 系统凭据对他可用，配置直接可用 | 同 `mock`：服务端没问题 |
| `missing` | 什么都没有 | 按下面的 `hint` 前缀分流 |

`mode=missing` 时，`hint` 本身就带成因，按前缀三选一：

1. 以「零密钥降级凭据写入失败（<异常类名>）」开头（`src/llm/degradation.py:251-258`）——
   零密钥、降级开着，但 Mock 凭据那条 INSERT 写不进去。查数据库连通性；中间件对同一失败
   只打**一次** warning「零密钥降级凭据播种失败」（`src/server/middleware/mock_credential.py:142-152`），
   后续请求会自己重试。
2. 以「读取凭据列表失败（<异常类名>）」开头（`src/llm/degradation.py:268-275`）——存储读失败。
3. 就是 `HINT_MISSING` 的原文（「未检测到可用的模型凭据，且零密钥降级已关闭…」，
   `src/llm/degradation.py:134-138`）——无 Mock（开关关着或已有真 key）且无共享。四种成因：

   - **有密钥但系统凭据播种失败**（最常见）：lifespan 只把它记成一条 **ERROR + 栈**
     （「系统凭据播种失败…」，`src/server/app.py:407-414`），**不阻断启动**——这正是它难发现的
     原因：`/readyz` 照常 200，探针**不会变红**，只能靠这条日志：

     ```bash
     docker compose --profile core logs --tail=500 app | grep "系统凭据播种失败"
     ```

     或直接查库（表名/列名来自框架
     `agentscope/app/storage/_sql/_tables.py:108-119`；
     `aligo` / `aligo` 是 `.env.example` 的默认 `POSTGRES_USER` / `POSTGRES_DB`，改过就换成你的值）：

     ```bash
     docker compose --profile core exec postgres \
       psql -U aligo -d aligo -c \
       "SELECT id, user_id FROM credentials WHERE id = 'aligo-system-model';"
     ```

     没有这一行 = 播种没成功（或被人删了，重启即恢复）。处置：按栈修因（数据库连通性/权限）→
     重启 app 让 lifespan 重新播种（`make up`，或环境变量没变时
     `docker compose --profile core restart app`）→ 再 curl 应得到 `mode=shared`。
     ⚠️ 共享是否生效以 `mode` 为准，判据走的是 `policy.list_accessible`
     （`src/llm/system_credential.py:208-223`），不是「查一下记录在不在」——记录在、但策略的
     `seeded` 没置位时用户仍然用不了（`src/llm/system_credential.py:307`），端点会**如实**
     回答 `missing`，不会出现「说能用、点了报 404」。
   - **零密钥且降级被显式关掉**：这是**矛盾配置**，服务在启动期就会崩——模块级
     `app = create_root_app()`（`src/server/app.py:1069-1072`）在装配智能体时会调
     `build_chat_model` → `build_credential` 抛 `ValueError`（`src/llm/factory.py:215-222`）。
     所以「能被访问到的服务 + 零密钥」基本可以排除这一条。
   - **策略查询本身抛异常**：`resolve_shared_model` 失败时端点**按「未配置」处理**
     （`shared = None`，`src/llm/degradation.py:301-302`）——所以「共享判据为真、查询却炸了」
     与「根本没有共享凭据」在这个端点上**是同一个响应** `missing`。区别只在日志里那条
     ERROR + 栈「查询系统凭据共享失败，按「未配置」处理。」。这条的设计理由与上面两条
     「吞异常」**不同**：会话链路自己也会走策略，所以策略坏掉时对话本来就会失败，
     端点再抛 500 只会让人去查这个端点本身（方向完全错了）。
   - **确实没配密钥**：默认 `use_mock_when_no_key: true`（`config/base.yaml:293`）时应该得到
     `mode=mock`；得到 `missing` 说明降级路径本身出了问题——回到上面第 1、2 条看前缀。
     ⚠️ 顺带一个易误判：`has_api_key` 只做 `strip()` 非空判断（`src/llm/factory.py:103-117`），
     `.env` 里的占位符（如 `sk-not-a-real-key`）会被当成真 key ⇒ 得到 `mode=shared`、按钮不灰，
     但真实模型调用会被上游拒绝——那是另一种症状，不要再往「没有模型」上排查。

**处置**：按上面的分支修因；修复后重跑 curl 确认 `mode` 落在 `mock`/`shared`（或 `configured`），
再让用户刷新页面。

### 8.2 403 + 「保留身份」：不是误报，是一次安全事件信号

**症状**：客户端拿到 403，响应体是 `{"detail": "该身份为系统保留身份，客户端不得声明。"}`
（`src/server/middleware/auth.py:571-576`）；或日志里出现一条 WARNING 级访问日志
`… → 403（…ms）`（`src/server/middleware/http_trace.py:147-161`）。它意味着**有人（或某个脚本）
在请求里声明了 `X-User-ID: aligo-system`**，或持有一个 `sub=aligo-system` 的 JWT，或在
`require_user_header=false` 下带了同名请求头。

**判据**：

```bash
curl -s localhost:8000/metrics | grep 'aligo_auth_failures_total.*reserved_identity'
```

计数器非零即坐实。⚠️ 这条拒绝**不写专门的日志**——中间件只记指标
（`src/server/middleware/auth.py:595`），你看到的访问日志 403 是通用的、别的 403 也长这样；
唯一权威的判据是指标 `aligo_auth_failures_total{reason="reserved_identity"}`
（`src/observability/metrics.py:119-124`；reason 常量见 `src/server/middleware/auth.py:146`）。

为什么要拦（一句话背景）：`aligo-system` 名下有一条带运营者真 key 的共享凭据，而框架的规则是
「属主读自己的凭据是明文、且可编辑可删除」——若客户端能声明这个身份，一次 `GET /credential/`
就能抄走 key 明文、一次 `DELETE` 就能让所有人当场没有模型。所以**三条通道**（直连头 / JWT 的
`sub` / 匿名通道）全部拒绝（`src/server/middleware/auth.py:391-397`、`:461-468`、`:360-363`），
并且在框架看到请求**之前**返回 403——这条路径**不可能**泄露密钥。403 而不是 401 也是刻意的：
401 会让客户端去走登录流程，而没有任何登录能变成系统身份（`src/server/middleware/auth.py:551-556`）。
⚠️ 判据是**精确比较**（调用方先 `strip()`）：`ALIGO-SYSTEM` 不是保留身份——它在框架眼里本就是
另一个用户，读到的凭据照样是打码的（`src/llm/identity.py:66-88`）。

**处置**：

1. **先找来源。** 容器访问日志**不带客户端 IP**，用同一请求的 `trace_id`（每行日志都有）在
   日志里找上下文；IP/来源方要去入口层（反向代理 / 网关 / LB）的访问日志里查。若指标只是一次性
   小尖峰，多半是某个内部脚本/健康检查写了这个头——在仓库、CI、运维脚本里搜 `aligo-system`
   确认并修掉那个脚本。
2. **按安全事件对待。** 这是有人在**试探系统身份**（或配置写错），不是普通客户端错误；
   持续速率上升说明是扫描/探测而不是误配。⚠️ 这条拒绝发生在限流**之前**（Auth 在 RateLimit
   外层，执行顺序见 `src/server/middleware/mock_credential.py:28-32`），本应用的限流帮不上忙——
   持续探测要在入口层封禁。
3. **不要「修复」它。** 不要把 403 当误报去放宽规则；不要给 `aligo-system` 签发 JWT；
   也不要靠改名了事（改名不解决「有人在试探」，还丢掉指标上的可见性）。自己用 curl 发一次
   以验证规则仍在生效，是**预期**行为，验证完即可。
4. ⚠️ 反向检查：若你发了 `X-User-ID: aligo-system` 却拿到 **200**、且指标里没有
   `reserved_identity` 时序，说明规则被改坏了（该计数掉到 0，而其它一切看起来完全正常）——
   按 `src/llm/identity.py:63-88` 检查保留身份集合与 `is_reserved_user_id` 的调用点。

### 8.3 输入框是灰的、点不动 —— 与 8.1 **不是**同一回事

**症状**：登录进了 `/chat`，输入框是灰的、`opacity: 0.5`、点上去没有任何反应
（Playwright 复现时表现为 `locator.click` 超时）。页面上写着「请先选择一个智能体。」
（`web/frontend/src/i18n/locales/zh.json:233`），而侧边栏的智能体下拉里**一个都没有**。

**它和 8.1 的区别**——两种病的外层症状一模一样（都是灰输入框），成因完全不同：

| | 8.1 | 8.3（本节） |
| --- | --- | --- |
| 缺什么 | 用户没有**可用模型** | 用户没有**智能体**（进而没有会话，进而没有模型） |
| 判据 | `GET /api/v1/default-model` 的 `mode` | `GET /agent/` 的 `total` |
| 修复 | 按 `mode` 分支处置 | `make provision-agent PROVISION_USER=<该用户>` |

**为什么缺智能体会让输入框变灰**（一条链，已核实）：

```text
`web/frontend/src/pages/chat/ChatViewport.tsx:852`  disabled={selectedModel === null}
        ↑ selectedModel 来自「当前会话的 chat_model_config」
        ↑ 会话必须挂在智能体下
        ⇒ 没有智能体 ⇒ 没有会话 ⇒ 没有模型 ⇒ 输入框永远禁用
```

**判据**（一条命令，响应体不含任何密钥，可安全贴进工单）：

```bash
curl -s -H 'X-User-ID: <该用户>' http://localhost:8000/agent/ | python3 -m json.tool
```

`"total": 0` 就是本节这个病。**处置**：

```bash
make provision-agent PROVISION_USER=<该用户>
```

脚本建完会打印该智能体的 id 与会话 id；让用户刷新页面即可输入。

> ⚠️ 三个容易踩空的地方：
>
> 1. **光有智能体还不够**——前端在「有智能体、零会话」时**不会**自动建会话，
>    输入框仍然是灰的（实测：此时页面文案变成「创建会话开始对话。」）。
>    脚本默认会补一条会话，就是为了消掉这一步。
> 2. **前端不会替你在任何地方提示这三步**：全新部署下用户看到的只有一句
>    「请先选择一个智能体。」和一个空下拉框。这正是本脚本存在的理由。
> 3. **身份是大小写敏感的**——`alice` 与 `Alice` 是**两个互不相通的工作区**
>    （身份只做 `strip()`，从不 `lower()`：`src/server/middleware/auth.py:360`）。
>    实测：本机库里同时存在 `alice`（有 `main_plan` + 1 条会话）与
>    `Alice`（另有一个独立的 `main_plan` + 1 条会话），两者的智能体 id 完全不同。
>    所以「我明明预置过了，怎么还是灰的」很可能是**登录时首字母大写了**——
>    这时候 `make provision-agent PROVISION_USER=Alice` 也救不了 `alice`，
>    它补的是另一个工作区。先确认浏览器里 `localStorage.username` 与预置时用的是同一个字符串。

## 九、Milvus 首次启动**不会**创建业务集合

这一节专门讲一件在真实部署里最先撞上的事，也是 `Makefile` 的 `WAIT_TIMEOUT` 注释点名要看的地方。

### 9.1 事实

**Milvus 容器首次启动只保证 Milvus 自身可用，不会创建本项目要用的业务集合。**
也就是说：`make up` 成功、`/readyz` 全绿、Milvus 的 `/healthz` 也返回 200——
但此时 `{milvus.collection}`（`config/base.yaml:190` 的基线是 `aligo_travel_policy`；
`config/dev.yaml:24` 与 `.env.example:163` 覆盖为 `aligo_travel_policy_dev`，
`test` 档是 `aligo_travel_policy_test`、`prod` 档回到基线名）以及派生的
`{milvus.collection}_memory` 在 Milvus 里**根本不存在**。

### 9.2 为什么不是自动的

- 集合的**参数**（维度 `milvus.dimension`、索引 `index_type`、度量 `metric_type`）必须以**配置为唯一真值**。
  若让 Milvus 容器或应用启动时顺手建一个，就会出现「集合参数以谁为准」的问题——
  两处都写 `create_collection`，迟早分叉。
- 建集合需要**显式、可回读核验**，而不是一个副作用。所以它是一个独立的 `make` 目标
  （`make milvus_init`），而不是启动流程里的一步。

### 9.3 对策

```bash
make milvus_init     # 幂等建两个集合（政策库 + 长期记忆）+ 回读核验；0 = 就绪，1 = 有集合不符或连不上
make seed_data       # 集合建好之后再灌数据（seed_data 不建集合）
```

⚠️ **部署顺序**：`make up` → `make milvus_init` → `make seed_data`。
跳过 `milvus_init` 直接 `seed_data` 会因为集合不存在而失败。

### 9.3.1 漏跑 `milvus_init` 会怎样（两条自愈路径，都不做核验）

值得单独说清楚，因为「漏跑」在真实部署里发生过（2026-10-03）：两个集合各自还有一条
**惰性自愈**的路，但它们都**不替代**本目标：

- **政策库**：框架的 `KnowledgeBase.search()` 每次先 `ensure_collection()`——
  问一句 `has_collection`，没有就 `create_collection`（见 `src/knowledge/guard.py` 的
  「三条设计约束」一节）。所以漏跑时，第一次检索会把集合顺手建出来。
- **长期记忆**：`SemanticMemory.remember` 在写入前幂等地 `create_collection`
  （2026-10-03 修复；此前无人建这个集合，「记住这个」直接失败）。
  ⚠️ **读路径不建集合**——每轮对话都跑一次建集合 RPC 是白花的，
  而读失败本来就降级成「没有记忆」；漏跑的代价是每轮对话各一条
  `collection not found` 的 ERROR 级日志（pymilvus 自己打的）。

**两条自愈都不做的事**：回读核验。集合按「建它的那一刻」的参数定形，
而自愈路径建出来的集合**没有任何人证明它**维度/索引/度量与配置一致——
那正是本目标存在的理由（见 6.2）。

### 9.4 与 `WAIT_TIMEOUT` 的关系

Milvus 冷启动最慢（其自身 `start_period` 为 90s，且要连 etcd 与 MinIO 初始化元数据），
叠加镜像构建耗时，`make up` 的等待预算要留足——这正是 `WAIT_TIMEOUT` 默认取 480 的原因。
**注意**：`WAIT_TIMEOUT` 只保证 Milvus **进程**健康，**不保证业务集合已建**——
后者只能靠 `make milvus_init`。

## 十、Milvus 卡死或崩溃时的行为（检索护栏）

第九节讲的是「Milvus 还没建集合」；这一节讲的是**Milvus 活着但卡住、或者干脆崩了**时，
系统会怎么表现、怎么看见、怎么恢复。内容全部来自一次真实故障（2026-10-03），不是推演。

### 10.1 故障经过（实测）

在本机 4 vCPU / 3.82 GiB 的 Docker VM 上跑满 tracing 档（12 容器）时，宿主负载冲高，
Milvus standalone 开始丢 etcd 租约，日志顺序是：

```text
Slow etcd operation save                      (8.194975168s)
clock offset is huge, check network latency and clock skew   (jet-lag=8.195225295s)
can not pull configs: context deadline exceeded
confirm the lease is expired, the session is expired without activing closing
```

随后进程先后以 **exit 80** 与 **exit 134（SIGABRT，日志里带 Go goroutine dump）** 退出。
触发条件是**宿主资源不足**（当时 4 核负载 64~77，容器内存限额合计约 6.0 GiB > VM 的 3.82 GiB），
不是配置错误。

**当时的后果被放大了两次**：

1. `MilvusLiteStore.search` 是 `await asyncio.to_thread(client.search, ...)`，**没有任何超时**
   （`pymilvus` 把 `timeout=None` 原样交给 gRPC）⇒ Milvus 卡住 = 对话请求**永不返回**。
   当时的表现是：`/healthz` 20 秒超时、`make smoke` 的端到端对话在 60 秒预算里只收到
   `REPLY_START`，应用日志停在那一句 embedding 之后，再无输出。
2. compose 里除 `app` 外的服务默认 `restart: no` ⇒ Milvus 崩了就**永远不回来**，
   后续每次冒烟都失败，且失败信息指向「Milvus 连不上」，与真正的原因（宿主资源）隔着两层。

### 10.2 现在的行为：读操作有截止时间，且会熔断

`src/knowledge/guard.py` 给向量库的**读**操作包了一层（装配点在 `build_vector_store`，
所以知识库检索与长期画像语义召回**都**自动带上）：

| 行为 | 取值 | 说明 |
| --- | --- | --- |
| 单次读超时 | **5s**（默认） | 配置项 `ALIGO__MILVUS__SEARCH_TIMEOUT_SECONDS`（`config/base.yaml` 的 `milvus.search_timeout_seconds`，必须 > 0 且 ≤ 120） |
| 熔断阈值 | 连续 **3** 次下游失败 | 超时与 pymilvus 异常算失败；**调用方自己的错误不算**（服务端标了 `is_input_error` 的 pymilvus 异常同样不算，否则熔断器会指错方向） |
| 熔断冷却 | **30s** | 冷却后放行**一个**探针，成功则闭合，失败则继续开路；探针若被取消（用户点了「停止生成」），名额会**归还**，不会把熔断器卡在半开态 |
| 覆盖范围 | `search` / `list_documents` / `list_chunks` / `has_collection` / `create_collection` | **`insert` / `delete` 刻意不受限**，判据是「非幂等写不静默放弃」。⚠️ `create_collection` 虽然名字像写操作，却**在**名单里 —— 它在检索路径上（集合缺失时 `ensure_collection()` 会调它），因此 `POST /knowledge_bases` 这条显式建集合的路径**也是**有界的 |
| 建连预热 | 与读操作同一个超时预算 | `get_client()` 会被移到**工作线程**里调用（它默认在事件循环上同步建连，会把整个进程按住，连超时回调都排不上） |

⚠️ `has_collection` 看着不像读操作，但它在**检索路径**上：框架的
`KnowledgeBase.search()` 每次都先经 `ensure_collection()` 问它
（`agentscope/rag/_knowledge.py:179`），卡住它与卡住 `search` 对使用者完全等价 ——
所以它在覆盖范围内，不是漏网之鱼。

**向量化那一侧另有护栏**（同一段检索路径的**前半段**）：检索是「先向量化、再查库」，
而向量模型的调用在框架里是无界的 —— 云端档是同步 HTTP 丢进线程池
（`agentscope/embedding/_dashscope/_model.py:371`），本地档是 ONNX 推理排队。
`src/web_embedding/bounded.py` 给**每一档**都套上调用截止时间：

| 行为 | 取值 | 说明 |
| --- | --- | --- |
| 单次向量化超时 | **30s**（默认） | 配置项 `ALIGO__EMBEDDING__TIMEOUT_SECONDS`，必须 > 0 且 ≤ 300。比检索超时宽松一档：向量化是外网 + 批量调用，正常就该慢一些 |
| 覆盖范围 | 三档**全部**（dashscope / local / mock），以及**框架侧**构造的那些 | 框架的 KB 管理器走 `CredentialFactory` 自己造向量模型（`src/knowledge/manager.py`），不经过我们的降级链 —— 那里也**显式**套了一层 |
| 超时异常 | `EmbeddingCallTimeout`（继承 `TimeoutError`） | 上层宽口径的 `except Exception` 照常降级；**内层的真实错误（缺 key / 模型下线 / 维度不符）原样透出**，不被包装成超时 |
| 与读护栏的关系 | 两段**各自**有界 | 向量化卡住时向量库熔断器**不会**开路（那次查询压根还没发出去）；反过来也一样。所以两处都要有，缺一段就仍会假死 |

**重排那一侧也有护栏**（同一段检索路径的**第三段**，只在
`ALIGO__RERANK__ENABLED=true` 时存在）：候选段落的排序是**再一次模型调用**
（`RAGMiddleware.on_reasoning` → `_rerank_results`），它不经过
`on_model_call`，因此 `ModelTimeoutMiddleware` 管不到它：

| 行为 | 取值 | 说明 |
| --- | --- | --- |
| 单次重排超时 | **`ALIGO__LLM__TIMEOUT_SECONDS`**（默认 60s） | 刻意复用主对话模型的单次调用预算，不新增配置键：重排是「为了答得更好」的中间步骤，比一次正常模型调用还慢就不值得等 |
| 覆盖范围 | 只覆盖重排那一次调用 | `src/llm/bounded.py` 的 `BoundedChatModel` 包住 `generate_structured_output` **整次**调用（含框架内部的「策略阶梯 + 重试」），而不是内部某一次 HTTP |
| 超时异常 | `ChatCallTimeout`（继承 `TimeoutError`） | 框架的 `except Exception` 会接住它并**退回向量序**（`agentscope/middleware/_rag.py:439`）—— 用户拿到的是「这一轮没重排」，不是「检索失败」 |
| 为什么不是 `asyncio.wait_for` | 框架的对话模型基类**吞掉** `CancelledError` | 与 `ModelTimeoutMiddleware` 同一个坑：`wait_for` 靠取消判定超时，而取消被优雅接住 ⇒ 超时判定永远不成立。这里是**按钟判断** |

⚠️ 重排的失败在用户看来与「重排生效但排序恰好没变」**完全一样**。
所以 `ALIGO__RERANK__ENABLED=true` 之后，务必确认 `ALIGO__RERANK__MODEL`
填的是**对话模型名**（`qwen-plus` 这类）而不是专用重排模型名
（`qwen3-rerank` / `gte-rerank`）—— 本框架没有重排模型类，
`rerank_model` 收的就是一个 `ChatModelBase`，见 `.env.example` 的「五·C」节。

超时后调用方拿到的是 `VectorSearchTimeout`（继承内置 `TimeoutError`），
上层已有的降级逻辑照常生效 —— 用户看到的是「这一轮没查到差旅政策」，
**对话本身继续**，不是整个服务假死。

⚠️ 五条必须知道的边界：

- **超时不会杀死底层线程，只压住它涨得多快。** `asyncio.wait_for` 取消的是
  `to_thread` 的 await；线程里那个 pymilvus 调用仍在跑（Python 无法中断线程）。
  所以「遗留线程」是这种护栏**固有**的代价，只能控速、压不到零。三层各管一段：
  **闸门**（`src/knowledge/guard.py` 的 `_gate()`，同时在飞 ≤ 4）管**并发**；
  **熔断器**管**持续**——稳态下约每 30 秒一个；**超时预算**管**单次**。
  ⚠️⚠️ **闸门限的是「同时在飞的协程」，不是线程数** —— 这两件事很容易被
  当成一件（这里就写错过一次，原文说「一次突发最多遗留 4 个线程」，不成立）。
  原因：超时会把名额**归还**，而那时线程还在下游卡着，于是排在闸门后面、
  自己 deadline 还没到的请求立刻又占满名额、再起 4 个卡死线程。持续故障下
  线程就是这样一批批涨上去的，闸门压缩的是**涨的速率**。
  为什么不能在超时时扣住名额直到线程结束：那样 Milvus 长挂时名额永不归还，
  闸门会变成一道**永久关闭**的门，检索再也不会自动恢复 —— 比多遗留几个线程更坏。
  ⚠️ 由此，三段加起来仍**不是**「线程数有上界」：Milvus 持续挂几小时，遗留线程会以
  约 120 个/小时堆积，最终吃光默认执行器那 8 个工位（`min(32, CPU+4)`，本机 4 核），
  连本地 ONNX 向量化一起饿死 —— 此时向量化会**按时失败**而不是挂住，
  现象是「检索整体降级」而非「服务假死」。这是**已知且写在明面上的取舍**，
  不是被忘掉的缺口。
- **护栏不治病。** 它把影响面从「整个服务假死」缩到「检索功能降级」，
  但 Milvus 为什么卡住仍然要按 10.5 去查。
- **熔断器是全进程共享的一个实例**（知识库与长期记忆两个 store 共用），
  所以一场故障只需数够一次三次，不会被两个 store 各自计数而推迟熔断。
- **仍然无界的只剩 `insert` / `delete`。** `DELETE /knowledge_bases/{id}`
  （逐文档删）与上传文档的**写入**那一段（分块落库；向量化那一段另有
  `ALIGO__EMBEDDING__TIMEOUT_SECONDS`）都会在 Milvus 卡住时一直挂着。
  这是刻意的取舍：写**非幂等**，超时后我们并不知道对端到底写没写进去，
  悄悄放弃会把「失败」变成「不知道」；而读超时无非是少一次召回，代价可控。
  ⚠️ **不要按「名字像读还是像写」来推断覆盖范围** —— 本项目在这里写过一次
  错的文档，两处都改了：`create_collection` 名字像写，但它在检索路径上
  （集合缺失时 `KnowledgeBase.search()` 会经 `ensure_collection()` 调它），
  所以它在 `_GUARDED_OPERATIONS` 里，`POST /knowledge_bases`（显式建集合）
  走的是**同一个**被箍住的方法 —— 它**有界**（5s 超时 + 计入共享熔断器），
  不是「管理接口会一直挂着」。判据只有一条：
  **「会不会在检索路径上被调用」**。
  ⚠️ 被箍住之后，`ensure_collection` 的 `_collection_ready` 会停在 `False`，
  于是后续每次检索都重试一次 `create_collection` —— 这正是要的：
  让熔断器数得到账，连续失败后停止再发。
- **MCP 工具调用的超时由注册方自己填。** 框架的 `MCPClient` 有
  `execution_timeout`（`agentscope/mcp/_mcp_client.py:122`），默认 `None` = **无界**，
  本项目不代设默认值。卡住的后果是「那一次工具调用永不返回 ⇒ 该轮对话假死」，
  而上面的模型截止时间**管不到它**（卡的是工具，不是模型）。
  ⚠️ 不给工具调用统一加超时是刻意的：本项目自己的差旅工具里有下单/改签这类
  **非幂等**操作，超时后我们并不知道对端到底做没做成 —— 把「失败」变成「不知道」
  比多等一会儿更糟。MCP 那一侧由注册方按自己工具的性质决定。

### 10.3 怎么看见

1. **日志**（应用容器）：超时发生时是一条 `WARNING`，形如

   ```text
   向量库 search 超时（5.01s ≥ 上限 5.00s），本次检索降级为「无结果」；
   连续失败 1/3 次后将熔断 30s。
   ```

2. **`/readyz`** 的顶字段 `vector_store_breaker`（与 LLM 那个 `breaker` **平级**，
   不是嵌在 `extra` 里 —— `/readyz` 的响应里没有 `extra` 这个键）：

   ```json
   {
     "vector_store_breaker": {
       "name": "vector_store", "state": "closed", "consecutive_failures": 0,
       "failure_threshold": 3, "recovery_seconds": 30.0, "open_remaining_seconds": 0.0,
       "total_calls": 0, "total_failures": 0, "total_rejections": 0, "total_opens": 0
     }
   }
   ```

   > 上面是**健康时**的实测响应（原样抄自 `curl /readyz`）。故障时变的只是**取值**：
   > `state` 变 `open`、`consecutive_failures` 涨到 `failure_threshold`(3)、
   > `open_remaining_seconds` 开始倒数 —— 字段名与结构不变。
   > 字段清单由 `src/server/probes.py:494` 给出，可直接对着实测响应核对。
   > ⚠️ `failure_threshold` 是 **3**，与 LLM 那个熔断器的 **5** 不同，且这个 3 是
   > **代码常量**（`src/knowledge/guard.py:154` 的 `_FAILURE_THRESHOLD`），
   > 而 LLM 侧的 5 来自配置项 `llm.circuit_breaker_failure_threshold`（`config/base.yaml:347`）。
   > 取小的理由是不对称性：检索是**可选**能力，熔断早了（其实只是抖动）代价是多等一个
   > 冷却期再自动恢复，熔断晚了代价是每个请求都白等一整个超时。

   ⚠️ 这一项**不参与就绪判定**（与 `checks.milvus` 同一条原则）：检索熔断只影响
   「查差旅政策」，对话、订单、审批、鉴权都不经过它 —— 所以此时 `/readyz` 仍然
   是 **200 / `ready=true`**，这是刻意的，不是探针失灵。

3. **`/metrics`**：`aligo_model_breaker_state{name="vector_store"}`，`0=closed`、
   `1=half_open`、`2=open`（与模型熔断器**分开**的 label 值，可分别告警）。

### 10.4 模型调用也有截止时间（与检索那一套是**两套**护栏）

前面三节讲的是检索。**模型调用**是同一类故障的另一处（同样「不抛异常、也不返回」），
护栏在中间件链上：`ModelTimeoutMiddleware`（`src/llm/middleware.py`），
装配位置在熔断器**之内**、上下文注入**之外**（见 `build_middlewares_factory` 的文档）。

| 行为 | 取值 | 说明 |
| --- | --- | --- |
| 单次模型调用超时 | `ALIGO__LLM__TIMEOUT_SECONDS`（默认 **60s**，`config/base.yaml` 的 `llm.timeout_seconds`） | 同时喂给 SDK 客户端（`client_kwargs`）与中间件；中间件是**兜底**那一道 |
| 超时异常 | `ModelCallTimeout`（继承 `TimeoutError`） | 冒到熔断器后被记成一次**下游失败** —— 这正是「卡住几次之后熔断」的成因 |
| 覆盖范围 | 非流式**与**流式（逐分块计时） | 流式下超时指的是「**下一个分块**多久没来」，不是「整轮回复多久」—— 正常的慢回复不会被误杀 |
| 为什么要兜底 | 框架不传 `client_kwargs` | `agentscope/app/_service/_model.py:54-58` 构造模型时只给 credential/model/parameters ⇒ SDK 默认 600s × 自身重试 × 框架 4 轮 ≈ **2 小时** |

⚠️ **实现方式与常见的 `asyncio.wait_for` 不同**，而且**必须**不同：
框架的模型基类会**吞掉** `CancelledError`（`agentscope/model/_base.py:219-224` 非流式返回空响应、
`:283-288` 流式发一个最终块），而 `wait_for` 只在取消真的抛出来时才判定超时 ——
用它写出来的超时**永远不会触发**。所以这里改成**按钟判断**
（`asyncio.wait(..., timeout=)` + 超时后显式 `cancel()`），
并且有专门的用例用「吞掉取消的模型替身」钉住这一点。

> ⚠️ 与检索那套的分工：**模型**这一侧用按钟判断（框架吞取消），
> **向量模型**那一侧用 `wait_for`（框架的重试只捕获 `Exception`，取消能穿透）。
> 两处写法不同是刻意核验过的结果，不是不一致 —— 各自的证据在
> `src/llm/middleware.py` 与 `src/web_embedding/bounded.py` 的模块文档里。

### 10.5 恢复步骤

```bash
docker ps -a --filter "name=aligo-milvus"        # 看它是 Up 还是 Exited(80/134)
docker logs --tail 50 aligo-milvus                # 认准 10.1 的租约过期签名
docker stats --no-stream                          # 先看宿主是不是又被打满了
```

- **现在所有服务都写了 `restart: unless-stopped`**（`docker-compose.yaml` 文首有完整理由），
  所以宿主缓过来之后 Milvus 会**自己回来**，不需要人工 `docker start`。
  这也是把 `restart` 从默认的 `no` 改掉的直接原因 —— 一次宿主负载尖峰不该把整个栈
  变成需要人介入的状态。
- 若它**反复重启**：先降档，再排查。12 容器的 tracing 档在这台 3.82 GiB 的 VM 上
  本身就在超配运行；日常验证用 `make up`（6 容器），要 tracing 时用 `make up-tracing`
  并盯 `docker stats`。
- ⚠️ 不要靠「反复重启」掩盖问题。重启只保证「下游恢复后自己回来」，
  真正的判据是 10.3 的三处观测点回到 `closed`。
