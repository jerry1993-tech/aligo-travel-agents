```

   │  X-User-ID  或  Bearer JWT（由我们的 ASGI 中间件解析后注入 X-User-ID）
   ▼
┌──────────────────────────────────────────────────────────────────┐
│ src/server/app.py  ← 硬契约：模块级 app，uvicorn src.server.app:app   │
│                                                                  │
│   app = create_app(...)   ← 直接复用其返回值作为根应用，绝不 mount    │
│   ├ 内核自带：/chat/ /sessions/**(SSE) /agent /knowledge_bases      │
│   │           /mcp /schedule /workspace /hub  + HITL/权限/多租户     │
│   ├ 我们追加：/healthz  /readyz  /metrics                          │
│   ├ 我们追加：/api/v1/**   差旅业务域（用户/行程/订单/申请单/审批）      │
│   ├ 我们追加：中间件 TraceContext → HttpMetrics → Auth → RateLimit    │
│   │           （P3 再把灰度路由插进 Auth 之后）                       │
│   └ 最后：mount("/", StaticFiles(...))  托管前端产物（必须最后）       │
└──────────────────────────────────────────────────────────────────┘
   │                    │                   │
   ▼                    ▼                   ▼
PostgreSQL           Redis              Milvus
business schema      RedisMessageBus    单集合政策知识库
+ AgentScope 表      (SSE/锁/取消广播)   + 画像语义召回
```

> **与初稿的差异（P2 实测）**：原图写的是「TraceID → Auth → RateLimit」三个中间件，
> 实际落地是**四个** —— `HttpMetrics` 被插在 `TraceContext` 与 `Auth` 之间。
> 理由：请求计数与耗时直方图必须在**鉴权之前**开始计，否则 401 的流量在监控里不可见，
> 而那恰恰是最需要看见的一类流量。灰度路由（P3）排在 `Auth` 之后，
> 因为它需要已解析出的用户身份。

### 为什么"复用返回值"而不是 mount —— 一个已核实的致命陷阱

`create_app` 把 lifespan 挂在自己的 FastAPI 实例上（`app/_app.py:292`），而 **Starlette 的 `mount()` 不会触发子应用的 lifespan**（`starlette/routing.py:396-398` 只处理 http/websocket 两类路由，不处理 lifespan 的转发）。AgentScope 作者本人就在健康检查的 docstring 里把这件事写成了警告（`app/_router/_health.py:45-54`）。

若按官方 docstring 的 `root.mount("/agentscope", app)` 写（`app/_app.py:121-129`）：`chat_service` / `session_service` / `scheduler_manager` 全在 lifespan 里才写入 `app.state`（`app/_lifespan.py:58-199`），于是 `app/deps.py:83-92` 取 `app.state.chat_service` → **AttributeError → 所有业务端点 500**。附带地，前缀 mount 还会打断官方前端：`client.ts:70` 用 `new URL(path, baseUrl)` 而调用处传绝对路径（`session.ts:112`），前缀会被丢掉。

**对策**：`app = create_app(...)` 直接作根应用，再 `include_router` / `add_middleware` / 包一层 lifespan。三个好处：lifespan 天然执行；**无前缀问题**，官方前端填根地址即可直连；`StaticFiles` 最后 mount 到 `/` 不会遮蔽 API。

## 关键技术决策（三处纠正了初始设想）

### 1. Milvus：复用 `MilvusLiteStore`，不自建 store

初始设想"必须自建 `VectorStoreBase` 子类"是**错的**。证据：`MilvusLiteStore` 内部就是 `pymilvus.MilvusClient(uri=self._uri, ...)`（`_milvus_lite.py:78-84`），而判定"本地 Lite 模式"的函数是 `_is_local_db_uri`（`_milvus_lite.py:539-543`），对 `http://milvus:19530` 返回 **False**（因为以 `http://` 开头且不以 `.db` 结尾）⇒ 走**远端服务**分支。类名有误导性，实际可直接连 compose 的 Milvus。

**真正的缺口在集合模型**：硬契约要的是**单集合** `aligo_travel_policy_dev`，而框架唯一的 KB manager 是 `CollectionPerKbManager`（per-KB 一个集合）。→ 自建一个 `SingleCollectionKbManager(KnowledgeBaseManagerBase)`，把所有知识库放进契约指定的集合，用 `metadata_filter` 做租户/KB 隔离（`_vector_store.py:236-285` 明确要求 filter 下推到后端，这也是多租户的纵深防御）。这样 `ALIGO__MILVUS__COLLECTION` 不是死配置。

### 2. 模型构建：把 `build_chat_model` 接进 app 链路，不另开端点

**冲突**：硬契约要求 `src/llm/factory.py::build_chat_model` + 共享 `breaker.py`；但 `agentscope.app` 的聊天链路走的是**另一条路** —— `app/_service/_model.py:12-63` 从 storage 里的 credential 记录解析，经 `CredentialFactory.from_dict` 构造 `model_cls(credential=..., model=..., parameters=...)`。

**对策**（保留两条硬契约，同时吃到 app 链路的会话/流式/HITL 红利）：
- 用 `extra_credentials`（`app/_app.py:211-215`）注册自定义 Credential 类型，并让 `build_chat_model` 成为**统一的模型装配函数**（app 链路与离线脚本/评测共用）。
- 启动时从 `OPENAI_API_KEY` / `OPENAI_BASE_URL`（`.env.example:46-47`）**播种**一条 credential 记录，使 app 链路开箱即用。
- 熔断做成 **`on_model_call` 中间件**（`middleware/_base.py:213-236`）——它能包裹真实模型调用、计失败、open 时短路，且天然全体共享一个实例。
- **零密钥降级**：`build_chat_model` 在 `use_mock_when_no_key=true` 且 api_key 为空时返回 MockLLM；app 链路通过注册一个 Mock `ChatModelBase` 子类 + 对应 credential 兑现同样语义。

### 3. 业务库：独立 engine + 独立 alembic + 独立 `business` schema

AgentScope 的表名极其通用且**会撞车**：`sessions`、`messages`、`agents`、`credentials`、`schedules`、`teams`、`knowledge_bases`…（`app/storage/_sql/_tables.py`）。因此：
- 业务表全部落 **`business` schema**（`__table_args__ = {"schema": "business"}`），alembic `version_table_schema` 同。
- `scripts/postgres/init/*.sh` 里 `CREATE SCHEMA IF NOT EXISTS business;`。
- 我们自己的 `create_async_engine`，参数读 `ALIGO__DB__*`；AgentScope 侧用 `AsyncSQLAlchemyStorage(url=..., create_tables=cfg.db.create_tables, auto_migrate=False)`。
- **不碰框架私有 API**（`_session()` / `_Base` 都是下划线）。
- **连接池算总账**：`POOL_SIZE=10 + MAX_OVERFLOW=20` ⇒ 单 engine 峰值 30 连接，N 个 worker 就是 N×30。这是保持 `WORKERS=1` 的理由之一。
- `auto_migrate` 恒为 `False`（`_storage.py:137-142` 明确警告多副本不安全）。

### P2 · 会话 + 流式 + 鉴权（目标：一句话端到端流式返回）✅

原计划条目：

- 中间件链 **TraceID → Auth → RateLimit**（注意 Starlette `add_middleware` 是 `insert(0)`，**后加的先执行**，顺序要倒着写）
- 鉴权：JWT 作为 **ASGI 中间件解析后注入 `X-User-ID`**，而不是替换框架的 `get_current_user_id`（`app/deps.py:34-56` 自认是临时方案）。开关 `ALIGO__AUTH__*`
- 多租户：沿用框架默认的 `DenyAllResourceAccessPolicy`（`app/_app.py:303-305`，已是 owner 隔离基线）；跨租户共享才用 `ResourceAccessPolicyBase` 显式开启
- `/api/v1/**` 业务路由骨架 + `src/storage/engine.py`

**验收**：`POST /chat/` → `GET /sessions/{id}/stream` 收到 `REPLY_START` + `TEXT_BLOCK_DELTA`（30s 心跳帧 `:\n\n`）；两个不同 `X-User-ID` 互相看不到对方会话。

**实际交付与偏差**（详见 `README.md` 与 `tests/test_e2e_stream.py`）：

- 中间件链最终是 **四个**：`TraceContext → HttpMetrics → Auth → RateLimit`（见上「与初稿的差异」）。
  写入顺序与执行顺序相反 —— `add_middleware` 内部是 `insert(0)`。
- 鉴权的**安全核心是先删后加**：Starlette 的 `Headers` 返回**第一个**匹配的 header，
  所以 `AuthMiddleware` 必须 `del` 掉客户端传来的 `X-User-ID` 再注入解析结果，
  否则伪造的 header 会赢。
- 验收线**已实测通过**：真实 uvicorn + 真实 TCP（不是 `httpx.ASGITransport` —— 它会缓冲整个响应，测不了 SSE）。
  两个关键时序事实被写进了测试：① SSE 连接**必须先于** `POST /chat/` 建立，
  因为 `_service/_chat.py` 在落库时会 `log_trim()` 掉整个重放日志；② `REPLY_END` 是**本轮对话**的结束，
  不是**连接**的结束 —— 服务端会保持连接并继续发心跳。
- 隔离性断言打在 `/messages`、`/stream`、`/status`、`GET /sessions/?agent_id=` 上（非 owner 一律 404）。
  `POST /chat/` **不能**用来验隔离：它是 fire-and-forget，对不存在的 session 也返回 `{"status": "started"}` ——
  这一条由一个断言**不变量**（而非行为）的测试覆盖。

### P3 · 智能体业务能力（目标：博客主链路可演示）✅

- **意图识别 Agent**：独立 Agent + `structured_schema` 拿多意图/消歧/query 改写；"显示推理"用 `ThinkingBlock` 事件天然呈现
- **快慢车道**：规则引擎 `classify()` 命中走快车道 —— 用 `LaneRouterMiddleware`(`on_model_call`) 强制 `tool_choice` 或直接短路；未命中走慢车道 ReAct
- **动态 Prompt**：`ContextInjectionMiddleware`(`on_system_prompt`) —— 该 hook **每次模型调用都重算**（`agent/_agent.py:3235-3239`），正是博客 `get_prompt_main_plan` 的现代形态
- **多智能体**：Routing = leader 用 `AgentCreate(subagent_type=...)` 选型；Handoff = `TeamSay` 回报。无状态专家（意图识别/改写/RAG）用 `FunctionTool` 包装；需独立会话与 HITL 的纵向域用 `SubAgentTemplate`
- **差旅工具集**：`FunctionTool` 包装，**返回值必须是 `ToolChunk(content=[TextBlock(...)])`** —— `content` 是必填的 **list**（`tool/_response.py:28-31`），传裸字符串会报错；用 `is_last` 而非旧文档里的 `is_interrupted`（本地版本无此字段）
- **思考链**：消费 `agentscope.event` 的 **28** 种 `EventType`（不是 27）

**验收**：快车道用例断言"未发生第二次模型调用"；多意图输入返回结构化拆解；前端渲染出自定义行程卡片而非 `DefaultRenderer`。

## 主要风险与对策

| 风险 | 对策 |
|---|---|
| Starlette `mount()` 不传递 lifespan → 存储/总线/调度永不启动 | **不 mount**，直接扩展 `create_app` 的返回值 |
| `Dockerfile --no-deps` 装 vendored 包 → 传递依赖缺失即 ImportError | `requirements.txt` 显式列全（已从两份 `pyproject.toml` 提取） |
| `ALIGO__` 未知键 → loader `extra_forbidden` 直接崩 | schema 为全部 29 个键留位；**`ALIGO__IMAGE_REGISTRY` 绝不能进 `.env`**（`check-env` 会拦） |
| 多 worker 下 `SchedulerManager` 每个进程都触发一次 cron | 保持 `WORKERS=1`（Dockerfile 默认，且该机 4 核）；或另起独立调度进程 |
| `InMemoryMessageBus` 在生产多进程下废掉 | **必须 `RedisMessageBus`**（`_in_memory_message_bus.py:8-14` 自述） |
| `download_secret` 每进程随机 → LB 后签名 token 失效 | 显式设为固定值（`app/_app.py:270-276` 警告） |
| **磁盘仅剩 16 GB** | 基础镜像已全部拉好（9.94 GB 已落地），`make up` 基本不需下载；P1 先 `docker system prune` 清 4.2 GB 可回收镜像 + 1.8 GB 构建缓存；`maxkb` 保持 `optional` 档不启用 |
| 容器内 pip 下载仅 180–240 kB/s | 本地 BGE 走 ONNX（不装 torch），镜像只多 ~150 MB；模型首次使用才下载并缓存 |
| 本机**未装 pnpm**（node v24.14.1 已有） | P4/P5 前 `corepack enable pnpm` 或 `npm i -g pnpm`；写进 README 前置依赖 |
| 工具权限要在 `on_check_permission` 做，不是 `on_acting` | `on_acting` 只包 `call_tool` 纯 I/O 层（`agent/_agent.py:2719`） |
| 前端 TS 定义与 28 个 `EventType` 是否对齐 | 【待验证】`pnpm install` 后比对 `@agentscope-ai/agentscope@^0.0.15` |
| 文档里的「文件:行号」与「N 个用例」会静默失效 | `make check-docs` 两个闸门常驻（`scripts/check_doc_{refs,counts}.py`），改动 `src/`、`config/`、`tests/` 或文档后必须重跑 |

## 验证方式

```bash
make up            # 起全栈（13 容器，含 postgres/redis/milvus）
make smoke         # 端到端冒烟：健康检查 + 一轮对话
make test          # pytest（含 Makefile 契约测试）
make check-docs    # 文档引用与计数校验
make up-tracing    # 追加 Langfuse，浏览器看全链路 trace
make milvus_init   # 幂等建 Milvus 集合，并回读核验维度/索引/度量（不灌数据）
make seed_data     # 灌差旅政策知识库与业务演示数据（不建集合）
python scripts/eval.py          # AI 评测集跑分
python scripts/loadtest.py      # 压测
cd web && pnpm install && pnpm dev   # 前端二次开发
```

⚠️ **顺序**：`make up` → `make milvus_init` → `make seed_data`。
两个脚本刻意分工（一个只管「集合建对了吗」，一个只管「库里有没有内容」），
跳过前者直接灌数据会因为集合不存在而失败 —— 详见 `docs/06-部署与运维.md` 第六节。
