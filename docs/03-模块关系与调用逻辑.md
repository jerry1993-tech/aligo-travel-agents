### 两个「刻意保持为空 / 只导出纯逻辑」的包

- `src/__init__.py` **刻意只有文档字符串**：任何在这里的 import 都会在「导入 `src` 下任意子模块」时被连带执行，
  从而把启动路径变得不可控，也会让一次循环导入以难以定位的方式炸开。
- `src/orchestration/__init__.py` **只导出纯逻辑**（`classifier`、`prompt`），框架耦合的 `lane` / `context`
  由使用方按完整路径导入。理由与验证方式见 `docs/02-技术架构.md` 第二节。

## 二、启动装配的调用顺序

`create_root_app`（`src/server/app.py:646`）是**纯装配**：不建立任何网络连接（引擎/存储都是惰性拨号），
因此可以在单测里安全调用。下面是它**从上到下**实际做的事，以及每一步为什么必须在那个位置。

```text
create_root_app()
 │
 ├─ 1. 取 settings（未传则用进程内单例）
 │
 ├─ 2. build_memory(settings, engine=lambda: engine_box["engine"])   ← 必须在 create_app 之前
 │        · engine_box 是本次调用**私有**的字典（不是模块级全局）
 │        · 为什么用「函数」而不是引擎：装配期引擎还没建（在 lifespan 进入段才建），
 │          推迟成取函数后，第一次查画像拿到的总是**当时活着**的那个引擎
 │
 ├─ 3. agent_wiring = build_agent_wiring(settings, memory=memory)    ← 必须在 create_app 之前
 │        · 见第四节：它构造模型与工具集
 │
 ├─ 4. resolved_storage = storage or build_storage(settings)         ← 落一个本地变量
 │        · create_app 与知识库管理器必须拿到**同一个实例**
 │          （各造一个的后果：「KB 记录写进 A，对话链从 B 读」）
 │
 ├─ 5. app = create_app(storage=…, message_bus=…, workspace_manager=…,
 │                      knowledge_base_manager=…, enable_scheduler=…,
 │                      enable_channel_worker=False,
 │                      download_secret=…, extra_credentials=[MockCredential],
 │                      **agent_wiring.as_kwargs())
 │
 ├─ 6. app.router.lifespan_context = _wrap_lifespan(框架 lifespan, settings, engine_box)
 │
 ├─ 7. setattr(app.state, BOOT_COMPLETED_ATTR, False)
 │      setattr(app.state, MEMORY_ATTR, memory)
 │
 ├─ 8. app.include_router(probes_router)        # /healthz /readyz /metrics
 ├─ 9. app.include_router(api_v1_router)        # /api/v1/**
 │
 ├─ 10. add_middleware 循环  [RateLimit, 降级凭据播种, Auth, HttpMetrics, TraceContext]
 │        # 书写顺序与执行顺序相反；执行序见 3.3 的五行链
 │
 └─ 11. _mount_static_if_present(app)           # 必须最后：挂到 "/" 会吃掉所有未命中路径
```

`src/server/app.py:1072` 的模块级 `app = create_root_app()` 意味着**导入 `src.server.app` 就等于装配整个应用**。
这么设计是为了让 `uvicorn --workers N` 下每个 worker 各自持有独立的 storage / message_bus / 熔断器；
若改成 lifespan 里懒装配，会有 asyncio 原语跨进程共享的风险。

### 2.1 为什么 `memory` 与 `agent_wiring` 必须在 `create_app` **之前**

`create_app` 的 `extra_agent_tools` / `extra_agent_middlewares` / `custom_subagent_templates`
这三个扩展点**只在它内部被读一次**。放在它之后，应用已经带着「没有业务能力」的状态构造完了，
再补参数也补不进去。所以整条智能体装配必须在 `create_app` 调用之**前**完成。

> 反过来，`app.state` 上的两个属性（`BOOT_COMPLETED_ATTR` / `MEMORY_ATTR`）**必须**在 `create_app` 之后挂，
> 因为那之前还没有 `app` 对象。中间件工厂拿到的是一个闭包，闭包里捕获的是 `memory` 本身，
> 与它挂在哪无关。

### 2.2 为什么是「复用 `create_app` 的返回值作根应用」而不是 mount

`create_app` 把 lifespan 挂在它自己创建的 FastAPI 实例上（`app/_app.py:292`），
而 **Starlette 的 `mount()` 不会触发子应用的 lifespan**。若按官方的
`root.mount("/agentscope", agentscope_app)` 写：

1. `chat_service` / `session_service` / `scheduler_manager` **全在 lifespan 里**才写入 `app.state`，
   于是取 `app.state.chat_service` 会 `AttributeError` ⇒ **所有业务端点 500**；
2. 前缀 mount 还会打断官方前端（它用 `new URL(path, baseUrl)` 且调用处传绝对路径，前缀会被丢掉）。

对策是让 `app = create_app(...)` 的返回值**直接作根应用**，再 `include_router` / `add_middleware` /
包一层 lifespan。三个好处：lifespan 天然执行；无前缀问题；`StaticFiles` 最后 mount 到 `/` 不会遮蔽 API。

### 2.3 `_wrap_lifespan` 的进入 / 退出顺序

`_wrap_lifespan`（`src/server/app.py:442`）把框架的 lifespan 包一层。顺序是这段代码的**全部要点**：

```text
进入段：
  configure_logging(settings)            ← ⚠️ 这里已是**第二次**调用：第一次在 app.py 的
                                            模块级（`app = create_root_app()` 之前），
                                            否则装配期打的 INFO 一条都看不到
                                            （幂等标记让这一次直接返回）
  setup_tracing(settings)                 ← 先于框架启动，才能采到启动阶段的 span
  business_engine = build_business_engine(settings)   ← 构造不建连接（惰性拨号）
  setattr(app.state, BUSINESS_ENGINE_ATTR, business_engine)
  engine_box["engine"] = business_engine               ← 与退出段的清空必须成对
  ┌─ async with framework_lifespan(app): ─────────────────────────┐
  │    ensure_business_schema(...)        ← 必须在 boot_completed 之前 │
  │    ensure_profile_table(...)  (失败只记日志，不中止)              │
  │    setattr(app.state, BOOT_COMPLETED_ATTR, True)   ← ★ 关键      │
  │    ---- yield：开始对外服务 ----                                 │
  │    finally: setattr(app.state, BOOT_COMPLETED_ATTR, False)       │
  └────────────────────────────────────────────────────────────────┘
退出段（finally）：
  engine_box["engine"] = None             ← 先清空**再** dispose
  await business_engine.dispose()
  shutdown_tracing()
```

三个位置相关的硬约束：

1. **`boot_completed` 必须严格在框架 lifespan 的进入段之后置位**。放之前（资源没就绪）或放 yield 之后
   （已经开始服务了）都是错的。框架自己的 lifespan **不设**这个标志，是我们自己设的。
2. **业务 schema 的引导必须在 `boot_completed` 之前完成**。反过来的话，`/readyz` 会在 schema 还没建好的
   那几十毫秒里报「就绪」，此刻打进来的请求会撞上 `relation "business.xxx" does not exist`。
   就绪探针的语义是「**现在**打进来能成功」，不是「马上就能成功」。
3. **`engine_box` 先清空再 dispose**。顺序反了的话，从 dispose 开始到清空之间有一小段窗口，
   此时盒子还指着一个正在关闭的引擎，恰好落在窗口里的画像查询会拿到一个半死的连接。

⚠️ **画像表建表失败不让启动失败**：画像是对话的增强，不是前提。代价说清楚——此时 `/readyz` 报的就绪是真的，
但「记住偏好」这类**写入**会失败（以异常形式出现在用户面前，不是静默），读取会正常降级为「没有画像」。

⚠️ 退出段里 dispose 在 `shutdown_tracing` **之前**，理由只有一条：dispose 期间仍可能产生 span，
provider 关掉之后新建的 span 会被直接丢弃，于是 trace 里恰好缺掉「关闭时到底发生了什么」那一段。

## 三、凭据引导链路的调用顺序

> **这条链路治的是什么**：框架的对话链路**不靠全局默认模型**工作，它要两样东西同时在位 ——
> (a) 一条**调用者可解析**的 credential 记录；(b) 会话的 `chat_model_config` 指向它。
> 缺任何一个 ⇒ 探针全绿、SPA 正常渲染、但「发送」按钮永远灰着（前端可用模型是
> `GET /credential/` × `GET /model/?provider=` 拼出来的，零凭据 ⇒ 分组为空 ⇒ `selectedModel === null`）。
> 接口形态与四种 mode 的字段见 `docs/01-功能接口.md` 2.4；安全论证见 `docs/02-技术架构.md`。

两条**互斥且互补**的引导路径，由 `should_use_mock(settings)`（`src/llm/factory.py:127`）在装配期二选一：

| 配置形态 | 路径 | 凭据形态 |
| --- | --- | --- |
| `should_use_mock == True`（零密钥降级） | `MockCredentialSeedMiddleware` 按需播种 | 每个已鉴权用户**各自一条** Mock 凭据（无秘密，复制一万份也不损失什么） |
| 降级关闭且 `has_api_key`（`src/llm/factory.py:103`） | 系统凭据共享 | **一条**属主为 `aligo-system`（`src/llm/identity.py:42`）的真凭据，经访问策略以 READ 共享给全体已鉴权用户 |

⚠️ **为什么真 key 只共享、不复制**：框架的可见性规则是「属主读自己的凭据是**明文**」
（非属主的 `data` 才被 `_build_view` 打码成 `{type, name}`，`third_party/agentscope/src/agentscope/app/_service/_access.py:548-569`）。
把真 key 复制进每个用户的记录 = 一次共享、全员泄密。所以真 key 只有一条记录，
而 `aligo-system` 这个属主身份**必须不可被客户端声明** —— 否则一次 `GET /credential/`
就能读出明文、一次 `DELETE` 就能让全员当场失效（保留身份与三条通道的拦截见 `docs/01-功能接口.md` 五）。

### 3.1 装配期（`create_root_app` 内，全部在 `create_app` **之前**）

与这个功能相关的部分，在 `create_root_app`（`src/server/app.py:646`）里的实际顺序是：

```text
create_root_app()
 │
 ├─ 1. engine_box = {"engine": None} + build_memory(...)      # src/server/app.py:705
 │
 ├─ 2. resolved_storage = storage or build_storage(settings)  # src/server/app.py:720
 │        · 落一个本地变量：create_app 与知识库管理器必须拿到同一个实例
 │
 ├─ 3. app_box = {"app": None}                                # src/server/app.py:742
 │        └─ _access_policy_provider()  ← 延迟取策略的「取函数」  # src/server/app.py:744
 │             · 给知识库管理器用的第三个「盒子」（见 3.4）
 │
 ├─ 4. kb_manager = build_knowledge_manager(..., access_policy_provider=…)  # src/server/app.py:753
 │
 ├─ 5. agent_wiring = build_agent_wiring(...)                 # src/server/app.py:770
 │
 ├─ 6. system_box = {"seeded": False}                         # src/server/app.py:787
 │      resource_access_policy = build_access_policy(settings, system_box)  # src/server/app.py:788
 │        · build_access_policy 定义在 src/llm/system_credential.py:327
 │        · 零密钥 ⇒ 返回 None ⇒ 框架回落 DenyAllResourceAccessPolicy（owner 隔离）
 │
 ├─ 7. app = create_app(..., resource_access_policy=…)        # src/server/app.py:790
 │
 ├─ 8. app_box["app"] = app     ← 必须在 create_app **之后**    # src/server/app.py:861
 │
 └─ 9. app.router.lifespan_context = _wrap_lifespan(           # src/server/app.py:866
          …,
          system_box if resource_access_policy is not None else None,  # src/server/app.py:873
      )
```

**为什么每一步必须在这个位置**：

- **第 3 步为什么是「取函数」而不是策略对象**：策略对象是**框架**在 `create_app` 内部写进
  `app.state.resource_access_policy` 的（`third_party/agentscope/src/agentscope/app/_app.py:303-304`），
  而知识库管理器在第 4 步就要构造好。传对象意味着「装配顺序决定谁能看见什么」，
  传取函数则让顺序不再是契约的一部分（`src/knowledge/manager.py:111-116` 的原话）。
- **第 6 步的 `system_box` 为什么是每次装配私有的字典**：与 `engine_box`（`src/server/app.py:702-709`）
  同形 —— 「装配期构造、就绪期才成立」。策略对象必须在 `create_app` **之前**交出去，
  而「那条凭据到底写成功没有」要等 lifespan 里 storage 进入异步上下文才知道。
  盒子私有 ⇒ 不同应用实例（单测里常见）互不串：做成模块级全局的话，
  一个实例的 `seeded=True` 会残留给下一个实例。
- **第 8 步为什么必须在 `create_app` 之后**：`app` 就是 `create_app` 的返回值，
  在这之前不存在可赋的对象；而任何「提前把策略取出来存一份」的想法更糟 ——
  策略是框架在 `create_app` 内部才置到 `app.state` 上的，提前取永远拿到 `None`，
  症状是「用共享凭据建的知识库检索时静默失效」（`src/server/app.py:862-867` 的注释）。
  ⚠️ 也不要按 `RESOURCE_ACCESS_POLICY_ATTR` 自己 `setattr` 一遍：**框架只在 `create_app`
  装配期写这个属性、之后不再碰它**（`third_party/agentscope/src/agentscope/app/_app.py:303-304`；
  其 lifespan 只读取，见 `app/_lifespan.py:56`，并把对象传给 `ResourceAccessService`，见 `:108`）——
  所以自己 `setattr` 的后果是：写在 `create_app` **之前**会被框架覆盖（白写），
  写在**之后**则**不会被覆盖**、从此有两个真相（框架那份与你自己那份，谁生效取决于谁读）。
  两种写法都坏，只是坏法不同（`src/server/constants.py:90-100`）。
- **第 9 步的 `system_box if resource_access_policy is not None else None`**：没注册策略却播种，
  会写出一条**没有任何人能看见**的凭据（策略没生效 ⇒ 列表里不出现），却要付一次数据库写入。
  传 `None` 让这条路径在装配期就断掉（`src/server/app.py:877-880`）。

### 3.2 就绪期（`_wrap_lifespan` 的进入段）

```text
async with framework_lifespan(app):            # storage / message_bus 进入异步上下文
    ensure_business_schema(...)                # 见 2.3
    ensure_profile_table(...)                  # 失败只记日志
    if system_box is not None:                 # src/server/app.py:579
        _seed_system_credential(app, settings, system_box)      # src/server/app.py:352
          ├─ system_box["seeded"] = False                  # 每次进入先重置（:394）
          ├─ if not sharing_enabled(settings): return      # 零密钥 = 正常路径，不打日志（:395）
          ├─ storage = app.state.storage                   # 取不到 ⇒ logger.error（:399-405）
          ├─ ensure_system_credential(storage, settings)   # 构造凭据 + 覆写 id/显示名
          │     └─ upsert_preset_credential(...)           # 幂等写入（见下）
          ├─ 成功 ⇒ system_box["seeded"] = True + logger.info          # :422/:426
          └─ 失败 ⇒ logger.exception 后 return —— **绝不阻断启动**      # :409-414
    setattr(app.state, BOOT_COMPLETED_ATTR, True)          # ★ 必须在播种之后（:583）
```

两条位置硬约束、两条失败取舍：

- **必须在 `framework_lifespan` 进入段之后**：storage 是在那里面才进入异步上下文的，
  放到外面写库会撞上「存储尚未启动」（`src/server/app.py:578-580`）。
- **必须在 `BOOT_COMPLETED_ATTR` 置位之前**：反过来的话，`/readyz` 已报 200，
  而这段时间打进来的请求会得到「可用模型为空」—— 正是本机制要消灭的状态（`src/server/app.py:572-575`）。
- **每次进入先置回 `False`**（`:394`）：不重置的话，第二次进入（测试里常见）若播种失败，
  盒子还留着上一轮的 `True`，策略会继续分享一条**本次启动根本没写成功**的凭据（`:375-377`）。
- **失败绝不阻断启动，但必须带栈**：共享是可用性增强，不是启动前提；代价说清楚 ——
  失败时 `/api/v1/default-model` 返回 `missing` 而不是 `shared`，那是**如实**的答复
  （`seeded` 没置位，用户确实用不了）。日志必须是 `logger.exception`，因为症状
  「所有人都是 missing」与「运营者压根没配密钥」完全一样，没有栈就无从区分（`:360-373`）。

⚠️ **为什么现在这条栈里不会出现 api_key**：唯一可能带绑定参数的异常来自那条 INSERT，
而**部署路径上的每个 engine**（`src/` 与 `scripts/` 下的全部 `create_*_engine` 调用点，
共 2 处：业务引擎与探针引擎）都开了 `hide_parameters=True`（`src/storage/engine.py:125`；框架 storage 也通过
`build_storage` 的 `engine_kwargs` 拿到同一份参数，`src/server/app.py:194`）。SQLAlchemy 默认把
绑定参数渲染进异常文本（`[parameters: ('aligo-system-model', 'aligo-system', '{"api_key": "sk-..."}')]`，
示例值是明显的假值），打开后变成 `[SQL parameters hidden due to hide_parameters=True]`。
改动那个开关前请先读那里的注释。

**幂等写入的形状**：`ensure_system_credential`（`src/llm/system_credential.py:226`）把
`build_credential` 构造出的对象覆写 id（固定 `aligo-system-model`，`:100`）与显示名后交给
`upsert_preset_credential`（`src/llm/preset_credential.py:71`）。框架对**带预设 id** 的写入是「先查后写」：
id 不属于调用者时走直接 INSERT，撞全局主键就抛 `IntegrityError`（框架有意如此：防跨租户覆盖）。
但那在「两个执行者同时给同一用户首次播种」时是**并发**、不是故障，所以只把
`type(exc).__name__ == "IntegrityError"` 当冲突并重试一次（`:94`）；其余异常原样抛出；
重试后仍冲突也照样冒泡（第二次不再捕获，`:99-102`）。改了密钥重启即生效，记录不会越长越多。

### 3.3 请求期

```text
请求 → TraceContext → HttpMetrics → Auth → MockCredentialSeedMiddleware → RateLimit → 应用
                                      │                │
                                      │                └─ 零密钥降级：按需为本次身份播种 Mock 凭据
                                      └─ 确立身份；命中保留身份 ⇒ 403（不是 401）
```

- **Auth 先确立身份**：`X-User-ID` 直连 / JWT 的 `sub` / `require_user_header=false` 的匿名
  三条通道都在放行前拒绝保留身份 `aligo-system`（`src/server/middleware/auth.py:361`、`:392`、`:461`），
  返回 **403 而不是 401** —— 401 会让客户端去走登录流程，而没有任何登录能变成系统身份
  （`:543-570`）。
- **Mock 播种中间件在 Auth 之内、RateLimit 之外**：⚠️ 注意这是**执行**顺序。
  `src/server/app.py:976-996` 的 `add_middleware` 书写顺序与执行顺序**相反**
  （`insert(0)` ⇒ 后写的在最外层），所以它在**书写列表里是第 2 项**
  （`[RateLimit, 本中间件, Auth, HttpMetrics, TraceContext]`）。
  在 Auth 之内才读得到身份；在 RateLimit 之外，限流不该被一次数据库写入拖慢。
  `should_use_mock` 只在装配期读一次（`src/server/middleware/mock_credential.py:93`），
  关闭时整条快路径直接透传（`:113`）。
- **为什么是「按需」而不是「启动时」**：没有用户表，身份来自请求，启动那一刻不知道将来会有谁用；
  这也顺带解决「没人会莫名其妙拥有一条凭据记录」（`src/llm/degradation.py:39-46`）。
  请求期读 `scope["state"]` 里的身份（`src/server/middleware/mock_credential.py:121`），
  无身份或本进程已播过则跳过（`:121`）；`asyncio.Lock`（`:99`）把「首次写入」窗口收窄到
  只有一个请求在写 —— 页面加载时前端会同时打好几个端点 —— 剩下的边角由 upsert 的重试兜住。
  失败只 warning 一次（`:139-146`），**绝不阻断请求**（播种是可用性增强，不是业务请求的一部分）。
- **`GET /api/v1/default-model` 的四种 mode**（`src/server/routers/_default_model.py:78` →
  `resolve_default_model`，`src/llm/degradation.py:199`），判定顺序是刻意的：
  ① `mock`（`:240`，开关开着本身就是运营者的明示选择）→ ② `configured`（`:263-279`，
  用户自己有凭据就**不替他选**；⚠️ 必须排在 `shared` 之前，否则一个自带公司密钥的用户
  会被悄悄切到系统凭据上，账单与配额都算错地方）→ ③ `shared`（`:287-306`，用
  `policy.list_accessible` 判定「**能不能用**」，不是「记录在不在」）→ ④ `missing`（`:307-311`，
  给一句可执行的 hint）。四种模式都是 200、都不含任何密钥；解释文案是常量
  `HINT_MOCK` / `HINT_CONFIGURED` / `HINT_SHARED` / `HINT_MISSING`（`:121-138`），
  供 smoke 脚本与文档引用同一句话。字段与前端边界见 `docs/01-功能接口.md` 2.4。
- **之后对话链路怎么用上它**：调用方把返回的 `chat_model_config` 写进会话；框架在
  `third_party/agentscope/src/agentscope/app/_service/_chat.py:1097-1105` 读
  `session_record.config.chat_model_config`，为空直接 `HTTPException(404, "No model configuration found for agent ...")`；
  随后 `get_model(user_id, model_cfg, self._access)`（`:1106`）经访问策略解析 credential
  （`resolve_credential` 先按属主、再按共享 refs，`third_party/agentscope/src/agentscope/app/_service/_access.py:376`）。
  这正是 `mock` / `shared` 给配置、`configured` / `missing` 不给的原因 ——
  只有前两种的 `credential_id` 对调用者是可解析的。
- **长期记忆的显式读写面**（`src/server/routers/_memory.py`）：五个端点的身份都来自
  `Depends(get_current_user_id)`，门面从 `app.state` 上的 `MEMORY_ATTR` 取
  （`src/server/routers/_memory.py:84`）。
  往下是同一个 `TravelerMemory`：画像走 `SqlProfileRepository`（`business.traveler_profiles`，
  lifespan 里建表），笔记走 `SemanticMemory`（Milvus 的 `{集合}_memory`）。
  ⚠️ 这一层与**对话链路**用的是同一个门面，但错误语义相反：对话链路里读失败降级为
  「没有画像」（见 §五.2），而显式接口把失败**报出来**（能力缺失 503、召回失败
  `200 + error`、写失败 503 且明说「没有生效」）——理由写在 `docs/01-功能接口.md` 2.5。

### 3.4 知识库那条线：共享凭据与 KB 之间的一道缝

```text
_resolve_embedding_credential(owner_id, credential_id)     # src/knowledge/manager.py:308
 ├─ 第一跳：storage.get_credential(owner_id, credential_id)          # :365（框架自带语义）
 └─ 第二跳（属主查不到时）：provider() → policy.list_accessible(owner_id, CREDENTIAL, storage)  # :369-382
       └─ 找到 ref.resource_id == credential_id 后，用 ref.owner_id 再查一次      # :386-391
```

- **为什么用 `ref.owner_id` 而不是 `owner_id`**：跨属主引用的全部价值就在「记录在别人名下」；
  用 `owner_id` 再查一次只会得到与第一跳相同的 `None`（`src/knowledge/manager.py:386-388` 的注释）。
- **它补的是框架哪两处假设之间的缝**：`GET /knowledge_bases/embedding_models` 明确把**共享凭据**
  列进可选列表（docstring 原文 "own + shared … so KB creation works against shared credentials too"，
  `third_party/agentscope/src/agentscope/app/_router/_knowledge_base.py:104-105`），而框架自带的
  `CollectionPerKbManager.get_knowledge` 只按**属主**查 embedding 凭据
  （`third_party/agentscope/src/agentscope/app/rag/knowledge_base_manager/_collection_per_kb.py:187-195`，
  那里自述的前提是 "KB manager is an owner-internal path"）。用户用共享凭据建出来的 KB 因此钉着一个
  别人的 `credential_id`：检索时按属主解析不出 ⇒ `KnowledgeBaseNotFoundError` ⇒ 对话链把它吞成
  一行「Skipping knowledge base」（`third_party/agentscope/src/agentscope/app/_service/_chat.py:1054`）
  ⇒ **知识库静默失效**，而上传、索引、前端列表全都显示正常。这正是本项目最想消灭的那类故障：
  探针全绿、界面正常、功能不在。
- **为什么这不会放宽权限**：`get_knowledge` 传给它的 `owner_id` 始终是 KB 记录的属主
  （`record.user_id`，`src/knowledge/manager.py:431`），第二跳问的是「**该属主**能访问什么」——
  策略不给它，这里照样解析不出来。规则也不另立一套：框架运行期解析模型凭据同样走
  「先按属主、再按可访问的 refs」。
- 装配那一半（`provider` 从哪来、为什么必须在 `create_app` 之后才填盒子）见 3.1 第 3、4、8 步。

## 四、智能体装配：`build_agent_wiring` 往下

`build_agent_wiring`（`src/server/agents_factory.py:655`）产出一个 `AgentWiring`，
它把三条**类型形态完全不同**的扩展点打包，一次性喂给 `create_app`：

| `AgentWiring` 字段 | 喂给 `create_app` 的 | 形态 |
| --- | --- | --- |
| `tools_factory` | `extra_agent_tools` | **async 工厂** `(user_id, agent_id, session_id) -> list[ToolBase]` |
| `middlewares_factory` | `extra_agent_middlewares` | **async 工厂** `(…) -> list[MiddlewareBase]` |
| `subagent_templates` | `custom_subagent_templates` | **静态列表** `list[SubAgentTemplate]` |

> `as_kwargs()` 的三个键名是 `create_app` 的**公开参数名**，不是 `app.state` 上的属性名。
> 看着像但是两回事——`app.state` 上 `custom_subagent_templates` 存的是 **dict**。

### 4.1 内部构造顺序

```text
build_agent_wiring(settings, memory=…)
 ├─ repos = build_repositories(settings)            # 见下：P3 是内存实现
 ├─ chat_model = build_chat_model(settings)         # src/llm：零密钥 → MockChatModel
 ├─ templates = build_subagent_templates()          # src/agents/registry
 └─ return AgentWiring(
        tools_factory      = build_tools_factory(settings, repositories=repos, model=chat_model),
        middlewares_factory= build_middlewares_factory(settings, memory=memory),
        subagent_templates = templates,
    )
```

**`RepositoryBundle`**（`src/server/agents_factory.py:113`）——用**一个对象**打包五个仓储
（transport / hotel / policy / order / approval），而不是让调用方分别持有五个引用。
理由是它们必须**同生共死**：P4 换成 Postgres 时五个要一起换成同一连接池上的实例；
分别持有的话很容易只换三个，剩下的仍指向内存——那种混用不报错，只会让一部分数据「写进去查不到」。
bundle 是 `frozen=True` 的：仓储的**引用**不该在运行期被替换，要换实现就重新构造一个 bundle。

> ⚠️ `build_repositories`（`src/server/agents_factory.py:140`）在 P3 是**内存实现**
> （`src/storage/memory.py` 的确定性模拟数据），P4 才接 Postgres。
> 它的 `_settings` 参数现在**用不上但刻意留着**——把「换实现时调用方不用改」这件事提前兑现。

### 4.2 `build_tools_factory`（`src/server/agents_factory.py:207`）

产出一个 async 工厂，**每次请求**被框架调用一次来构造这轮的工具列表：

- `intent_tool`（`recognize_intent`）**只构造一次**（`build_intent_tool`），因为识别器内部每次调用都新建 Agent，
  持有单个实例是安全的；
- 业务工具（`build_business_tools`）按请求构造，这样工具能拿到当前用户/会话上下文。

工具清单与卡片契约见 `docs/01-功能接口.md` 第四节。

### 4.3 `build_middlewares_factory`（`src/server/agents_factory.py:476`）

产出每条链路上生效的**智能体级**中间件（注意：不是 HTTP 中间件），是**固定的四段**
（`src/server/agents_factory.py:609-619`），顺序是：

```text
LaneRouterMiddleware（最外层）→ TracingMiddleware → BreakerMiddleware → ContextInjectionMiddleware（最内层）
```

- **`LaneRouterMiddleware`**（`src/orchestration/lane.py`）判快慢车道并**短路「第一次模型调用」**——
  它不是拒绝请求，而是直接产出路由决策。它拿到的 `agent_names` 是 `(MAIN_AGENT_NAME,)`，
  即只在主规划智能体上生效。两个守卫保证它只短路一次：`cur_iter == 0` 且本轮尚未记录过 `reply_id`。
- **`TracingMiddleware`**（框架 OTel 埋点，`:617`）位置同样是刻意的：**在车道之内**
  （避免为快车道短路的假调用开 span）、**在熔断之外**（让被熔断拒绝的调用留下 error span）。
- **`BreakerMiddleware`**（`src/llm/`）读**全体智能体共享**的熔断器单例。
- **`ModelTimeoutMiddleware`**（`src/llm/middleware.py`）在熔断**之内**、上下文注入**之外**：
  熔断器要「先看到失败」才可能开路，所以超时必须发生在它之内 ——
  `ModelCallTimeout` 顺着链冒到熔断器，被记成一次下游失败。
  它补的是熔断器**管不到**的那一半：卡住不返回的调用既不抛异常也不返回，
  熔断器永远数不到账、请求也永远不返回。
- **`ContextInjectionMiddleware`**（`src/orchestration/context.py`）在最内层，通过 `on_system_prompt`
  把画像与已知槽位拼进 system prompt。它在最内层，才能看到前几层改动后**最终**的 prompt。

### 4.4 子智能体模板

`build_subagent_templates()`（`src/agents/registry.py`）从注册表生成模板。
默认 5 个智能体：`main_plan`（主规划）、`intent`、`policy_rag`、`approval`、`order_query`。
模板里的占位符集合是 `PLACEHOLDERS`（`team_name` / `team_description` / `member_name` /
`member_description` / `leader_name`）。提示词本体在 `src/agents/prompts.py`，是**纯数据**，不 import 框架。

## 五、一次请求内各模块的协作

HTTP 中间件链、鉴权注入、SSE 端点的细节分别在 `docs/01-功能接口.md` 与 `docs/02-技术架构.md`。
这里只补三条**跨模块**的调用关系：

1. **HTTP 链路**：`AuthMiddleware` 注入 `x-user-id` → 框架 `get_current_user_id` 读出它 →
   存储层按该身份过滤（`/api/v1/me` 就是拿这条线做证明）。
2. **提问链路**：`ContextInjectionMiddleware.on_system_prompt` 从 `memory` 门面取画像摘要，
   拼进 system prompt；**这条路径上**的读**永不抛异常**（降级为「少了点个性化」而对话继续）。
   ⚠️ 同一条门面的另一条出口是显式接口 `/api/v1/memory/**`，那里读失败**要报出来** ——
   两处语义相反是刻意的，见 §3.3 最后一条。
3. **事件链路**：框架每条 `AgentEvent` → `EventChainAdapter.consume` 更新 `TaskCollector` →
   `iter_task_states` 扁平化成快照 → `/api/v1/sessions/{id}/chains` 推给前端。
   adapter 与 collector 是**每连接各一份**的（见 `docs/01-功能接口.md` 2.3）。
