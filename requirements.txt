# ==============================================================================
# 文件职责：AliGo 差旅助手的**第三方依赖清单**（唯一真值）。
#
# 上下游依赖：
#   - 上游：被 `Dockerfile` 的 builder 阶段以 `pip install -r /tmp/requirements.txt`
#           安装；被本机开发环境以同一份清单安装，从而保证「本地跑得过 = 容器跑得过」。
#   - 下游：`src/` `scripts/` `tests/` 全部代码 import 的第三方能力都出自这里。
#
# ------------------------------------------------------------------------------
# 【为什么这份清单必须「显式列全」，而不能靠 pip 自动解析】
# ------------------------------------------------------------------------------
# Dockerfile 第 56 行用 `pip install --no-deps --no-build-isolation` 安装两个
# **本地源码包**（third_party/agentscope 与 third_party/ReMe）：
#     `--no-deps` 的含义是「只装这两个包本身，**不要**去解析它们的依赖」。
# 这么做的理由见 Dockerfile 该段注释（避免解析出与本地开发环境不一致的版组合）。
# 代价是：**这两个包在各自 pyproject.toml 里声明的依赖，pip 一个都不会装** ——
# 少写一条，容器启动时就是一句难以归因的 `ModuleNotFoundError`。
# 因此下面第 一、二 节的条目，是从两份 pyproject.toml 的 `dependencies` 与
# 我们实际启用的 `optional-dependencies` 逐条誊抄而来的，**不是**凭印象写的。
#
# 已启用的 agentscope extras（对应下面的分节）：
#   service        —— FastAPI 服务层（create_app 的宿主）
#   storage-redis  —— RedisStorage / RedisMessageBus
#   storage-sql    —— AsyncSQLAlchemyStorage（会话与消息落 PostgreSQL）
#   vdb-milvus     —— Milvus 向量库（本项目唯一向量库，见 docker-compose.yaml 第五节）
# 未启用的 extras 及理由：
#   channel        —— 钉钉/飞书/Discord 适配器，本项目不接外部 IM
#   workspace-*    —— 各云沙箱后端，本项目用 LocalWorkspaceManager
#   models         —— gemini/ollama/xai 三家模型，本项目走 OpenAI 兼容协议（DeepSeek）
#   tools          —— 只含 `ripgrep>=14.1,<15`，**必须排除**：它只发布了
#                     macOS-arm64 与 manylinux_2_39 的 wheel，而本镜像基于
#                     python:3.11-slim（Debian bookworm，glibc 2.36）⇒ 拿不到 wheel
#                     ⇒ 回落到 Rust sdist ⇒ 构建期**必然失败**（该风险由上游 pyproject
#                     自己的注释写明）。本项目不使用内置 Grep 工具，故不装。
#   rag            —— 文档解析器（pdf/pptx/docx/xlsx），P4 灌知识库时再按需追加，
#                     理由见文末「P4 追加」一节：这些库的重导入都在方法内部
#                     （`rag/_parser/_pdf.py:66` 等），不装也不影响 import。
#   tui / a2a / realtime / memory-mem0 —— 本项目用不到
#
# ------------------------------------------------------------------------------
# 【关于版本钉法】
# ------------------------------------------------------------------------------
# 一律用 `==` **精确钉死**到本机已装、且已被实际跑通的版本（取证命令：`pip list`）。
# 不用 `>=`：本项目已多次踩到「上游同名不同码」的坑（见 README「三条硬性约定」），
# 浮动版本会让「本地绿、容器红」这类问题无法复现。改版本请连同本文件上方的
# 分节注释一起复核。
# ==============================================================================

# ⚠️ fastmcp **必须停在 3.x，绝不能升到 4.x** —— 这是本文件里唯一一处「版本被上游依赖
#    反向钉死」的地方，把原因写清楚，免得后人顺手升级后又踩一次：
#      · fastmcp 4.0.x 的元包**无条件**依赖 `fastmcp-slim[client,server]==4.0.x`，
#        而该 slim 包在 client / server 两个 extra 上都要求 `mcp>=2.0.0,<3.0.0`；
#      · 但 agentscope（`third_party/agentscope/pyproject.toml:29`）要求 `mcp<2.0.0`，
#        本文件第 62 行据此钉了 `mcp==1.30.0`。
#      ⇒ 4.x 与 agentscope 的要求**在区间上不可能同时满足**：Dockerfile 第 48 行是
#        一次 `pip install -r` 整体求解，于是直接以 ResolutionImpossible 失败
#        （2026-09-24 `make up` 实测报错原文：
#         "Cannot install fastmcp-slim[client,server]==4.0.5 and mcp==1.30.0 ..."）。
#      · 而 fastmcp 3.4.x 的 slim 包要求 `mcp<2.0,>=1.24.0` —— 与 agentscope 的要求
#        **区间相容**，`mcp==1.30.0` 同时落在两者之内，冲突就此消解。
#      · ReMe 自己声明的是 `fastmcp>=3.1.0`（`third_party/ReMe/pyproject.toml:27`），
#        3.4.7 满足；且 ReMe 对 fastmcp 的 import **全部写在函数体内的惰性 import**
#        （`grep -rn 'from fastmcp' third_party/ReMe/reme/` 可见），`import reme` 本身
#        根本不触碰 fastmcp，所以降这一档不会让「默认关闭的 ReMe 开关」变成坏开关。
#    已验证（2026-10-01，非推断）：容器内 `mcp==1.30.0 + fastmcp==3.4.7` 下，ReMe 实际
#    用到的 13 个 fastmcp 符号（FastMCP / Client / ToolError / FunctionTool / Transport /
#    combine_lifespans / SSETransport / StdioTransport / StreamableHttpTransport /
#    CallToolResult 等）**逐个 import 成功，13/13 通过**；且全量
#    `pip install --dry-run --ignore-installed -r requirements.txt` 求解通过（rc=0）。
